# S23 O6 — 窗口 P：O3/O4 内核端到端验收（第一个兑现的设备侧收益 + O4 被 parity 打回）

> perf-verifier 的 O6 数据与判读。工具与协议见 [`s23-o6-tooling.md`](s23-o6-tooling.md)。
> 纪律：**只比同窗口内的臂**；plan §1 的 193.8 ms / 19.2 t/s 是历史窗口，和本文任何数字都不可直接比较。

## 0. 一句话

- **O3（decode tile 拦截项）端到端兑现**：同一窗口、同一 python 树，换 `7f87e185` 构建 + `DECODE_CFG=35`
  后 c=1 warm p50 **148.58 → 137.68 ms（−7.34%）**，输出 **27.82 → 29.06 t/s（+4.13%）**，
  accept 7.00 / tok/step 7.53 不变，parity **8/8 逐 token 一致**。与 plan 的 c=1 理论上界
  （−9.8 ms/138 ms = −7.1%）吻合 —— 说明上界预测本身是对的，不是运气。
- **O4（`VLLM_DCU_FP8_STREAM_MAX_M=8` 把 `5120:1536` 从 stream 改走 tile）不发布**：
  它确实更快（warm p50 再 **−1.9%**，合计 −9.20%），但**破坏 bit-exact greedy parity**：
  8 条 prompt 里 5 条逐 token 分叉，且**重试后仍然分叉**（真数值差异，不是臂内不确定性）。
  机制明确：该形状在 M=8 从 `fp8_emu_gemv_stream_block_kernel<8,3,Half>` 换成
  `fp8_emu_gemm_block_wide2_kernel<64,8,32,1,2,Half>`，fp32 累加序改变。
  按 plan §1①/§6.2 的硬门禁，这是「已实现、不可发布」（§6.2 第二种情形）。

## 4. O4 的 parity 失败（本窗口最重要的负结果）

基线 = 同窗口 `o3_control` 的 greedy capture（8 条 prompt，各 64 token，`temperature=0, ignore_eos`）。

| prompt | prompt tokens | 逐 token 一致 | 首个分叉位置 | 重试后仍分叉 |
|---|---|---|---|---|
| p8_facts | 8 | ❌ | 12 | ✅ 是 |
| p64_code | 54 | ❌ | 17 | ✅ 是 |
| p512_analysis | 412 | ❌ | 28 | ✅ 是 |
| p512_zh | 465 | ✅ | — | — |
| p2k_log | 1678 | ❌ | 1 | ✅ 是 |
| p2k_math | 1643 | ✅ | — | — |
| p4k_repeat | 3254 | ❌ | 1 | ✅ 是 |
| p8_stream | 16 | ❌ | 1 | ✅ 是 |

解码文本也不同（`text_equal=false`）。重试复现 ⇒ 不是臂内不确定性，而是确定性的数值差异。
机制：`5120:1536`（生产里 64/256 次调用）在 M=8 由 stream kernel 改走 cfg35 tile kernel，
两者 fp32 累加/分块归约顺序不同；其余四个形状两个构建逐 bit 相同（`cand35_qt_off` parity 干净证明这一点）。

### 4b. 判别臂 `cand16_qt_on`（窗口 Q）：把原因钉死在「换路」上，cfg35 无罪

vllm-py 提出反证：kernel-dev 的微基准里 `cfg16 / cfg34 / cfg35` 对 `5120:1536 @ M=8` 都是
`bitwise_equal_vs_cfg16=True`，且 `cfg16 bitwise_equal_vs_prod=True`。于是加了一条判别臂：
**同构建 + `STREAM_MAX_M=8` + `DECODE_CFG=16`**（即用 pre-change 的 cfg16 tile 去接这个形状）。

| 事实 | 数据 |
|---|---|
| 判别臂 parity | **也失败**，且与 `cand35_qt_on` 的 token 流**逐字节相同**（8/8 条完全相同） |
| 与 stream 基线分叉位置 | 两条 tile 臂完全一致：12 / 17 / 28 / 1 / 1（p512_zh、p2k_math、p4k_repeat 干净） |
| 请求体一致性 | 每条 case `body_sha_equal=true`（同一 `completion_body` 构造，无 seed/template 差异） |
| 自一致性 | 所有分叉 case `self_consistent=true`（重试复现本臂自己的输出）⇒ 确定性差异 |
| 判别臂 kernel 名单 | `wide2=False stream=False`，20×`fp8_emu_gemm_block_kernel<8,64,1,2,Half,1>` ⇒ 门生效，tile 接手 |
| mprobe 该形状 | stream 90.96 µs / cfg16-tile 75.97 µs / cfg35-wide2 62.26 µs |

**判读**：数值差异属于**stream 路径 vs tile 路径**本身，与 cfg 选择无关——两个 tile 内核彼此逐字节一致、
只有 stream 内核不同。cfg35（O3）因此对这一效应**无罪**；O4 的机制被确证，同时被 parity 判死。
kernel-dev 的微基准之所以显示相等，是**合成输入不暴露该差异**（他的 a/w 是该形状的随机 fp8，够不到
真实激活下的分位差），这条也要写进结果文档，否则后人会拿他的日志推翻本结论。

**结论**：O4 关闭为「已实现、不可发布」。不放松 parity 门禁（plan §1①、仓库可复现纪律）。
让该形状走 tile 意味着换一条累加序，任何 tile 配置都会同样分叉（判别臂已证），所以本项不做。

## 5. c=4 / c=16（回归检查，不是收益证明）

| 并发 | 臂 | fwd t/s（warm 中位） | gen t/s | step ms | accept | 每轮 fwd t/s（第 1 轮冷） |
|---|---|---|---|---|---|---|
| 4 | o3_control | 899.8 | 37.3 | 359.9 | 8.00 | 414.1 888.7 899.8 917.3 |
| 4 | cand35_qt_off | 907.7 | 37.6 | 297.1 | 8.00 | 472.8 973.8 907.7 721.3 |
| 4 | cand35_qt_on | 896.6 | 37.1 | 304.3 | 8.00 | 458.0 896.6 844.1 907.3 |
| 16 | o3_control | 1050.2 | 41.0 | 1346.1 | 8.00 | 594.2 1050.2 1060.1 1013.9 |
| 16 | cand35_qt_off | 1029.7 | 40.2 | 1409.7 | 8.00 | 595.5 1044.4 1029.7 925.6 |
| 16 | cand35_qt_on | 1035.6 | 40.4 | 1402.2 | 8.00 | 593.2 1042.3 1035.6 1009.0 |

无回归、也无收益。**为什么这和 O1 的 c=16 结论不矛盾（读者最容易掉的坑）**：本 sweep 的
`fwd/step = 839.7`（c=16）说明它是**prefill 主导**的工作负载（512 token 入、128 token 出，
且 c 路并发共享 prefill 容量）。O3/O4 削的是 decode M=8 的 tile 拦截项，prefill 步骤根本不用那条路径，
所以这个 sweep 对 O3/O4 **只能当回归门禁**。反过来 O1 削的是 host 派发税，prefill 步骤同样每步 256 次调用，
所以在同一个 sweep 上能看到 +3.6%（见 [`s23-o6-w1-arms.md`](s23-o6-w1-arms.md)）。
两张表放在一起对比时必须带上这句限定。

另：每个并发的第 1 轮是冷 prefix cache，处于不同 regime（c=4 冷 414–473 vs 热 888–974 t/s），
因此只有热轮（2–4）的中位可作结论；上表两个数都列了。
