## 一、结论（先看这段）

**设计图说的"1.32 倍缺口里有可压缩的固定时间"不成立。这个内核的余量
已经基本用完，剩下的几条路每一条都被硬限制挡住，不是没写好。**

四个候选改动全部止损，没有一个进生产：

1. **把 QK 循环全展开**（设计图最看好的一刀，说能消掉 64 条索引指令）：
   指令确实消掉了，但寄存器从 109 涨到 128 并溢出，速度掉到 **0.34 倍**。
2. **把每轮的地址计算改成累加**：做到了，速度没变（0.99 倍）——
   这些指令本来就不在关键路径上。
3. **把 LDS 读改成"先发四条再用"**：全展开版寄存器爆（0.26 倍），
   收回展开度版本能跑但更慢（0.80 倍）。两个目标（少算索引 / 多发起读）
   在这个循环里**抢同一批寄存器，不能同时做到**。
4. **用 DPP 指令替代 softmax 的蝶形交换**：编译门就没过。
   gfx906 只有 `row_shl/shr/half_mirror/bcast`，**没有 `row_xor`**，
   而蝶形交换要的正是 xor。这是"指令不存在"，跟 S70 的 WMMA 一样。

第五条（Q 驻留 LDS，设计图里"最大的未测杠杆"）**没开工就已止损**：
重测 S63 那版得到 1260 ms（0.88 倍），与当年记录的 1260.3 ms 逐位吻合；
而且它承诺的收益上限被这一版实测修正到约 997 ms，够不到 925 ms 的门。

**唯一通过全部门的仍是 S70 的 P3（因果截断）**：内核在短上下文
最多 3.3 倍（4k）/ 1.79 倍（8k），131k 只有 2.9%；输出逐位相同、
占用零变化。但服务级 131k 门（≤270 s）没通过（285.9 s），
按纪律已回退，未采纳。

## 三、各工作包要点

### WP1 单缓冲矛盾归一（`.s71/wp1-singlebuf-diff.md`）

S63 说"单缓冲只慢 1.1%"，S70 说"单缓冲慢 2.25 倍"。两个都对，
因为它们是**两件不同的事**：

| 臂 | vgpr | spill | 占用 | 131k |
|---|---:|---:|---|---:|
| 基线 | 109 | 0 | 2 CTA/CU | 1113.9 ms |
| E1 单缓冲（S63 写法） | 109 | **0** | 2 CTA/CU | 1125.8 ms（1.0×） |
| P2 单缓冲（S70 写法） | 64（被钉死） | **36** | 4 CTA/CU | 2500.0 ms（0.45×） |

P2 为了让占用翻倍，把 `launch_bounds` 提到 4 CTA/CU，每 lane 只剩 64 个
vgpr，而这个内核自然要 109 个 → 溢出 36 个，每轮都多一轮 scratch 读写。
**"单缓冲贵"是假象，"把寄存器预算砍到 64"才是真死因。**

顺带修了一个 harness 事故：`with_serve_env.py` 用 `execvpe` 固定了整套
env，命令行前缀的 `VLLM_S70_SINGLE_BUF=1` 根本传不进去，第一轮"P2 臂"
实际跑的是双缓冲（数字与基线逐位相同）。给 harness 加 `--env k=v`
（进程内设）后才真正分开。

### WP2/WP3 四个候选（`.s71/wp2-wp4-verdict.md`）

| 臂 | 131k | 8k | vgpr/spill | 裁决 |
|---|---:|---:|---|---|
| L1a 全展开 | 3301.3 ms | 201.3 ms | 128 / 57 | ❌ |
| L1c 地址流水化 | 1119.9 ms | 71.2 ms | 110 / 0 | ❌ |
| L2b 全展开 | 4285.5 ms | 260.1 ms | 128 / 61 | ❌ |
| L2b 收回展开度 | 1393.2 ms | 88.4 ms | 107 / 0 | ❌ |
| L2a DPP | — | — | — | ❌ 指令不存在 |

**与设计图的偏差**：HA1（swizzle+地址 ~200 条可压 ≥60%）、HA2（读批次
加深，余量 16 vgpr）、HA3（DPP 替代 bpermute）三条全部被实测否证。
根因是同一件事——**这个内核的展开度被 109/128 vgpr 钉死**：`unroll 4`
已经是编译器在预算内的最优档；u8 = 1521.7 ms、u16 = 1562.3 ms 都更差。

### WP4 L3 未开工（`同上`）

施工图 §5 的出口 B 触发。S63 §1.1 的半 tile 形态虽然从未测过，但它
依赖的两个前提在本轮都被打掉：半 tile 化会同时压寄存器预算与 LDS 读带宽，
而这两项正是本轮所有失败臂撞的墙。

### WP5/WP6 合并臂与服务级（`.s71/wp5-wp6-verdict.md`）

P3 是唯一幸存者，所以"合并臂"就是 P3。内核五深度全部逐位同（131k vs
fp32 = 7.696e-06，与基线一致），静态主循环 364→288 条。服务级：
8k +0.2%、32k −2.5%、131k −2.9%，贪心 8/8 全同、TPOT 14.2 ms、AER 0。
**131k 没过 270 s 门，已回退**（symlink 指回 `.s58`，env 移除
`VLLM_S70_CAUSAL_EARLY`，服务重启回生产形态）。

> 门没过的直接原因是设计图的预算口径：P3 在 131k 的内核收益本来就只有
> 2.9%（空转 tile 在 131k 只占 5.3%），折算端到端 ≈1.8%，实测 2.9%。
> 270 s 那道门是按"全胜 −8.6%"设的。按纪律照样回退，不追认。

## 四、Prefill 各阶段速度（本轮实测，生产形态）

口径同 S68：`.s62/prefill_stages.py`（引擎逐 chunk 日志，`--enable-logging-iteration-details`），
单请求冷热混合（每长度新 seed 避开前缀缓存），`--gen 8`。
服务：生产 argv/env + 日志 flag（测毕已还原，AER 0）。
原始数据 `runs/prefill-lctx/s71/stages.json`。

### 4.1 总表

| ctx | TTFT (s) | prefill 步数 | 引擎 tok/s | 客户端 tok/s | S68 参照 TTFT |
|---:|---:|---:|---:|---:|---:|
| 1024 | 1.20 | 1 | 869.5 | 851.5 | 1.22 |
| 4096 | 4.64 | 2 | 885.9 | 883.3 | 4.67 |
| 8192 | 9.71 | 2 | 845.8 | 843.7 | 10.10 |
| 16384 | 23.31 | 3 | 706.4 | 703.0 | 23.37 |
| 32768 | 46.26 | 6 | 709.4 | 708.4 | 46.30 |
| 65536 | 107.42 | 10 | 610.8 | 610.1 | 109.73 |
| 131072 | 295.05 | 19 | 444.5 | 444.2 | 326.22 |

S68 的 131k 是 326 s，与 S63 的 293 s 差 11%；本轮 295 s 与 S63 一致，
说明 326 s 那次是窗口抖动，不是内核回退。

### 4.2 逐 chunk 分解（ms / tokens）

- **1024**：1178 / 1024（单步）
- **4096**：2540 / 2496 → 2083 / 1600
- **8192**：7124 / 6656 → 2563 / 1536（全程 2D 路径）
- **16384**：8262 / 7488 → 12644 / 7488 → 2289 / 1408（首 chunk 2D，其后 3D/HIP）
- **32768**：8372 → 12647 → 9735 → 10566 → 2909 → 1961
- **65536**：8300 → 12655 → 9741 → 10568 → 11667 → 12763 → 13861 →
  15027 → 9073 → 3644
- **131072**：8376 → 12687 → 9795 → 10602 → 11956 → 12814 → 14286 →
  14984 → 16079 → 17645 → 18354 → 19345 → 20463 → 21539 → 22752 →
  24054 → 24851 → 9495 → 4791

### 4.3 读法（三句话）

1. **首 chunk 恒定 ~8.3 s**（权重 GEMM + 集合通信 + 归一化，注意力尚浅），
   任何 ctx 都要付；1k/4k 这类短请求的 TTFT 基本就是这一项 + 一两步；
2. **深 chunk 逐级变贵**：131k 中间 chunk 达 24.9 s/chunk，注意力随 KV
   深度线性增长，与 S63/S68 同形；
3. **16k 门槛两侧无断崖**：16384 首 chunk（2D 路径）8262 ms 与 8192 首
   chunk 7124 ms 差 1.1 s（≈多算 832 token），门槛本身不是瓶颈。

vgpr 预算三面互相钉死**的结构性代价。

## 六、新增纪律（进 `.s71/` 台账，写给下一轮）

1. **`with_serve_env.py` 会吞掉命令行前缀的 env**——分臂开关一律走
   `ab_arm.py --env k=v`，并且每臂先做"拨 0/1 两次计时可区分"的验证；
2. **任何"改展开度/改占用率"的臂先过 readelf**：本内核自然需求 109 vgpr，
   128 上限下 spill 就是 0.3× 级别的事故；
3. **"删 barrier"之外再加一根探针："全展开"**——它同时测出寄存器预算
   与索引折叠的真实边界，成本 0.5 h；
4. **gfx906 的 DPP 只有 row_shl/shr/half_mirror/bcast**，`row_xor`/`row_share`/
   `row_newbroadcast` 汇编器直接拒绝；任何蝶形通信不能指望 DPP；
5. **服务级门要按臂的收益形状设**：P3 这类短上下文项不该用 131k 门裁决。
