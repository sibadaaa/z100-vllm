### 3. W8A8 INT8 `sdot4`：decode 3.9×，本项目最大的一笔单项收益

**内存与 vintage 纪律**：C 配置的达标配方 = 附加 **4 GiB swapfile（与宿主原有 4 GiB `/swap.img` 合计 8 GiB）** + **`vm.swappiness=200`** + **AOT 重载预热** + 4 桶 `PIECEWISE` ⇒ ready **230 s**、decode 中位 **49.65 ms**、`min MemAvailable` **2.35 GiB**；**不要用默认 51+2 桶**（ready 1645 s、余量 66 MB，只换 4.3% decode）。**"先空缓存预热再重启服务"保留，但它只保证启动快、不保证输出一致**（S14e 已否证 S11m 的"预热即可复现"）。容器**不得设 cgroup 内存上限**；监控 `Available KV cache memory`、`/proc/swaps`、`dmesg | grep global_oom`。

**回滚路径**：内核级 `VLLM_DCU_USE_INT8_SDOT4=0` 即回 Triton 路径（同一份树内，差距 3.82–3.91×）；扩展级 `_rocm_C.abi3.so` 可回到 `5d1e50e1…`（加 sdot4 前），而 `_C_stable_libtorch` **不要回退**（当前 `93bf7b4a…` 含 S7c 的 packed-silu 修复，回退会重现 NaN）；ACS 保持部署态关闭（12×`0x0000`，systemd `dcu-p2p-acs`）。**生产若要求 token 流可复现只能用 eager（慢 4.4%）；要用 graph 就得在 SLA 写明"同一请求跨重启/跨批组合输出不保证一致"。**

## 二、自研 HIP 算子：方法学与三族算子

### 自研 HIP 算子的开发历程与方法学

Z100（`gfx906`）上"能不能写算子、值不值得写"不靠文档与经验，靠**探针**：先把 ISA 能力钉死，
再按钉死的能力设计内核，最后用**机器码**证明内核真的走了那条指令。下面三族算子（INT8 `sdot4`、
FP8 仿真、BF16/FP16 dense GEMV）加 block-scaled 扩展，全部走同一条闭环。

#### 1. 方法学：从 ISA 探针到归档的五步闭环

| 步 | 做什么 | 为什么需要这一步 | 产物 / 出处 |
|---|---|---|---|
| ① ISA 探针 | `tools/dcu/isa_probe.sh` 给出**三列表**：汇编器接受性 / `__has_builtin` / codegen 实际发射，外加 gfx906 **基线断言** | 文档会过时、内建存在性 ≠ 硬件支持、"我觉得 clang 会发这条"是假象的唯一来源。三列表把"能写"降级成"能落码"，把"能落码"再降级成"真落码" | `tools/dcu/isa_probe.sh`；S11d 归档 §3.1–§3.3、§3.7；S11f 归档 §3.1 |

#### 2. 三族算子

##### 2.1 INT8 W8A8 `sdot4`（`v_dot4_i32_i8`）

**背景（为什么必须自研）**：ROCM 的 INT8 选核表是 `_POSSIBLE_INT8_KERNELS[ROCM] = [Aiter, Triton]`
——Aiter 要求 `compute_capability >= 90`（gfx906 = 9,0 出局），Triton 在 gfx906 上退化成 FMA 展开
（实测 2.2 TFLOPS）。**表里没有任何 `sdot4`**（S11d §3.5）。而 `v_dot4_i32_i8` 是 gfx906 上
**唯一有生产硬件先例**（前序工程 13–14 ms/token）的 INT8 指令。

**指令选择**：`__builtin_amdgcn_sdot4(a,b,c,/*clamp=*/false)`。
明确**不要** `v_dot4c_i32_i8`（gfx906 缺 dot8 特性，汇编器直接拒绝）、**不要** `v_dot4_u32_u8`
（W8A8 需要有符号，且树内 0 次使用无先例）。

**契约与关键设计选择**（`csrc/rocm/w8a8_sdot4.{cu,h}`）：

| 项 | 内容 | 为什么这么选 |
|---|---|---|
| 权重布局 | 保持 `[N,K]` int8 **原样**（不转置、不反量化） | 常驻显存与 checkpoint 相同；每行只读一次、访存与 M 无关。Triton 版会转成 `[K,N]` |
| decode（M ≤ 8） | **一 block 一输出列**，64 线程切 `K/4` 个 int32，`sdot4` int32 精确累加，LDS 树形归约 | 不能用 `tl.dot`：最小 tile M=16，M=1 时 15/16 是掩码行（16× 算力浪费，S11d §3.6(2) 量化依据） |
| prefill（M > 8） | `BM×BN` 寄存器 tile，`BK=32`（8 int32）双缓冲 global→寄存器→LDS；`cfg` 0 自动（M≤32→32×64，否则 64×64），1..4 显式（32×64/64×64/64×128/128×128） | 结构照抄前序已验证骨架；K 必须是 4 的倍数，否则上层回落 Triton |
| epilogue 顺序 | `(acc*x_s)*w_s` → cast 到 out dtype → `+bias` | 与 `triton_scaled_mm` **同序**，结果才可比（否则"逐位相同"这个强门禁不成立） |
| scale 契约 | `x_s` = `[M]`（动态 per-token）或 `[1]`（静态 per-tensor）；`w_s` = `[N]`（per-channel）或 `[1]`；1 元素 scale 内核里用 **stride 0** | S11e2 把它和 FP8 内核统一；`can_implement` 只要求 `input_symmetric`（内核无 azp 修正项，非对称量化必须回落） |

**3.9× 的来历（三个独立证据链，别只记一个数字）**：

| 口径 | `=1`（sdot4） | `=0`（Triton） | 倍数 | 出处 |
|---|---|---|---|---|
| 逐 shape ABBA（kernel only，63/63 组） | 最差 ×1.022、中位 ×2.16、最好 ×22.61（N=1024 K=5120 M=1，decode 的 k/v_proj） | 1× | — | S11e §3.5 |
| 逐 shape ABBA（`full`，含 `scaled_int8_quant`） | 最差 ×1.148 | 1× | — | S11e §3.5 |
| 27B W8A8 TP=2 端到端（同命令 A/B） | **84.07 / 82.74 ms/token** | 329.05 / 320.30 | **3.91× / 3.87×** | S11k §3.5.2 |
| kernel 级占比（同卡同 harness，32 步） | GPU busy **82.5 ms/step**；304 次/step 的 int8 GEMV **52.68 ms** | 320.5 ms/step；290.85 ms | **3.88× / 5.52×** | S11k §3.6.1/§3.6.3 |
| 重验收（S11l，同会话 A/B，S9 协议） | decode **84.00 ms/token**、TTFT 2.234 ms/prefill-tok、conc8 33.12 tok/s | 321.09、2.996、17.03 | **3.82× / 1.32× / 1.94×** | S11l §3.4 |

峰值算力 22.2 TFLOPS（M=512，N=17408 K=5120）vs Triton 18.0；且 **63/63 组无 shape 变慢**
（`no shape regresses`，两次独立运行偏差中位 0.2%）。对照生产基线（TP=4、eager、bf16、122.47 ms/token）
为 **快 1.458×**，但存在 TP/图模式/dtype 三处口径差，保守表述是"**已越过生产基线**"（S11l §3.4）。

**`custom_op` + Dynamo 的教训（S11k，本族最贵的一课）**：

| 项 | 内容 |
|---|---|
| 现象 | 内核/接入/数值/逐 shape 性能**全过**，但 `VLLM_DCU_USE_INT8_SDOT4=1` 时 27B 在 `torch.compile` 阶段抛 `ConstraintViolationError`（`L['positions'].size()[1]` 被标成 dynamic 却特化成 2048），150 s 内退出；`=0` 正常 |
| 归因（三次对照） | ① 去掉 Python 的 M 分支 → **仍崩**（负结果）；② 同 kernel 类把自定义 op 换成 `_triton_fallback` → **编译 173 s 通过并进入 capture** ⇒ 触发者 = **自定义 op 本体** |
| 根因 | Dynamo 在**裸 `TORCH_LIBRARY` op 调用点**给符号 token 维加 `Eq(dim, hint)` 守卫，`set_replacement(..., range_refined_to_singleton)` 把它变成常量；vLLM 标记该维 dynamic ⇒ `produce_guards_verbose()` 抛错。**不是 Meta 缺失**（`s11k_meta_probe.py` 证明 C++ `Meta` 有效、FakeTensor 形状正确），也**不是分支选错**（实验 B） |
| 修法 | **`torch.library.custom_op` + `register_fake`**（声明输出 `(x_q.size(0), w.size(0))`），并把 **GEMV/GEMM 的 M 分支搬进 opaque body**。`@torch.compiler.disable` 可用但引入 1 次 graph break；`splitting_ops` **结构性无效**——崩在 Dynamo 出图后的 `build_guards`，早于 vLLM/Inductor 切图；给已注册的 C++ op 补 `register_fake` 被 torch 直接拒绝（已有 `DispatchKey::Meta` 实现） |
| 验证 | `torch.equal` vs 裸内核 **18/18**；vs `triton_scaled_mm` **126/126** 逐位相同；`dynamic=True` 下 M=2048→M=1 复用同一张图、无 graph break；副作用是 `torch.compile` **更快**（88.24 s vs `=0` 的 159 s）、KV 显存相同（11.53 GiB） |
| 遗留 | 逐 token 文本一致未达成；S11l 的隔离实验给出定论：把 opaque op 的 body 换成与基线**完全相同**的 `triton_scaled_mm` 后 **8/8 prompt 照样翻转**、5 个早期分叉点与 `opaque(sdot4)` **完全重合、方向一致** ⇒ **H_graph 成立、H_kernel 否定**（"换内核导致文本变"不成立，"改变编译图/编译产物导致文本变"成立）；16 个分叉点**全部落在 ≤0.53 nat 的贴边决策**上。量化敏感度实验解释了放大机制：1 ULP 输入扰动 → int8 code 变 20–120 个（5120 里）→ 输出变化 2.2–3.3e-3，比不量化的 fp16 路径大 2–5×，且是离散跳变 |
| 默认值 | **保持 OFF**（S11k 把 S11e 的"默认开"有意推翻：仓库里不允许存在"取默认值就起不来"或"默认改变服务输出"的开关）；生产显式 `VLLM_DCU_USE_INT8_SDOT4=1`。S11e2 并入族总开关 `VLLM_DCU_USE_GFX906_EMU`，显式单项值优先 |

##### 2.2 FP8 W8A8 仿真（`ds_read_u16` LUT 加宽 + `v_dot2_f32_f16`）

**背景**：gfx906 **没有任何 fp8 指令**（`v_cvt_f32_fp8`/`v_cvt_pk_fp8_f32`/`v_cvt_pk_f32_fp8`/`v_cvt_f32_bf8`
全部 `not supported on this GPU`）、没有 fp8 MFMA、`torch._scaled_mm` 的 FP8 路径不支持 ⇒ vLLM 里
**所有** FP8 选核在 gfx906 上拒绝（`ROCmFP8ScaledMMLinearKernel`："wvSplitKQ is not built on gfx906 (no MFMA)"；
torch 系列："requires a platform with torch FP8 scaled-MM support"）；唯一能跑的 block-scaled 是纯 Triton
的标量 `v_fmac_f32` 模拟，实测 **≈36× 慢**（S8b：4096³ 上 304.2 ms vs fp16 8.4 ms，机器码
`v_fmac_f32_e32` **8160** 条、`v_mfma`/`v_dot2_f32_f16`/`v_dot4_i32`/`v_pk_fma_f16`/`v_cvt_f32_fp8` **全 0**）。
硬约束：27B FP8 ≈ 27 GiB，fp16 副本 54 GiB **装不下** ⇒ 必须**边读边转**，不允许物化 fp16 权重副本。

**为什么不能走位运算（关键设计选择）**：e4m3 的次正规（`|x| < 2^-6 ≈ 0.0156`，在 per-channel scaled
权重里非常常见）与 fp16 的次正规指数不同，**无法用"移位 + 加偏置"一步映射**，位运算路线必须再补逐 lane
修正；而 **256 项 fp16 LUT 对 e4m3fn 与 e5m2 的全部有限码都是无损的**（e4m3 峰值 448、3 位尾数；e5m2
峰值 57344 < 65504、2 位尾数，其 2^-16 次正规正好落到 fp16 次正规），一次 `ds_read_u16` 就得到精确值
——注意 `ds_read_b16` 在 gfx906 上**不存在**。因此默认路线固定为 LUT（`VLLM_DCU_FP8_CVT=lut`），
位运算只留作 A/B。LUT 由宿主侧按 dtype 构建（`functools.lru_cache` + 每设备缓存，512 B），
由 `test_lut_is_lossless_for_every_code` 对全部 256 码逐条断言（含 inf/NaN 与符号）。

**契约与实现**：

| 项 | 内容 |
|---|---|
| 布局 | `a`/`w` 为 8 位 fp8；`w` 是 `[N,K]` K 连续（checkpoint 布局，FP8 选核传进来的是它的 `[K,N]` 视图，内核用**零拷贝** `.t()` 读）；`a_s` = `[M]`（per-token）或 `[1]`；`w_s` = `[N]`（per-channel）或 `[1]`；epilogue `(acc*a_s)*w_s` → cast → bias |
| GEMV（M ≤ 8） | 一 block 一输出列，`nt=64` 线程跨 `K/4` dword 连续读，LDS 树归约；**M ≥ 2 时把 A 的加宽提到循环外**（多一个极小的 widen kernel + `M×K×2` 字节 scratch）——因为每个 block 都要重读同一份 A，不提出去的话 M=8 时 LUT 访存是 dot2 的 **9 倍** |
| GEMM（M > 8） | `BM×BN` 寄存器 tile + `BK=32` 双缓冲 LDS，结构照搬 `w8a8_sdot4.cu`（同项目同硬件已验证），只是 LDS tile 单元从 int32 字换成 **fp16 对**（1 dword = 2 lane = 1 条 dot2），staging 时用 LUT 把 fp8 加宽成 fp16 对；cfg 0 自动（M≤32→32×64，否则 64×64） |
| MAC | `v_dot2_f32_f16`（2 fp16 MAC/指令 + **fp32 累加**），正好是 FP8 想要的累加契约 |

##### 2.3 BF16/FP16 dense decode GEMV：f32 路线 vs f16 重定标路线

**背景**：gfx906 没有任何 bf16 运算指令（转换/点积都不存在），且 decode 形状的**未量化**线性层两条快路
都不可用——`ops.LLMM1`（skinny GEMM）因 MFMA 被排除出 gfx906 构建，`n <= 16` 的 Triton matmul 带
`not on_gfx9()`，只能落到 rocBLAS：实测 `[1,5120] @ [17408,5120]` bf16 GEMV 仅 **235 GB/s**（HBM 的 24%），
小 N 更差（N=512：**24 GB/s**）。

**契约**：一个 block 一个输出列 + LDS 树归约（复用 sdot4 的阻塞方式）；权重按 `[N,K]` 原样读，
不转置不拷贝；`K` 必须是 2 的倍数、`M ∈ [1,8]`、`nthreads` 为 2 的幂且 ≤ 512。
`route` 三档：**0 = auto**（fp16 → dot2；bf16 → fp32）、**1 = fp32**、**2 = dot2**（bf16 时需 `range_safe`）。
两条路线的取舍就是本族最核心的设计选择：

| 路线 | 做法 | 契约 / 代价 | 采纳 |
|---|---|---|---|
| **f32（bf16 默认）** | 每 lane `v_lshlrev_b32 16` 精确展宽 + `v_fma_f32`/`v_fmac_f32` | 对**全部** bf16 取值精确（含次正规/零/inf），是"bf16 权重 + fp32 累加"的硬件 MMA 数值口径 | ✅ 默认 |
| **f16 重定标（bf16 可选）** | `(s - 112<<7) << 3` 得到 fp16 位型（前提 e8 ∈ [113,143]），再走 dot2 | 快，但 fp16 指数窗口比 bf16 **窄约 30 个 binade**：`|x| < 2^-14` 冲零、`≥ 65536` 饱和；**零值的 e8=0 会静默回绕（实测零 lane → 2.0）**，σ~1e-3 的权重分布会被冲掉约 **6%** 的信号（阈值是绝对的、不是相对的）。契约要求**两个操作数的每个 lane** 都在窗口内 | ⚠️ 仅 A/B；Python 侧 `range_safe=False` 默认不开，须先做逐行范围检查 |
| **fp16 输入** | 直接走 dot2（无转换，精确） | — | ✅ 默认（route 0） |

**实测（K=5120，对照 rocBLAS；误差 = 输出 dtype 的 ulp）**：

| 形状 | fp16 M=1 | bf16 M=1 | 备注 |
|---|---|---|---|
| N=17408 | 2.74×（592.6 GB/s，0.35 ulp） | 2.61×（624.7 GB/s） | rocBLAS 仅 215–235 GB/s |
| N=8192 | 3.95×（580.8 GB/s，0.39 ulp） | 2.50×（553.5 GB/s） | |
| N=5120 | 2.11× | 2.01× | |
| N=512 | 1.49× | **5.71×** | rocBLAS bf16 小 N 极差 |
| N=48 | 1.29× | **2.46×** | |
| bf16 M=4 N=512 | — | 2.14× | 唯一启用的 M>1 形状 |
| bf16 M=8 N=17408 | — | 0.51× | **未启用**（内核落后 rocBLAS） |

全部误差 ≤ **0.39 ulp**。**机器码门禁**（76 kernel）：`v_dot2_f32_f16` **18,666**、`ds_read_u16` **1,092**、
`v_fma_f32` 24、`v_mfma` **0**、`v_cvt_f32_bf16`/`v_dot2_f32_bf16`/`v_cvt_f32_fp8` **0**。

作基线，收益是 **emu/triton = 2.28–8.54×**（bf16 N=17408：0.271 ms @657 GB/s vs triton 0.908 ms @196 GB/s）。

##### 2.4 block-scaled（128×128）FP8 扩展（2026-10-11）

**动机**：端到端选用的 ModelScope `Qwen/Qwen3.8-27B-FP8` 就是 **block-scaled** 的
（`activation_scheme: dynamic`、`fmt: e4m3`、`weight_block_size: [128,128]`，**407 个 scale 全部是
`weight_scale_inv`**（`[cdiv(N,128), cdiv(K,128)]`），没有任何 per-tensor `weight_scale`）。per-tensor
内核按设计拒绝它 ⇒ 回落到 `TritonFp8BlockScaledMMKernel`（标量 `v_fmac_f32` 模拟）：模型能起、
输出连贯，但 **TTFT 4969 ms / decode 1984.8 ms/token（0.50 tok/s）**，服务不可用。

**契约与关键洞见**：

```
out[m, n] = Σ_kb ( Σ_{k ∈ kb} a[m,k] · w[n,k] ) · a_s[m, kb] · w_s[n // block_n, kb]
```

关键洞见是**标量乘法可以分配到线程局部部分和上再归约**：

```
Σ_t Σ_kb p[t,kb]·s[kb]  ==  Σ_kb s[kb]·Σ_t p[t,kb]
```

⇒ 只需要在**当前 K 块的累加器**上乘 scale，就**保住了原有的"一次归约树 / 一个寄存器 tile"结构**——
不必先归约再乘 scale，也不必为每个 K 块开一遍归约。

| 位置 | 关键实现 |
|---|---|
| GEMV `fp8_emu_gemv_block_kernel` | **每线程独占整个 K 块**（`kb = t, t+nt, …`）而不是跨线程切 dword：一个 block 只碰一个 cache line（block_k 字节、每元素 1 字节），**scale 每 128 元素只取一次**（而非每 dword 一次）；`acc[m] += loc[m] * (a_s[m·nkb+kb]·wsv)` |
| GEMM `fp8_emu_gemm_block_kernel` | 用两个 tile：`blk[TM][TN]`（当前 K 窗口）+ `acc[TM][TN]`（已完成块）；**在 128-K 边界折叠**——`fp8_gemm_fold_block_scale` 做 `acc[i][j] += blk[i][j]*sa*w_s[(col/block_n)*nkb+kb]; blk[i][j]=0`，折叠点在 `((c+1) % cpb) == 0`（`cpb = block_k / 32`），epilogue 只做 cast + bias |
| **W 行 stride（padding）支持** | block 路径会走 `process_fp8_weight_block_strategy` → `_maybe_pad_fp8_weight`（`VLLM_ROCM_FP8_PADDING` 默认开、K=5120 满足 `stride*1 % 512 == 0`），权重变成 `stride(0) = K + 256` 的**非连续**视图。内核按 `w_stride = w.stride(0)` 索引行，要求 `stride(1) == 1` 且 `w_stride % 4 == 0`；单测 `test_block_accepts_padded_weight_row_stride` 断言**填充视图与连续权重逐位一致** |
| 权重方向自适应 | `apply_block_scaled_mm` 按 `B.shape[1] == K` 判定 `[N,K]`（checkpoint 布局）/`[K,N]`，两种都**零拷贝**；`stride(1) != 1` 时**明确报错**而不是偷偷 copy |

**结果**：

| 项 | 结果 | 出处 |
|---|---|---|
| 单测 | **41 passed**（新增 11 项 block：GEMV/GEMM vs fp32 反量化参考、奇数形状（N=100 < block_n、M < BM）、填充 stride 逐位一致、bias、门控/`can_implement` 矩阵） | S11f §9.3 |
| ISA / 选核 | `ISA_PROBE_STRICT=1` **53/53 MATCH、退出 0**；开关 ON → `Gfx906Fp8BlockScaledMMLinearKernel`，OFF → `TritonFp8BlockScaledMMKernel`（原行为） | S11f §9.3 |

### 2. block-scaled（128×128）FP8 内核

**动机**：ModelScope `Qwen/Qwen3.8-27B-FP8` 是 block-scaled（`weight_block_size:[128,128]`、
407 个 `weight_scale_inv`、无 per-tensor scale），原内核 `can_implement` 按设计拒绝它 ⇒
只能回落 `TritonFp8BlockScaledMMKernel`（标量模拟）。

**契约与关键洞见**：

```
out[m, n] = Σ_kb ( Σ_{k∈kb} a[m,k]·w[n,k] ) · a_s[m, kb] · w_s[n // 128, kb]
```

标量乘法可分配到**线程局部部分和**再归约（`Σ_t Σ_kb p·s = Σ_kb s·Σ_t p`），因此只在
*当前 K 块*的累加器上乘 scale，就保住了原有的"一次归约树 / 一个寄存器 tile"结构：

- `fp8_emu_gemv_block_kernel`：每线程独占整个 K 块（`kb = t, t+nt, …`），一个 cache line/块，scale 每 128 元素只取一次；
- `fp8_emu_gemm_block_kernel`：在 128-K 边界把 `blk` 折叠进 `acc`（`fp8_gemm_fold_block_scale`）；
- **W 行 stride 必须支持**：block 路径会走 `process_fp8_weight_block_strategy` →
  `_maybe_pad_fp8_weight`（`VLLM_ROCM_FP8_PADDING` 默认开），权重变成 `stride(0)=K+256` 的非连续视图；
- 新算子 `fp8_emu_gemv_block` / `fp8_emu_gemm_block`(+Meta) + `custom_op("vllm::fp8_emu_mm_block")`
  （GEMV/GEMM 分支留在 opaque body 内，避免 Dynamo 给 token 维加 guard——S11k 教训）+
  `Gfx906Fp8BlockScaledMMLinearKernel` 插在 ROCm block 选核表首位。

**门禁**：单测 **41 passed**（新增 11 项：vs fp32 反量化参考、奇数形状 N=100<block_n、填充 stride 逐位一致、bias、门控矩阵）｜ISA **53/53**｜选核 ON→新内核、OFF→Triton｜机器码：106 kernel、`v_dot2_f32_f16` **37254**、`ds_read_u16` **2184**、`v_mfma`/`v_cvt_f32_fp8` 全 0；`v_fmac_f32` 1258 条**全部是新增 block 内核里的 scale 折叠 FMA**（静态 1:16–1:32、动态约 1:64），per-tensor 内核仍为 0。产物 md5 **`fbfd45edb00713594793151a3e9ca76a`**。

### 3. 端到端上线（官方 Qwen3.8-27B-FP8，TP=4）

模型 82 文件 / **30.89 GB 与 API 清单逐项尺寸一致**；架构 `Qwen3_5ForConditionalGeneration`
（与生产 INT8 版同架构，64 层 / hidden 5120 / 原生 262144 上下文）。

| 臂 | 内核 | TTFT | decode |
|---|---|---|---|
| 对照 | `TritonFp8BlockScaledMMKernel` | 4969 ms | **1984.8 ms/token** |
| 本步 | `Gfx906Fp8BlockScaledMMLinearKernel` | 600 ms | **123.0 ms/token**（8.1 tok/s） |

⇒ **16.1×**；同请求口径 85.0 s → 5.38 s；与生产 **INT8** eager/TP=4 的 126.83 ms/token（S14）
**同档**，说明剩余成本在 eager 模式与 GDN/attention，不在 FP8 GEMM。

**质量**（4 提示词 × 32 greedy token，两臂对比）：2/4 逐位一致；另 2 条只在第 29/31 个 token
分叉，`max|Δlogprob| ≤ 0.32 nat`，与该机型自身噪声底（S14b：0.1–0.6 nat）同量级；4 条输出全部连贯。

**上线形态**：作为生产槽位 drop-in 起在 **:8000**（`api-gateway` 的 upstream），服务名沿用
`qwen3.8-27b`，配方同 `serve_27b_tp4.sh`（TP=4 / util 0.85 / maxlen 262144 / MBT 2048 /
prefix caching / mamba align / eager）；KV 18.55 GiB、1,192,990 tokens、262K 可并发 4.55×。
实测 `:8000` 与网关 `:8080` 两条链路都通（12×12→**144**、7²→**49**）。

### 4. 卡间通信 P2P：验证、尝试启用、结论

**三层结论**：

| 层 | 状态 | 证据 |
|---|---|---|
| 设备级 P2P DMA | ✅ **已启用且有效** | 12 桥 ACS=`0x0000`；`can_device_access_peer` **12/12 YES**；跨卡 `copy_` **28.30–28.39 GB/s**（本卡基线 279–407 GB/s；ACS 开时约 6.95 GB/s） |
| 集合通信（RCCL，TP 实际走的路） | ❌ **无法启用** | **10 组开关 + `iommu=pt` 重启，全部 `via P2P=0`** |
| vLLM custom all-reduce | ❌ 同一根因阻断 | `allocate_shared_buffer_and_handle` → `hipErrorOutOfMemory` |

**开关矩阵**（4 rank all-reduce，`via P2P/SHM/NET` = 实际建立的连接数）：

| 环境变量 | via P2P | via SHM | via NET | 1 MiB 延迟 |
|---|---|---|---|---|
| 默认 | 0 | 56 | 0 | 2247 µs (0.70 GB/s) |
| `NCCL_P2P_DISABLE=1` | 0 | 28 | 0 | 2225 µs |
| `NCCL_P2P_USE_CUDA_MEMCPY=1` | 0 | 56 | 0 | 2255 µs |
| `NCCL_SHM_DISABLE=1` | 0 | 0 | 56 | **16371 µs（慢 7.3×）** |
| `NCCL_P2P_DIRECT_DISABLE=1` | 0 | 56 | 0 | 2231 µs |
| `NCCL_IGNORE_DISABLED_P2P=1` | 0 | 56 | 0 | 2257 µs |
| `NCCL_P2P_LEVEL=SYS` + USE_CUDA_MEMCPY | 0 | 56 | 0 | 2261 µs |
| （含上述两两组合，共 10 组） | 0 | — | — | — |

**根因链**（全部实测）：RCCL 的 `transport/p2p.cc` → `ncclP2pAllocateShareableBuffer` →
动态链接 `hipExtMallocWithFlags@HIP`（`nm -D` 实证）；ctypes 直接探测该 API：

```
Default(0x0)              rc=0  no error
Finegrained(0x1)          rc=2  out of memory
hipMallocSignalMemory(0x2) rc=1  invalid argument
Uncached(0x3)             rc=2  out of memory   ← RCCL 直接 P2P / custom-AR 需要的那个
Contiguous(0x4)           rc=1  invalid argument
UncachedXdp(0x1000)       rc=2  out of memory
hipIpcGetMemHandle rc=0（IPC 可用）        hipHostMalloc rc=0
```
> 枚举值取自本机 `/opt/dtk/include/hip/hip_runtime_api.h`。**4 KB 的 `Uncached` 分配在显存空闲的卡上同样
> 返回 `out of memory`**，而 `Default` 成功、IPC 句柄可建 ⇒ 这是**该平台/驱动缺少 uncached 内存池**的能力问题，
> 不是真的显存不足。（修正记录：本节初版把 `0x02` 标成 Uncached，实际 0x02 是 `hipMallocSignalMemory`；
> 用正确枚举重测后错误码为 `out of memory`，与归档 S13 的观测一致——**结论不变，错误码与推理已改正**。）

**`iommu=pt` 实验（需要宿主重启）**：RCCL 每次启动警告 `Missing "iommu=pt"`，且原内核命令行确无该参数。
改 GRUB 加 `iommu=pt` 后重启（内核仍钉在 5.15.0-191，因其是唯一装有 hydcu 驱动的内核；
**注意 5.15.0-194 已安装但没有 DCU 驱动模块**）：`iommu: Default domain type: Passthrough`
生效，但 **`Uncached`(0x3) 仍 `out of memory`、RCCL 仍 `via P2P=0`**，延迟在噪声内。
⇒ 该分配不可用是 **hydcu 驱动 / gfx906 缺少 uncached 内存池** 的能力限制（表现为 `out of memory`，与显存余量无关），**与 IOMMU 映射模式无关**；
要推进只能向厂商提需求（`hipIpcGetMemHandle` 可用说明理论上存在基于 IPC 的路径，但 RCCL 不走）。

### 8. 条目与状态统计

- **条目总数：92 条**（按上表逐行计）。分节：§1 平台/生态 13 条、§2 编译与图模式 18 条、§3 内存 10 条、§4 数值与质量 10 条、§5 内核能力边界 15 条、§6 运维/构建/依赖 26 条。

- **🔶 有绕法 / 降级方案：36 条** —— 含"明确未做 + 原因"（小 N 大 M 未做 split-K、UE8M0/MXFP8/非 128 block 未测、静态输入 scale 未端到端、MTP/GDN 未扩展 bf16、非对称激活量化未实现、INT8 MoE/GGUF 未做、block GEMM tile 未重 tune、S14g 的 H2/H3/H4、G3/G4/G5 三格电池等）与"可用但代价明确"（swap 桥接、降级到 eager、回落 rocBLAS / Triton、`AMDGCN_USE_BUFFER_OPS=0`、capture 桶限制等）。
- **✅ 已修 / 已裁定口径：34 条** —— 其中 **5 条是口径更正**：S12→S14 的 cgroup 上限误判、S14b 对 S14 噪声底与"graph 改变输出质量"的更正、S11m 对 S11l"开关决定 token 串"的更正、S14e 对 S11m"预热后重启可复现"的更正、S11f 对自身 `v_fmac_f32` 计数/数值门限/探针基线的更正。
- **跨档说明**：同一条目可能在执行过程中跨档迁移（最典型的是 `--enforce-eager`：⛔ 禁令 → 根因定位 → csrc 根修 → ✅ 禁令事实基础移除），本表按**最终状态**归一次、不重复计数。

```bash
# ---- 容器环境（所有 GPU 命令都先做这三步）----

  tests/kernels/quantization/test_gfx906_fp8_emu.py \
  tests/kernels/test_gfx906_bf16_gemv.py \
  tests/kernels/quantization/test_gfx906_int8_sdot4.py

python tools/dcu/s11f_fp8_emu_probe.py --mode check --max-m 512 --rel-tol 1e-5 --abs-tol 1e-3

# ---- 门禁 4：机器码（拆 .hip_fatbin + 按 kernel 归因）----
SO=/mnt/game/port/gfx906-vllm-211/vllm/_rocm_C.abi3.so
mkdir -p /tmp/mc/bun && cd /tmp/mc && llvm-objcopy --dump-section .hip_fatbin=fat.bin $SO null.so
python3 -c 'd=open("fat.bin","rb").read();p=b"__CLANG_OFFLOAD_BUNDLE__";o=[];i=d.find(p)
while i!=-1:o.append(i);i=d.find(p,i+1)
[open(f"bun/b{n:02d}.bin","wb").write(d[s:(o[n+1] if n+1<len(o) else len(d))]) for n,s in enumerate(o)]'
cd bun && for f in b*.bin; do clang-offload-bundler -type=o -unbundle \
  -targets=hipv4-amdgcn-amd-amdhsa--gfx906 -input=$f -output=${f%.bin}.o; done
for o in *.o; do llvm-objdump -d $o; done > all.dis
grep -c v_dot2_f32_f16 all.dis     # 期望 >0；v_mfma / v_cvt_f32_fp8 期望 0

# ---- 构建（改 csrc 后必做；注意先同步硬链接）----
cp -f csrc/rocm/*.cu csrc/rocm/*.h /mnt/game/port/gfx906-vllm-211/csrc/rocm/   # 见下方"硬链接坑"
docker exec -d z100-vllm bash /mnt/game/port/build-211.sh _rocm_C
docker exec z100-vllm bash /mnt/game/port/install-211.sh _rocm_C

# ---- 端到端 ----
docker exec -d z100-vllm bash /mnt/game/port/serve_fp8_8000.sh     # :8000，服务名 qwen3.8-27b
curl -sS http://127.0.0.1:8000/v1/models

# ---- P2P ----
sudo python3 tools/dcu/dcu_p2p_acs.py show                        # 期望 12 桥 0x0000
docker exec z100-vllm bash -lc 'PYTHONPATH=/src HIP_VISIBLE_DEVICES=0,1,2,3 python tools/dcu/p2p_verify.py'
```
