S36 B1 调查记录:MTP draft 计数异常(draft_tokens/drafts≈1.02、pos1 验收 1.7%)
================================================================
日期:2026-10-29。只读调查,未改任何 A 轨触点。

[结论] 成因是 S24 dynamic-k(dynk)对 MTP k=2 的阈值错配,**不是 step3p5 proposer
的 parallel/顺序起草分支问题**。第二个 draft token 由 proposer 正常产出,但调度器
在 ctx > dynk_hi(65536)时把 verify 截到 k'=1,导致每请求每步只验证 1 个 draft。

[证据链]
1. 指标语义:vllm/v1/spec_decode/metrics.py SpecDecodingStats.observe_draft
   以「每请求每步」为粒度累计:num_drafts += 1,num_draft_tokens += 该请求本步
   被调度的 draft 数。draft_tokens/drafts ≈ 1.02 = 每请求每步平均只带 1 个 draft。
2. 截断点:vllm/v1/core/sched/scheduler.py:805-820 —— 纯 verify 步在 dynk_enabled
   且 k_dyn+1 < num_new_tokens 时把调度截到 k'+1 行;
   k_dyn 由 _dynk_spec_len(2705-2734)给出:
     ctx <= VLLM_S24_DYNK_LO(16384)         → 全 k
     ctx >  LO,EMA < 5.0(weak)             → dynk_mid_k = 3(k=2 时 3+1≥3 不截)
     ctx >  VLLM_S24_DYNK_HI(65536),weak   → dynk_min_k = 1(截!)
3. 错配根源:scheduler.py:302-303 写明 "Acceptance length that still counts as
   'drafting well' (of k=7)" —— dynk_ema_good=5.0 是按 S24 时代 k=7 草稿塔标定的;
   MTP k=2 的 accepted EMA 上限就是 2.0,**永远 < 5.0 ⇒ ctx>65536 时必然 k'=1**。
   生产 env(VLLM_S24_DYNK_LO=16384 / HI=65536 / EMA=0.1)随 vllm_env.sh 注入 MTP 臂。
4. 对账:S34-WP6 dynkoff 臂日志(.s34/serve-s34-wp6-dynkoff.log,10-27):
   Mean acceptance length 2.56-2.69,Per-position acceptance 0.838 / 0.717-0.846
   —— 同样的 MTP k=2、只关 dynk,pos1 验收立刻回到 72-85%。
   在役 MTP 臂的 1.02/1.7% ≈ 「ctx≤65536 的 ~2% 步数」占比,完全吻合。

[影响]
- 长 ctx(>64k,生产主力口径)的 MTP 实际按 k=1 在跑:S34 长上下文 MTP 对比里
  「MTP 臂」的 verify 宽度被悄悄砍半,收益口径失真(短 ctx 7.5k 探针不受影响)。
- B2 若直接按现 env 重启 MTP,长 ctx 依旧 k'=1。

[修复方向(供 B2 裁决,未实施)]
  a) 零代码:MTP 臂 env 置 VLLM_S24_DYNK_LO=0(dynk 整体关闭;dynkoff 臂已验证该口径)。
  b) 小改:scheduler 把 dynk_ema_good 随 num_spec_tokens 缩放(如 0.7×k,k=2→1.4),
     dynk_mid_k 取 min(dynk_mid_k, k);保留长 ctx 降档机制。
  c) 明确不推荐:动 step3p5 起草分支(与成因无关)。
建议:b 为主、a 为 MTP 重启的先导 A/B(一次重启即可对比)。
