S36 W2' F 分解记录(2026-10-29)
================================================================
方法:零代码,生产 .so(md5 86470c5d,in-service),M=1 走 m1 核。
微测口径:HIP graph replay + 4 组旋转权重(同 /tmp/fill_model.py);
"packed" = 单 graph 内连发 kpk 个 kernel(生产 piecewise cudagraph 同构)。
工具:fill_model / s36_decomp.py / s36_packed.py / s36_packed2.py / rocprofv2(--kernel-trace,
注意:本机 rocprofv2 不接受 "--" 分隔符,且 one_launch.py import fill_model 会连带跑五形状 bench)。

[1] 基线(event,单 kernel/graph,rotating)
  o 27.47-27.81 | qkv 27.55-29.0 | gateup 76.6-77.2 (581 GB/s) | down 46.7-48.4 | syn4352 44.4
  o M=4 42.3, gateup M=4 146.9(cfg 0/35 无差);torch.equal 基线语料 120/120 存 .s36/parity/

[2] K 扫描(N=1280,grid=320):T(s) = 10.96 + 2.60·s(全6点)/ 12.00 + 1.86·s(s≥3)
  → 截距 F≈11-12us 与 slice 数无关 = per-kernel 固定项;K=4096 点反复离群(两次扫描均+30%)。
[3] N 扫描(K=1024,1 slice):320blk 12.5us → 4352blk 53.7us(us/block 0.039→0.012)
  → 固定项随 grid 增长 = 波次铺开/尾延迟,非纯常数。
[4] rows/nt A/B(零代码,H2 检验):o rows8/nt512(grid 减半)= 26.8 vs 27.3(-0.5us);
  qkv 29.1 vs 27.6(恶化);gateup 78.4 vs 76.7(恶化,568 GB/s 逼近 570 门)→ **H2 拒绝**。
[5] packed(kpk=32,o):1/graph 27.75 → 32/graph 20.76us/kernel;
  边际(2..32)≈20.6us 恒定;graph↔graph 间隙 ≈7us(生产 piecewise graph 不支付)。
  torch profiler(32-packed,320 实例):kernel dur p50=20.80us ≈ event 20.76
  → **in-graph 间隙≈0,o 的 20.8us 全在核内**。
[6] packed K 扫描(kpk=32,N=1280):6.36/8.95/11.41/(18.68 离群)/16.34/20.96
  → 拟合 T≈3.5+2.9·s(受离群污染);bytes 下限 1.76us/slice(745GB/s),
  实际边际 2.4-2.9us/slice → 每 slice 超额 0.7-1.1us。
[7] m1 vs wholea A/B(qkv,in-graph):22.59 vs 21.68(-0.9us only)
  → per-slice A-restage+barrier 链合计 ≈0.9us(5 slice),**不是主要超额**;
  剩余超额与 grid 并行度相关:同 bytes 率 320blk≈378-535 GB/s,2176blk≈640-660 GB/s。

四假设裁决:
  H1(首两 slice 预取暴露)  部分:仅 init 链 ~0.5-1us;稳态 W 深度已足够(refill 预算≈2 slice 时间 ≫ 600ns)
  H2(ramp/波次铺开)        拒绝(rows A/B 无改善;固定项不随 nt 收缩)
  H3(LUT/scale 串行预置)   计入截距 ~0.5-1us;LUT 改 __constant__ 对 per-lane 散射索引有害,不做
  H4(冷 TLB/L2)            与 4 组旋转强相关,部分解释 per-slice 边际;无近期动作

W2'-H1a 施工结果(pf[2]→pf[3],peel-by-three,按施工图 §1.2):
  位同 PASS(120/120 torch.equal);VGPR 40→44,SCR=0(rocprofv2 元数据);
  **性能回归:o in-graph 20.8→23.7us(+14%),event 27.5→30.2;down +19%;gateup 537GB/s(<570 门)**
  → 回滚(git checkout;磁盘 .so 已还原 86470c5d)。教训:320-512 block 的 decode GEMV
  occupancy 由 grid 决定,VGPR +4 在此不解释回归;更深 ring 反而扰动稳态调度。

结论与去向:
  - o 的可回收空间 ≈ 20.8 → ~16us(floor:bytes@640GB/s + 3.5us 截距),唯一的脚本内杠杆是
    H1b(slice 1024→2048,半数 staging 链 + 2KiB 连续 refill),已按位同映射
    (chunk%64→lane,{L,L+64} 序,acc 两笔加法保序)实现于 m1 核(kM1Slice,单独常量,
    stream_block/wholea 不动),见 s36-w2p-h1b 记录。
  - 语义澄清:W2' 微测门 "o≤20us/qkv≤22us" 若按 fill_model(单 kernel/graph)口径,
    含 ~7us graph 间隙,核内任何改进都到不了;应按 packed/in-graph 口径评
    (生产 piecewise cudagraph 与之同构)。建议后续 WP 门统一标注口径。

W2'-H1b 施工结果(m1 核 kM1Slice=2048,每 lane 2 chunk,{L,L+64} 保序映射):
  位同 PASS(120/120);构建 aae21ab5。
  **性能回归:o packed kpk16 22.33 vs 20.94(+6.6%);event o 28.6/qkv 30.3/gateup 86.5
  (515 GB/s,<570 门)/down 49.0/syn4352 49.0,全线 +3~12%** → 回滚(.so 还原 86470c5d)。
  裁决:H1a(深 ring)与 H1b(大 slice)双双回归 → 1024-slice/depth-2 是该访问模式的
  局部最优;o/qkv 剩余超额(~5us/kernel)属低 block 数下的 DRAM 并行度结构项,
  核内微调不可达。这实际上**复活了 S34-WP5(split-K)的适用条件**:设计图 §2.3 预留的
  "若 W2'-分解发现 F 实为可摊薄结构,重新评估" 成立——建议后续 WP 以新证据重启
  split-K GEMV 评估(仅 o/qkv 类小 N 形状,目标把 o 的 20.8us 压向 bytes 下限 ~12-13us)。
  本轮 W2' 结论:零收益,两条脚本路线均被位同+微测门拦截后回滚;.so 与源码均回到基线。
