# 实测校准：4×Z100L 的 SOL 常量与修正后的极限基线（2026-10-25）

> **性质**：真机实测（卡空闲），把 `docs/perf/SOL-BASELINE-qwen38-27b-tp4.md` 里的
> 常量逐条验证，并**修掉两条被推翻的假设**。
> **环境**：容器 `fp8-w8a16-gpu`（`z100-dtk2604-torch211:fp8`），DTK 26.04 / torch 2.11.0 /
> HIP 6.3.26113，4×Z100L，`hy-smi` 全程 0% VRAM / 0% HCU（测前测后各一次）。
> **窗口**：2026-10-25 08:20–08:29 (+08)。
> **原始数据**：`docs/perf/data/sol-20261025.json`（单卡项 + P2P）、
> `ar-sizes-20261025.json`（AR 尺寸扫描）、`ar-80mb-20261025.json`、
> `ar-140op-20261025.json`。
> **脚本**：`tools/dcu/sol_measure.py`、`tools/dcu/ar_bench.py`（均在树内，可复跑）。
> **复算**：`.venv/bin/python tools/dcu/sol_baseline.py --measured`。

## 0. 结论（先看这五条）

| # | 结论 | 影响 |
|---|---|---|
| 1 | 带宽/算力常量**被证实**，且比历史值略高：copy **815–828 GB/s**（旧 776）、read **784**、GEMM **19.63–19.67 TF/s**（旧 19.61）、P2P **28.4 GB/s × 12/12**（一致） | 旧 SOL 的"硬件上限"一栏偏保守 5%，其余不变 |
| 2 | **`decode SOL 8.7 ms` 不可达**：它隐含"权重按 copy 带宽读"，而 GEMV 形状实测只有 **197–292 GB/s**。纯行归约能到 **684 GB/s** ⇒ 瓶颈是 GEMV 的 K 链，不是 HBM | 权重项从 8.3 ms 修正为 **16.3 ms（生产 stream kernel）～24.1 ms（rocBLAS GEMV）** |
| 3 | **all-reduce 的 per-op 地板 = 90 µs**（80 KB，4 rank，独立复现），不是带宽。140 次/步 = **12.6 ms** | 与历史"13 ms 屋顶"吻合；这是 TP4 decode 的**第一大项** |
| 4 | 修正后的单流 decode：**29.3 ms（stream GEMV，可达）/ 37.1 ms（rocBLAS）/ 21.3 ms（copy 口径，不可达）** ⇒ **76–97 tok/s 可达** | 现状 129 ms / 22 t/s，差距 **3.5–4.4×**，不是 10× |
| 5 | prefill 把 AR 税算进去：8k SOL 从 1452 → **1208 t/s**（AR 594 ms） | 现状 840 t/s ⇒ 差距 **1.4×** |

**一句话**：这台机器的 decode 上限不是"8.7 ms 读一遍权重"，而是
**"权重 16–24 ms + 通信 12.6 ms"≈ 29–37 ms/步**；瓶颈从"带宽"变成了
**小 M 内核效率 + RCCL 每 op 90 µs 的固定开销**。

## 1. 原始测量

### 1.1 四卡一致性（`sol-20261025.json`）

| 卡 | copy GB/s | read GB/s | GEMM 4096³ TF/s |
|---:|---:|---:|---:|
| 0 | 815 | 784 | 19.63 |
| 1 | 828 | 784 | 19.64 |
| 2 | 815 | 783 | 19.67 |
| 3 | 815 | 784 | 19.66 |

四卡差异 <1.6%，无"混插慢卡"现象（历史 672/651/490/490 的分化已不存在——那批
2×Z100+2×Z100L 已换成 4×Z100L）。

### 1.2 P2P（12/12 对）

`peer_access` 全 1，**12 对全部 28.4 GB/s**（ACS 关闭态）。与 2026-10 归档一致，
说明 fabric 配置没漂。注意：这是 `copy_` 的 peer 带宽，**RCCL all-reduce 仍走 SHM**，
所以它不等于通信上限（见 1.4）。

### 1.3 GEMV 形状：本次最重要的测量

`W[N,5120]` fp16，读整块权重，单位为 GB/s（4 卡取卡 0，其余三卡同量级）：

| N | GEMM M=1 | GEMM M=8 | `torch.mv` | `w.sum(dim=1)`（纯归约） |
|---:|---:|---:|---:|---:|
| 1280 | 193 | 169 | 102 | 333 |
| 3584 | 238 | 197 | 208 | 575 |
| 4096 | **90** | 217 | 268 | 590 |
| 5120 | 222 | 229 | 275 | 633 |
| 8704 | 240 | 197 | 292 | **684** |

**判读（三条都重要）：**

1. **读侧没问题**：`w.sum(dim=1)` 到 **684 GB/s**（read 屋顶 784 的 87%）⇒ HBM 能喂饱
   一个"逐行归约"的内核。
2. **GEMV 只有 197–292 GB/s**（copy 的 24–36%）：同样的字节量，一旦变成 `dot(W_row, x)`，
   带宽掉到 1/3。原因是小 M 下 K=5120 串行链 + tile 浪费，与 PERF1 §5 的
   "M≤8 走 GEMV/GEMM 派发"结论一致。
3. **M=8 不比 M=1 快**（169–239 vs 90–240）：对 M 平坦 ⇒ 投机解码的 verify 宽度
   **几乎免费**（与 PERF1 §5.1 的"GEMM 在 M=1..8 平坦"独立互证）。
4. `N=4096` 的 M=1 掉到 90 GB/s 是 rocBLAS 选核的形状效应（四卡一致复现），
   说明**按形状派发**在这张卡上不是微优化，是 2.5× 的差别。

**修正**：SOL 里"权重项 = 6.75 GB / 815 GB/s = 8.3 ms"保留为**理论上界**，但
**可达上界**必须换成 GEMV 口径：

| 权重流口径 | 6.75 GB / 卡 | 依据 |
|---|---:|---|
| copy 815 GB/s（做梦，GEMV 达不到） | 8.3 ms | §1.1 |
| **stream GEMV 414 GB/s** | **16.3 ms** | PERF1 §5.1，N=8704 实测 |
| rocBLAS GEMV 280 GB/s（本次最好 N） | 24.1 ms | §1.3 |
| 生产现状（175 GB/s） | 38.6 ms | PERF1 §0.2 |

### 1.4 all-reduce：per-op 90 µs 的地板

4 rank、bf16、`dist.all_reduce`、50 组采样（`ar-sizes-20261025.json`）：

| 消息 | p50 µs | 有效 GB/s | 140 次/步 |
|---:|---:|---:|---:|
| 10 KB | 98.6 | 0.1 | 13.8 ms |
| 40 KB | 101.0 | 0.4 | 14.1 ms |
| **80 KB（k=7 verify）** | **91.0** | 0.9 | **12.6 ms** |
| 160 KB | 95.5 | 1.7 | 13.4 ms |
| 1 MB | 132.7 | 7.9 | 18.6 ms |
| 4 MB | 297.2 | 14.1 | 41.6 ms |
| 20 MB | 1205.1 | 17.4 | 168.7 ms |
| 80 MB（8k prefill chunk） | 4641.1 | 18.1 | 649.8 ms |

**判读：**

1. **<160 KB 的消息完全是延迟项**：90–100 µs，与消息大小无关。带宽口径下 80 KB
   ring 只要 4.3 µs ⇒ **95% 是固定开销**。这独立复现了 PERF1 的 72–260 µs/op。
2. 140 次 × 91 µs = **12.6 ms/步**；这正是历史文档里"allreduce 屋顶 ~13 ms"的来源，
   本次把它从"推断"升级为"实测可复现"。
3. ≥1 MB 才看到带宽：**17.4–18.1 GB/s**（28.4 GB/s P2P 的 62%），因为走 SHM。
4. **prefill 也要付这笔**：8k chunk 的 128 次 AR 是 594 ms（4.64 ms/op），占 8k prefill
   总时间（约 5.6 s）的 **10.5%**；20 MB 档 1.2 ms/op 与线性外推对得上。

## 2. 校准后的极限基线

### 2.1 decode（单流，c=1，k=7，bf16 KV，acc 2.84）

| 权重流口径 | ctx 7.5k | ctx 32k | ctx 128k |
|---|---:|---:|---:|
| copy 815（不可达） | 21.3 ms / 133 t/s | 22.6 / 125 | 27.8 / 102 |
| **stream GEMV 414（可达）** | **29.3 ms / 97 t/s** | 30.7 / 93 | 35.8 / 79 |
| rocBLAS GEMV 280 | 37.1 ms / 76 t/s | 38.5 / 74 | 43.6 / 65 |

拆解（7.5k，stream GEMV 口径）：**权重 16.3 ms + KV 0.4 ms + AR 12.6 ms = 29.3 ms**。
⇒ 通信占 43%，权重占 56%，KV 在 7.5k 可忽略。

| 场景 | 校准前 SOL | 校准后 SOL | 现状 |
|---|---:|---:|---:|
| 单流 decode 7.5k | 12.5 ms / 226 t/s | **29.3 ms / 97 t/s** | 129 ms / 22 t/s |
| 单流 decode 128k | 19.1 ms / 149 t/s | **35.8 ms / 79 t/s** | 数十秒/步 |
| 4×121k 并发 | 37.8 ms / 300 t/s | **54.4 ms / 209 t/s** | 40–100 s/步 |

### 2.2 prefill（含 AR 税）

| prompt | AR 税（128 次） | prefill t/s | TTFT s |
|---:|---:|---:|---:|
| 512 | 45 ms | 1282 | 0.96 |
| 2048 | 154 ms | 1283 | 2.16 |
| 8192 | 594 ms | **1208** | 7.34 |
| 32768 | 2376 ms | 968 | 34.40 |
| 131072 | 9505 ms | 540 | 243.36 |

校准前 8k SOL 是 1452 t/s（不含 AR），校准后 **1208 t/s**；现状 840 t/s
（TTFT 8.89 s）⇒ 差距 **1.4×**，余量比原来更小。

### 2.3 聚合封顶

算力封顶仍是 **1452 t/s**（78.4 TF/s ÷ 54 GFLOP）。但因为通信地板存在，
单步成本 ≈ 29 ms（低并发），要到 **~15 路 × acc 2.84 ≈ 43 token/步** 才撞上算力墙。
⇒ **低并发被"GEMV + AR"限制，高并发才被算力限制**；两端之间有一个很宽的平台区
（每多一路几乎不增加步时），这正是"提高并发最划算"的区间。

## 3. 对优化优先级的影响

| 项 | 校准后的大小 | 与旧判断的差别 |
|---|---:|---|
| host launch（PERF1：48×2.83 ≈ 136 ms/步） | 仍是最大单项 | 不变 |
| **AR 12.6 ms/步（140 op × 90 µs）** | **第二大，纯延迟** | 从"带宽问题"改为"op 数 × 固定延迟" |
| 权重流（175 → 414 GB/s） | 38.6 → 16.3 ms，值 22 ms | 与旧判断一致，但现在有了 M 平坦的证据 |
| 权重流（414 → 815） | 16.3 → 8.3 ms，值 8 ms | **不现实**：GEMV 形状到不了 copy 带宽 |
| prefill AR 税（594 ms/8k chunk） | 占 10.5% | **新增项**，旧 SOL 完全没算 |

三条可执行的判断：

1. **降 AR 次数比降 AR 字节更值钱**：80 KB 与 10 KB 都是 90 µs。
   每层两次 AR 合成一次 ⇒ 140 → 76 次 ⇒ 省 **5.8 ms/步**；这一项不依赖任何新硬件。
2. **不要为"GEMV 追 copy 带宽"立项**：684 GB/s 是行归约的上限，GEMV 的 K 链决定了
   280 GB/s 量级；把 175 → 414 是现实目标（PERF1 已经做到过一次）。
3. **prefill 的 AR 税要单独记**：8k 上 594 ms，chunk 越大越贵（消息线性变大），
   所以"MBT 越大越好"在 AR 这一侧是有代价的，与"减少 chunk 边界"要一起算。

**GEMV 那一条的后续**：已单独做成 [GEMV-OPT-20261025.md](GEMV-OPT-20261025.md)——
实测一个 `warp-per-row` kernel 在 M=1 就能到 749–771 GB/s（750 是形状天花板，不是 200），
而生产在 k=7（M=8）上被 `smem > 44 KiB` 的门挡出了 stream 内核，落到 139–182 GB/s 的
tiled 回退；A 改成按 K 切片后 M=8 实测 451 GB/s。

## 4. 复跑方式

```bash
# 0) 先确认卡空闲（本脚本要 ~5 GB/卡）
hy-smi | sed -n 4,8p

# 1) 单卡项 + P2P（~40 s）
docker cp tools/dcu/sol_measure.py fp8-w8a16-gpu:/tmp/
docker exec -w /tmp fp8-w8a16-gpu python3 sol_measure.py \
  --devices 0,1,2,3 --samples 8 --json /tmp/sol.json

# 2) all-reduce 曲线（~30 s，需要 4 卡）
docker cp tools/dcu/ar_bench.py fp8-w8a16-gpu:/tmp/
docker exec -w /tmp -e USE_LIBUV=0 fp8-w8a16-gpu \
  python3 -m torch.distributed.run --nproc_per_node=4 --master_port=29611 \
  ar_bench.py --sizes 10KB,80KB,160KB,1MB,4MB,20MB,80MB \
  --iters 20 --warmup 10 --samples 30 --out /tmp/ar.json

# 3) 用实测常量重算 SOL 表
.venv/bin/python tools/dcu/sol_baseline.py --measured
```

**注意**：本次跑在 DTK 26.04 容器（torch 2.11 / HIP 6.3）；生产是 rocm101 自编栈。
算力/带宽/P2P 是硅片属性，可直接搬；**RCCL 的 90 µs 地板属于栈属性**，生产栈上
若不同，以 `ar_bench.py` 在同一栈上复测为准（这正是 PERF1 里 72/260 µs 两个数并存的原因）。
