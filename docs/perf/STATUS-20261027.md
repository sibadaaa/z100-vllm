## 2. 实测性能

### 2.1 单流上下文曲线（s34-prod，c=1，256 tok 输出）

| ctx | step p50 | tok/step | 引擎 t/s | ms/tok | 相对 7.5k |
|---:|---:|---:|---:|---:|---:|
| 7.5k | 46.50 ms | 2.40 | **51.6** | 19.4 | — |
| 32k | 52.65 ms | 2.27 | 43.0 | 23.2 | +6.1 ms |
| 60k | 60.64 ms | 2.23 | 36.7 | 27.2 | +14.1 ms |
| 64k | 51.00 ms | 1.83 | 35.9 | 27.9 | +4.5 ms |
| 128k | 62.21 ms | 1.95 | **31.4** | 31.9 | +15.7 ms |

- 64k 的非单调是 dynamic-k 截断的产物：`tok/step` 从 2.23 掉到 1.83，
  但步时也掉到 51 ms，所以 t/s 与 60k 接近。**不要用 64k 单点判断趋势。**
- 同一组数在 WP1 的 A 腿是 49.44 ms / 2.40 tok = 48.6 t/s（另一 boot 的
  accept 世界）。7.5k 的合理表述是 **48.6–51.6 t/s**，51.6 是 specbench
  三次贪心的中位（47.9/51.6/52.0）。

### 2.2 MTP k=2 的收益与代价

| 口径 | 无投机（s33） | MTP k=2（s34） | Δ |
|---|---:|---:|---:|
| 96 tok 贪心（t/s） | 36.9 | **51.6** | **+40%** |
| 512 tok temp0.7+rp1.05（t/s） | 34.7 | **40.6** | **+17%** |
| warm TTFT @7.5k | 0.72 s | **2.40 s** | +1.68 s |
| step p50 | 27.1 ms | 46.5 ms | +19.4 ms |
| tok/step / accept | 1.0 / 1.0 | 2.40 / 2.1–2.6 | — |

**盈亏平衡（贪心、含 TTFT）约 220–230 输出 token**（按无投机 36.9–37.5 t/s 口径）：
`N/51.6 + 2.40 = N/37.5 + 0.72` ⇒ N≈230；用 36.9 则 N≈218。
96-token 请求端到端约 22.5 t/s（低于无投机的 29.3 t/s）；512-token 请求约 41.6 t/s；
输出越长越接近 51.6。
这正是“短回复净收益小”的定量版本，也是 ROADMAP 里 TTFT/自适应投机项的由来。

### 2.3 并发（c=4）现状

| 口径 | 值 | 备注 |
|---|---|---|
| 7.5k c4 步周期 | 134–137 ms | decode 相 |
| 7.5k c4 tok/步 | 9.0–9.5（4 流合计） | 每流 ~2.25 tok/步 |
| 聚合 | 59–70 t/s | decode 相 66–70；整窗口径 59；仅单流的 1.2–1.4×，**不是线性 4×** |
| 128k c4 | 137 ms/步，9.48 tok/步，~68 t/s（解码相） | 探针 `ctx_tokens` 字段异常，见 §5-R6 |

合批步的 verify 载荷 = 12 token × 5120 × 2 B = **120 KiB**，正好落在
S34-WP2 把 AR 门从 64 提到 128 KiB 的靶子上；因此 c4 的 AR 仍走 push。
但“4 路只拿 1.2–1.4×”说明瓶颈不是 AR，而是 **合批 verify 的调度/内核效率**
（F1，见 ROADMAP）。

S34 的两项增量：AR size 门 128 KiB → **c4 −4.6 ms/步**；GEMV stack
（`rows=4` + `M1=1`）→ **MTP 臂 −2.03 ms/步**。

### 2.4 生产流量口径

S34 开工时的 `/metrics` 统计（48 请求，平均 prompt 60.3k）：
**TPOT 30.5 ms → 32.8 t/s**。与 60k 探针的 36.7 t/s 差 11%，
差额是真实调度、长尾与请求间空档；不要把探针的 36.7 当 SLA。

长会话生产 prefix cache 命中率约 **91.5%**（S34 开工统计）；未命中时
60k 冷 prefill 约 178 s、128k 约 520 s。**命中率是 TTFT 的生命线**。

## 3. 时间花在哪

### 3.1 无投机基线（S33 分账，29.48 ms 口径）

| 块 | ms/步 | 占比 | 说明 |
|---|---:|---:|---|
| fp8 GEMV（256 calls） | 12.49 | ~42% | 5.58 GB/步，447 GB/s |
| TP all-reduce（128 calls） | 6.9–7.4 | ~24% | push 前；延迟主导 |
| Triton 小核（norm/quant/silu） | 3.26 | ~11% | 25 个核，延迟受限 |
| attention（16 layers） | 1.28 | ~4% | 7.5k，KV 远未饱和 |
| lm_head | 0.90 | ~3% | 700 GB/s，已在天花板 |
| GDN m1 native | 1.00 | ~3% | 48 × 12.9 µs |
| 核间空隙 | 3.8 | ~13% | S33-WP0 去 profiler 工件后 |
| 其余 | ~0.3 | ~1% | 采样/尾部 |

> 量级账：单项有 ±0.3 ms 口径差，总和 ≈ 29.5–30.0 ms。S33 的 push AR
> 再省 2.0–2.8 ms、S34 的 GEMV stack 再省 2.0 ms，所以无投机臂现在约
> **24.7–26.7 ms/tok**；MTP 臂在这之上再加 draft + 3-token verify 的
> ~20 ms/步，换成 +1.4 tok/步。

### 3.2 长上下文增量（128k − 7.5k = +15.7 ms/步）

- **KV 带宽只解释约 3 ms**：128k 约 2.1 GB/卡，@776 GB/s ≈ 2.7 ms。
- **主因是 batch-1 长扫的并行度**：`triton_unified_attention` 按
  (seq, kv-head) 切分，batch-1 在 TP4 后每卡只有 1 seq × 1 kv-head 可切；
  c4 下 4 seq 摊薄后步周期与 7.5k c4 几乎相同（137 vs 134 ms），
  反证“不是带宽，是并行度”。
- **dynamic-k 不是杠杆**：E 腿（dynk OFF）实测 64k 步时 51.0→64.2 ms、
  tok/step 1.83→2.36（t/s 35.9→36.8）；128k 62.2→89.0 ms、
  1.95→2.84（31.4→31.9）。**净打平**——截断省的步时被全 k verify 的
  KV 扫描吃回去。真正能动的是 attention kernel，不是 dynk 开关。

### 3.3 已经贴顶、不要再投入的项

| 项 | 现状 | 结论 |
|---|---|---|
| all-reduce per-op | push 10 KiB ≈ 69 µs | 已低于 RCCL 90 µs 地板；只剩融合空隙 |
| lm_head | 700 GB/s | 接近读屋顶；除非改精度 |
| GDN 递推 | 12.9 µs/call | 串行版 216 µs，已 17× |
| prefill GEMM | 16.5–17.7 TF/s（M≥512） | fp16 屋顶 19.6；只剩非 GEMM 的 41% |
| GEMV 带宽 | 447 GB/s | 规划屋顶 650；再往上要 split-K / INT8 |
