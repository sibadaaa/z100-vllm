# 注意力优化方案：把 86 ms 的"注意力"拆成可执行的三项（2026-10-25）

> **输入**：`docs/result/z100-gemv-p0-slice-result.md` §5.1 的 eager 逐层表（128.5 ms/step）
> + 采纳配方 graph-A 的 torch trace（`/mnt/game/s27-prof/s27five3_rank0.1792854499912000168.pt.trace.json.gz`，
> 20 个稳态 round，`docs/result/z100-five-phase-profile.md`）。
> **口径**：单请求、真实 7469-token 文档、DFlash2 k=7（M=8）、TP=4、MBT 8192、rank0。
> **证据**：本文件 §1 的 kernel 普查可由 `tools/dcu/s27_five_phase_profile.py --phase parse` 复跑；
> 微测/对拍命令见 §4。

## 0. 结论（先看四条）

1. **你贴的那张表是 eager 臂，不是采纳配方。** eager 的 GDN attn 1.2 ms/层里，**0.70–0.76 ms 是
   C++ MTP 核**（`fused_sigmoid_gating_delta_rule_gfx906_mtp_update_kernel`，grid (6,1,1)，state 布局导致每 warp
   访存跨 32 条 cache line）；graph-A 臂里同一个核换成 **Triton MTP，25.6 µs/次**，
   48 层合计 **1.23 ms/step**。**这一项 33 ms 的差只由 `VLLM_QWEN35_MTP_GDN_TRITON` 一个 env 决定，
   而代码默认是 0、launcher 是 1——一旦 env 丢了，无论 eager 还是 graph 都 +33 ms。**
2. **graph-A 下"注意力"模块 ≈ 48 ms（42%），其中 25 ms 是它自己的 4 个投影 GEMM（权重读取），
   真正可优化的只有 14.6 ms**：in_proj_ba 10.4 ms + FA verify 3D 8.2 ms 的可压缩部分。
   GDN MTP 已经不是问题，FA 的 segment reduce 只有 0.22 ms。
3. **剩下两项都被"非量化项 greedy parity 逐 token 不变"这条门禁卡住**（ba 换 GEMV、FA BLOCK_M=16
   都会改 MMA 求和顺序）。`verify-3D` 自己就是用"近平局披露"协议过的，现在需要你**再拍一次同样的板**，
   否则注意力这条线在 116.4 ms 上最多再拿 0.2 ms。
4. **注意力之外还有两个更大的：draft 33.8 ms（29%）和 GEMM 38.1 ms（33%）**。
   前者靠 S24 dynamic-k 下探到 4–16k 是最便宜的一刀（32k 实测 −23% ITL），后者是 W4/`v_dot8` 立项。

## 2. 方案（按 ROI 排序）

### A1. `in_proj_ba`：48 次 216.8 µs 的 Triton 小 GEMM → 专用 skinny GEMV（**−8.5~−9.5 ms**）

- 现状：每 rank N=24、K=5120、M=8，读 123 KB 要 217 µs ⇒ **0.57 GB/s**，是整条 step 里
  效率最差的一个 kernel（`triton_matmul` 在 target 段的 48 次全部是它，PERF1 §6 已按 grid
  `(1,1,1)` 定位）。
- 改法：命中 `VLLM_DCU_USE_BF16_GEMV` 的 bf16 emu GEMV（`nt=128`），PERF1 §6 实测
  M=1/2/3/4 = **12.5/15.3/19.0/23.5 µs**（6.6–10.4×）。M=8 需补测；按 M≤4 的斜率外推
  ≤40 µs ⇒ target 段 10.41 → 1.0–1.9 ms。
- 落点：`vllm/model_executor/layers/utils.py:_gfx906_gemv_shape_ok`。**只给 `n_out<=64` 单独
  放行到 `n_tokens<=8`**，不要动 `n_out<=1280` 那一档的 `M<=4` 门——docstring 记录的
  "M>=8 变 LDS/compute bound、0.2–0.9×" 说的是 N=512–1280 的宽 N，N=24 每步只读一遍
  245 KB 的 bf16 权重，M 从 4 到 8 只多算 4 行，不会翻转。
- 更彻底（可选，二期）：把 `in_proj_ba` 的权重在 load 时拼到 `in_proj_qkvz` 的 N 维上，
  一层一次 GEMM（Qwen3-Next 上游就是 `in_proj_qkvzba`），省一次 launch 和一次权重读；
  但 N 变了、tiling 变，parity 同样要过。
- 风险：改 bf16 dot2 的求和顺序 ⇒ 逐 token parity 可能翻近平局（见 §3）。
- 门禁：M=1..8 逐形状 `max|Δ|`（对 fp64 参考）≤1e-3 + 8 prompt greedy。

### A2. FA verify：`BLOCK_M=16`（**−4.1 ms**），可选 BM48 再 −2 ms

- 现状：7469 ctx、8 个 query token → 8 个 q-block × 128 段 = 1024 CTA，每 CTA 只有
  1 个 token 的 6 行有效；KV 被重读 8 遍，逻辑 KV 带宽 **11.6–15.7 GB/s**
  （`docs/result/z100-longctx-vram-optimization-result.md` §12.1）。
- `BLOCK_M=16`（2 token/q-block，KV 重读减半）在 M∈{4,8} **全上下文 −45~−52%**，
  e2e 32k ITL −7.3%；旋钮已经存在：`VLLM_GFX906_ATTN_DECODE_BLOCK_M=16`。
  本工作点预期 514 → ~260 µs/层 ⇒ 8.22 → ~4.1 ms。
- 未晋级的原因只有一个：`tl.dot` 的 constexpr M 变了 ⇒ MMA 归约顺序变 ⇒
  `p512_analysis` 第 39 token 近平局翻转（§12.2）。**这是政策问题，不是工程问题。**
- 可选 A3：`BLOCK_M=48`（8 个 token 一个 CTA 全包，KV 只读 1 遍）+ `warps=8`。
  acc = 48×256 fp32 = 48 KB/CTA，4 warps 下 48 VGPR，很可能 spill，需
  `.s24/probes/l31_verify_scan.py` 先扫；过了再谈 e2e。这一段的上限是 514 → ~130 µs/层。
- 不要动 segments：在本工作点 128 段已经是网格上限，降到 64 只省 0.1 ms 量级，
  还会再改一次数值。

### A4. GDN MTP：**已经是最优，别改**，但要把它"焊死"

- Triton MTP 25.6 µs × 48 = 1.23 ms/step；C++ 705–759 µs × 48 = 34–36 ms。
- 但：代码默认 `VLLM_QWEN35_MTP_GDN_TRITON=0`，只有 launcher 设 1；eager 下 Triton 有
  225 µs/call 的 host 税（PERF1 §4，+9.4 ms/step），graph 下被子图捕获后消失。
  **建议把默认改成"graph 臂默认开、eager 默认关"，或直接按 §2 A4' 落 C++。**
- A4'（如果必须支持 eager）：把 Triton 的 lane 映射（lane 落在 k 轴、grid
  `(V/BV, kv_heads, req)`、`BV=4`）搬进 C++ 作 `mtp_v3`，保留原生
  `[slot][head][v][k]` 布局。PERF1 实测同一映射 19.5 µs（空载）/44.5 µs（pinned worker），
  host 20 µs ⇒ 48×(45+20) ≈ 3.1 ms/step，比现在的 eager 34 ms 省 31 ms。
  工作量约 1 天，对拍拿现成的 `tools/dcu/perf1_gdn_parity.py`。
- 备选：把 state pool 分配成 `[slot][head][k][v]` 再扩 `mtp_v2` 到 `kMaxTokens=8`。
  所有 kernel 都吃 stride 参数，改动面主要是分配点 + `state.size(2)/(3)` 的 check +
  prefill 侧写 state 的那几个核，比新写一个核风险高，收益相同，不推荐先做。

### A5. 真实的天花板（不属于注意力，但决定你还能走多远）

| 项 | ms/step | 说明 |
|---|---:|---|
| draft 塔 | 33.8（29%） | 7 个 draft token 的代价；S24 dynamic-k 只在 ≥16k 生效，4–16k 没开。k=7→3 时 draft 与 verify 宽度同时下降 |
| GEMM（qkv/o/gateup） | 38.1（33%） | 权重 6.75 GB/rank，实测 ~200 GB/s；W4/`v_dot8` 是唯一再下一档的路线 |
| all-reduce | 8.3 | 64.7 µs/op，已低于 SOL 的 90 µs 独立地板；custom AR / LL 已证伪 |

**建议的顺序**：A1 → A2（先过 parity 板）→ A5 的 dynamic-k → A4'（只在需要保 eager 时）。

## 3. 需要拍板的一件事：parity 协议

A1、A2 都会改数值（不同 GEMM/dot 形态）。现有两条先例：

- `verify-3D`：439 ctx 第 15 token 翻了一次，`max|Δlogprob| 0.80 nats` 的近平局，
  以"同臂内 bit-identical + 逐 token 披露"过；
- `BLOCK_M=16`：`p512_analysis` 第 39 token 翻转，按"逐 token 不变"拒。

两者是同一类现象、不同裁决。建议把判据写成可执行的：

1. per-op：对 fp64 参考 `max|Δ| ≤ 1e-3`（P0 已用这个口径）；
2. token：8 prompt × 64 token，允许翻的位置必须满足"该位置 top-2 logprob 差 < 0.05 nat"，
   且翻转方向是双方互有（不是单向劣化），并在结果文档里逐条披露；
3. 服务：`step p50`、`tok/s`、`accept`、0 crash，5 reps 同窗口。

没有这一条，A1/A2 都进不了生产，注意力这条线就到此为止（只能拿 A4 的"防丢"）。
