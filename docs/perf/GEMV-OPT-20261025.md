# GEMV 优化：实测定位 + 改动清单（2026-10-25）

> **问题**：decode 的 SOL 从 8.7 ms 退到 29 ms，是 GEMV 带宽（197–292 GB/s）造成的。
> 那 GEMV 该怎么优化？
> **方法**：在空闲的 4×Z100L 上跑三种 GEMV 形态 × M 的带宽扫描（fp16 权重，
> 排除 LUT 干扰），再把生产 kernel 的代码门逐条对上。
> **证据**：`docs/perf/data/gemv-probe-20261025.txt`（原始输出）、
> `tools/dcu/gemv_probe.cpp`（可复跑，hipcc 单文件）。
> **环境**：容器 `fp8-w8a16-gpu`，DTK 26.04 / HIP 6.3，N=8704、K=5120，
> 权重 89.1 MB；`hy-smi` 全程 0%。

---

## 0. 结论

1. **硬件不背这个锅。** 一个 30 行的 `warp-per-row + uint4` kernel，M=1 就跑
   **749–771 GB/s**（read 屋顶 784）。GEMV 不是"天生只能 200 GB/s"。
2. **你现在 k=7 的 verify（M=8）根本没走 stream 内核。**
   `stream_block_select` 的 LDS 门是 `M*K*2 + M*nkb*4 > 44 KiB` ⇒ M=8 时 82 KB，
   被拒，退回 tiled GEMM（实测 139–182 GB/s）。**这是最大的一项，且是纯代码问题。**
3. **把 A 按 K 切片放 LDS（8 KB，而不是整块 82 KB），M=8 实测 451 GB/s**
   （同形状 2.5–3×），M=4 580、M=1 727。这一条就能把权重项从 ~38 ms 压到 ~15 ms。

| 形态（fp16, N=8704, K=5120） | M=1 | M=4 | M=8 | GB/s 来源 |
|---|---:|---:|---:|---|
| 纯归约（控制组，无 dot） | 760 | — | — | `sum` |
| warp-per-row，A 从 global/L1 重读 | **749–771** | — | 341–351 | `dot1` / `dot8` |
| warp-per-row，A 整块进 LDS（生产设计） | 727 | 580 | **451** | `lds_*` |
| rocBLAS `torch.mv` | 102–292 | — | — | 1.3 节 |
| **生产 fp8 stream（PERF1）** | 414 | — | 297 @M=3 | PERF1 §5.1 |
| **生产 fp8 tiled 回退（M=8 实际路径）** | — | — | **139–182** | PERF1 §5.1 |

## 1. 实测：形态 × M

### 1.1 M=1 的天花板就是 750，与"读"无关

```
baseline  ROWS=1  NWARP=8  sum 760  dot1 752
rows2     ROWS=2  NWARP=8  sum 736  dot1 746
rows4     ROWS=4  NWARP=8  sum 730  dot1 734
unroll2   ROWS=4  NWARP=8  sum 694  dot1 744
unroll4   ROWS=4  NWARP=8  sum 744  dot1 771
rows8w16  ROWS=8  NWARP=16 sum 743  dot1 759
nwarp4    ROWS=4  NWARP=4  sum 632  dot1 659
```

- `sum`（只读不点积）与 `dot1` 差 <2% ⇒ **M=1 时点积是免费的**，瓶颈只在读。
- 甜点：**ROWS=2–4、UNROLL=2–4、NWARP=8–16**；`NWARP=4` 掉到 659（每块 256 线程，
  每 lane 只有 8 B，凑不出 16 B 向量）。`ROWS=8` 反而降到 643–759（块大了 wave 变少）。

### 1.2 M=8：A 的复用方式决定一半

```
-- A 从 global/L1 重读（每个 m 各读一遍）--
dot8     341–351（ROWS=8/NWARP=16）
-- A 整块/切片进 LDS，warp 内复用 --
lds_m8   SLICE=512  451      SLICE=1024  430      ROWS=16  418
lds_m4   SLICE=512  580
lds_m1   SLICE=512  727
```

每读 16 B 权重，M=8 要读 8×16 B 的 A：从 L1 重读会把这 8 次变成 8 条 global load，
从 LDS 读是 8 条 `ds_read_b128`。两条路都不便宜，但 LDS 版快 1.3×。
**M=8 的 451 不是终点**——把 m 分 4+4 两组、每组共用一次 W 读，LDS 读减半，
预期 550–600（见 §3 P1）。

### 1.3 对照：ROCm 库路径为什么不行

`torch.mv` 在 N=1280…8704 上是 **102–292 GB/s**，`x @ W.T`（M=1）是 **90–241**，
而 `w.sum(dim=1)` 是 **578–684**。同一个读，换个"归约形状"就差 3×：
**rocBLAS 的 GEMV 在这张卡上没有为"整行流式读"选核**，形状稍不对就掉一半。

## 2. 生产 kernel 卡在哪（代码级）

| 位置 | 事实 | 后果 |
|---|---|---|
| `csrc/rocm/fp8_emu_gemm.cu` `stream_block_select` | `smem = M*K*2 + M*nkb*4`；门限 `stream_smem_limit()` = min(44 KiB, LDS−1 KiB) | K=5120 时 M=4 → 41 KB（过），**M=8 → 82 KB（拒）** |
| 同上，退回 `run_block` 的 tile 分支 | 实测 245–321 µs / 44.6 MB | **139–182 GB/s**，这就是 k=7 生产路径的真实带宽 |
| `kMsMax = 8`（编译期） | M 上限 8 | verify k=7 正好在边界上 |
| 内核内 `fp8x4_to_f16x2x2` ×4 + `dot2` ×8 每 16 B | LUT 成本 | fp16 750 → fp8 414（M=1，−45%） |
| 自家 probe `k_stream_rows` | 621.7 GB/s（同几何） | 同一份代码，实现差距 1.5× |

**三件事叠起来**：M=8 被门挡掉（3×）、M≤4 有 tail wave（1.5×）、LUT 再吃 45%。
优先级就按这个顺序。

## 3. 改动清单（按实测收益排序）

### P0 —— 让 M=8 重新进 stream 路径（最大，~30 行）

把 A 从"整块进 LDS"改成"**按 K 切片**进 LDS"：

```cpp
// 现在: smem = M*K*2            -> M=8 时 82 KB，被拒
// 改成: 每次只放 SLICE 个 k:  smem = M*SLICE*2  -> 8*512*2 = 8 KB
for (int s0 = 0; s0 < K; s0 += SLICE) {
  stage sA[0..M) from x + m*K + s0     // 一次 __syncthreads
  for (r = warp; r < rows; r += nwarp) // 同一份 sA 被 rows 行复用
    for (v = lane; v < SLICE/16; v += 64) { w = W[row][s0+v*16]; dot2 × 8 }
}
```
- 预期：M=8 **175 → ~450 GB/s**，权重项 **38.6 → 15 ms/步**（step 129 → ~105 ms，−19%）
- 代价：每片一次 barrier（K=5120/SLICE=512 ⇒ 10 次）＋A 的 LUT 每片重算（A 只有
  M·K = 4 万元素，占权重 0.09%，可以忽略）
- 验收：N=8704/K=5120/M=8 单 kernel ≥ **450 GB/s**；输出 vs tiled 路径 max|Δ| ≤ 1e-3（fp16 累加口径）

### P1 —— 把 M=8 的 LDS 读放大减半（~10 行）

M=8 时每 16 B 权重读 8×16 B LDS。把 m 拆成 4+4 两组、两组共用一次 W 读：

```cpp
for (int g = 0; g < 2; ++g)
  for (m = 4*g; m < 4*g+4; ++m) { ... }   // W 的 uint4 在寄存器里复用两次
```
- 预期 451 → **550–600 GB/s**（−3~4 ms/步）
- 注意：累加器从 8 个 float 变 4 个 × 2 轮，VGPR 反而降，occupancy 可能升

### P2 —— rows/nt/PREF 按 N 选（零代码，改 dispatch 参数）

- 自家表：grid ≥ 112 blocks 才有 420–445 GB/s，64–80 blocks 只有 250–400。
- N=8704 → `rows=4..8`（1088+ blocks）；N=1280 → `rows=8`（160 blocks）。
- `VLLM_DCU_FP8_GEMV_PREF` 当前是模板旋钮，A/B 一次即可（本测 UNROLL=2→4 带来 +3–4%）。

### P3 —— W4（`v_dot8_i32_i4`）再减半字节

ISA 有 `v_dot8_i32_i4`（前序探针实测 2× dot4、9.11× fma）。M=8 时权重项 15 → 7.5 ms。
代价是量化质量与一条新的反量化/scale 路径，属于独立立项（先 P0/P1 拿到 15 ms 再说）。

### P4 —— 结构性杠杆（比 kernel 更大）

- M=8 + acc 2.84 ⇒ 每 **被接受 token** 的权重字节从 6.75 GB 降到 2.38 GB；
  把 acc 从 2.84 提到 4.0 就再省 30%（不需要改 kernel）。
- 并发到 4–5 路时权重按步摊薄，聚合吞吐才撞算力墙（见 SOL-MEASURED §2.3）。

---

## 4. 不要做

| 想法 | 为什么 |
|---|---|
| 追 copy 屋顶 815 GB/s | GEMV 形状 M=1 到 750 已是 92%；M=8 受 LDS 读限制在 450–600 |
| 换 rocBLAS / 调 `torch.mv` | 102–292 GB/s，形状相关，比手写差 2–3× |
| 把 A 整块放 LDS 后等 M=8 | 82 KB > gfx906 的 64 KB/block，物理上不可能 |
| MMA/WMMA 路线 | gfx906 无 `v_mfma_*`/`v_wmma_*`（汇编探针实测） |
| 先重写 GEMV | 现有 stream 内核在 M≤4 已经 414 GB/s；M=8 是**门限**问题，不是重写问题 |
