## 0. 一页结论

### 0.1 现状（2026-11-08 生产在役栈，全部端到端实测）

| 指标 | 实测 | 条件 |
|---|---:|---|
| **prefill 峰值** | **838.5 t/s** | 8192 tok，TTFT 9.77 s |
| **prefill 有效算力** | **41–47 TF/s** | 理论 78.6，**只用 52–60%** |
| prefill @20k | 716.4 t/s | TTFT 28.61 s |
| prefill @128k | 447.0 t/s | TTFT 293.2 s |
| **decode ITL @8k** | **35.93 ms** | c=1，MTP k=2，cudagraph |
| decode ITL @32k | 39.51 ms | 同上 |
| decode ITL @128k | 51.05 ms | 同上 |
| **decode 单流 @8k** | **69.6 t/s** | 实测 2.50 tok/step ÷ 35.93 ms |
| **聚合（B=4，8k）** | **70.0 t/s** | 4 × 2.40 ÷ 137.21 ms |
| 接受长度 @8k | 2.50 tok/step | accept_rate 0.742 |
| 接受长度 @128k | ~2.0 tok/step | @32k 实测 2.222 |

**ITL 模型（7 点拟合，128k 处误差 <1%）**：

```
ITL(ms) = 35.31 + 0.1213 × ctx_k    # 即 35.31 ms 固定 + 121.3 µs / 1k token
         ctx=1024 → 35.96   ctx=65536 → 43.62   ctx=131072 → 51.05（实测）
```

### 0.2 两条被实测推翻的旧结论

| # | 11-07 的说法 | **11-08 实测** | 影响 |
|---|---|---|---|
| 1 | decode SOL 单步 38.5 ms（权重 22.7 + AR 15.7） | **实测 35.93 ms，已经比“SOL”快** | “decode 还差 1.21×”作废：**单流已经贴着当前实现的极限跑** |
| 2 | 长上下文 KV 只值 1.28 ms（128k） | **实测 16.6 ms（128k）**，斜率 121.3 µs/1k token | 长上下文 decode 的钱**在 KV 读**，不在 attention 并行度 |

两条都源于同一个错误：11-07 的 AR（15.7 ms/步）是按 **RCCL** 的 140 op × 112 µs
算的，而**生产跑的是 custom AR + fusion**（`VLLM_DCU_CUSTOM_AR=1`、
`VLLM_DCU_CUSTOM_AR_FUSION=1`），op 数和逐 op 开销都不是 RCCL 的口径。
**拿离线 RCCL 地板去算在线步时，会得到“实测比理论还快”的矛盾——这正是信号。**

### 0.3 三条真正的新结论

1. **单流 decode 已经基本到顶**（35.93 ms vs 拟合出的 35.31 ms 固定成本）。
   再压只能动“固定成本”本身：权重流 + AR。
2. **合批几乎不省时间**：ctx=512（KV 可忽略）下 B=1→4，ITL 35.61 → 127.08 ms，
   `step(B) = 5.1 + 30.5×B`。**每多一路就多花一份“读权重”的时间**，
   而不是共享。这是当前最大的结构性损失（§3.2）。
3. **长上下文的斜率是 KV 读，且效率只有 64 GB/s 量级**（§3.1）。
   128k 时 KV 占步时 32%，这是唯一随上下文增长、且还有 10× 空间的项。
4. **prefill 的实际算力只有理论值的 52–60%（41–47 TF/s vs 78.6），
   而且这个比例从 8k 到 128k 稳定存在**（1.69× → 2.33×）。
   **根因已定位：attention 只跑 1.56 TF/s（屋顶的 2%），8k 里它占 31% 的墙钟
   但只有 1.0% 的 FLOPs。GEMM 本身已到 20.8 TF/s，不是问题**（§5.3）。

## 1. prefill 实测

条件：`tools/dcu/s24_longctx.py --reps 3 --gen 24`，冷缓存（每 rep 换 seed），
生产栈在役、无其他负载。

| prompt | TTFT s | prefill t/s | 相对峰值 |
|---:|---:|---:|---:|
| 512 | 0.78 | 662.5 | 79% |
| 2048 | 2.59 | 790.5 | 94% |
| **8192** | **9.77** | **838.5** | **100%** |
| 20480 | 28.61 | 716.4 | 85% |
| 32768 | 46.30 | 707.6 | 84% |
| 131072 | 293.20 | 447.0 | 53% |

**判读**：

1. **峰值在 8k**，838 t/s；两端都掉。小 prompt 掉是固定开销摊不开，
   大 prompt 掉是 attention 占比上升（128k 时 attn 占 28.5% 的 FLOPs，
   而 attention 的 MFU 远低于 GEMM）。
2. **小 prompt 有 ~0.15 s 固定开销**：512 tok 的 0.78 s 里纯 prefill 0.61 s，
   2048 tok 的 2.59 s 里 2.44 s ⇒ 两点拟合出 **≈0.15 s 截距**，
   与 8k 的斜率一致。
3. **真正的问题不是“峰值 838”，而是“有效算力只有 41–47 TF/s”。**

### 1.1 有效算力：实测 ÷ 理论 = 52–60%

把每个长度的 FLOPs（`2·27e9·T + 2·T²·5120·16`）除以实测 TTFT：

| prompt | 实测 TTFT | 理想（78.6 TF/s） | 倍数 | **有效 TF/s** |
|---:|---:|---:|---:|---:|
| 8192 | 9.77 s | 5.77 s | 1.69× | **46.4** |
| 20480 | 28.61 s | 14.94 s | 1.91× | **41.1** |
| 32768 | 46.30 s | 24.75 s | 1.87× | **42.0** |
| 131072 | 293.20 s | 125.86 s | **2.33×** | **33.7** |

> `78.6 TF/s` = 4 卡 × 19.65（rocBLAS fp16 **4096³** 实测屋顶）。

**这张表说明**：

- **8k 只用了 59% 的算力**，128k 只剩 **43%**；
- 上一版写的“prefill 差 1.43×”是拿 **838 t/s 的峰值**去比公式，
  **那个公式假设全程 19.65 TF/s**；
- 真实空间是 **1.7–2.3×**（不是 1.4×）。

**缺口在哪？§5.3 的 profile 已经给出答案**：

| 曾怀疑 | 实测 | 结论 |
|---|---|---|
| GEMM 大 M 达不到峰 | **20.8 TF/s**（比 4096³ 的 19.65 还高） | ❌ 排除 |
| AR 税 | 0.67 s / 9.08 s = 7.4% | 次要 |
| **attention** | **1.56 TF/s = 屋顶的 2.0%，占 31% 墙钟** | ✅ **主因** |

**注意 19.65 本身偏保守**：大 M 下 GEMM 到 20.8，所以“有效算力只有 41–47 TF/s”
**不是因为 GEMM 慢**，而是**attention 的停顿把墙钟拉长、把平均值拉下去了**：

```
8k: 总 FLOPs 446.8 TFLOP ÷ 9.77 s = 45.7 TF/s
    若 attention 的 2.82 s 停顿消失 ⇒ 446.8 ÷ 6.95 s = 64.3 TF/s
    ⇒ prefill 8192 ÷ 6.95 = 1179 t/s（与 §5.3.3 的 1176 一致）
```

## 2. decode 实测

### 2.1 ITL vs 上下文（c=1，8k 以上逐个上探）

| ctx | ITL p50 ms | 相对 8k |
|---:|---:|---:|
| 1024 | 35.96 | — |
| 4096 | 35.70 | — |
| 8192 | 35.93 | 1.00× |
| 16384 | 36.82 | 1.02× |
| 32768 | 39.51 | 1.10× |
| 65536 | 43.62 | 1.21× |
| **131072** | **51.05** | **1.42×** |

**32k 之前基本平坦**（35.9 → 39.5），**32k 之后线性上升**。
这不是“attention 内核慢”，是一段**随 ctx 线性增长的字节搬运**——
见 §3.1 的斜率分析。

### 2.2 接受长度随上下文衰减（这是吞吐的真实拖累）

| ctx | acc tok/step | accept_rate |
|---:|---:|---:|
| 512 | **2.759** | 0.879 |
| 8192 | 2.500 | 0.742 |
| 32768 | 2.222 | 0.604 |

**要点**：MTP k=2 的上限是 3 tok/step。512 上下文能到 2.76（92% 上限），
**32k 只剩 2.22（74%）**。所以“长上下文变慢”有两个独立来源：

```
实际 t/s = (acc ÷ ITL)
         = 接受长度 ↓（2.76→2.22，−20%）× ITL ↑（35.9→51.1 ms，−42%）
```

**两者叠加**：512 的 77 t/s → 128k 的约 39 t/s。**接受长度这一半常被忽略**，
它属于投机解码策略（草稿模型 / k 值 / 温度），**不属于 kernel 优化**。

### 2.3 合批：几乎是纯线性，没有共享

| B | ctx | ITL p50 ms | peak_running | 聚合 t/s |
|---:|---:|---:|---:|---:|
| 1 | 512 | 35.61 | 1 | 67.4 |
| **4** | **512** | **127.08** | **4** | 75.5 |
| 1 | 8192 | 36.76 | 1 | 65.3 |
| 2 | 8192 | 60.36 | 2 | 79.5 |
| **4** | **8192** | **137.21** | **4** | **70.0** |

用 ctx=512（KV 项 <0.1 ms，可忽略）拟合：

```
step(B) = 5.1 + 30.5 × B   ms        (B = 并发路数)
```

**每多一路，步时 +30.5 ms。** 参照量：读一遍每卡权重按离线 GEMV 最好的口径
约 22.7 ms ⇒ **边际成本 ≈ 1.34 个“读全量权重”**。

**这意味着**：合批**完全没有共享权重读**，每一路都在重新走一遍权重。
理想情况（权重只读一次）应是 `step(B) ≈ 22.7 + 15.7 + 0.12×B`，
B=4 时约 39 ms；实测 137 ms ⇒ **3.5× 损失**。

聚合吞吐因此几乎不随 B 增长（67 → 70 t/s），**加并发目前不划算**。

## 3. 由实测反推：钱花在哪

### 3.1 长上下文的斜率 = KV 读，效率只有 ~64 GB/s

ITL 对 ctx 的斜率 **121.3 µs / 1k token**。把它换算成带宽：

| 口径 | KV 字节/token/卡 | 斜率隐含带宽 | @128k 耗时 |
|---|---:|---:|---:|
| fp8 KV（8 KB） | 8192 | **64.5 GB/s** | 16.6 ms |
| fp8 KV，重扫 ×3 | 8192 | 193.5 GB/s | 16.6 ms |
| bf16 KV（16 KB） | 16384 | 129.0 GB/s | 16.6 ms |
| bf16 KV，重扫 ×3 | 16384 | 387.0 GB/s | 16.6 ms |

参照本机 `sum` 读带宽 **784 GB/s**。**即使按最宽容的口径（bf16 + 3× 重扫），
128k 的 attention KV 读也只跑到 387 GB/s = 屋顶的 49%；按 fp8 单扫口径只有 64.5 GB/s
= 屋顶的 8%。**

**判读**：长上下文 decode 的 attention **确实有 2–10× 的带宽空间**，
但**必须在同一口径下先钉住 KV 到底走 fp8 还是 bf16、重扫系数是多少**
（跑一次 `grep kv_cache_dtype` + 一次 profile 即可），否则会像 11-07 那样
把 1.28 ms 写成 16.6 ms 的 1/13。

### 3.2 单步固定成本 35.31 ms 的拆解

`ITL = 35.31 + 斜率×ctx`，把 ctx=0 外推：

| 组成 | 估算 | 依据 |
|---|---:|---|
| 权重流（每卡 6.75 GB） | **≈22.7 ms** | 6.75 / 297 GB/s（生产 GEMV 口径） |
| AR | **≈8–10 ms** | custom AR + fusion，op 数未知，见下 |
| attention / GDN / 采样 / host | ≈3–5 ms | 剩余项 |

- **权重流是最大单项**，且它已经是“离线最好口径”而不是“生产口径”：
  生产在 M=3（MTP k=2 verify）走的是哪条 GEMV 路径**没有单独量过**，
  这是下一步最该钉的数。
- **AR 从 15.7 ms 降到 8–10 ms 是 fusion 的功劳**（`VLLM_DCU_CUSTOM_AR_FUSION=1`），
  说明**上一版文档里“AR 140×112 µs”的假设在生产上不成立**。
  要重算必须用 `perf1_trace_kernels.py` 数实际 op 数，不能用 RCCL 的默认值。

### 3.3 长上下文 TTFT（128k = 293 s）的拆解

**理想分解**（78.6 TF/s，attention η=1）：

| 组成 | 128k | 8k |
|---|---:|---:|
| 纯线性层 | 90.0 s | 5.63 s |
| attention | 35.8 s | 0.14 s |
| 理想合计 | 125.9 s | 5.77 s |
| **实测** | **293.2 s** | **9.77 s** |
| **缺口** | **167 s（2.33×）** | **4.0 s（1.69×）** |

缺口不能只归给 attention —— **即使把 attention 当免费，128k 也只有 90 s vs 实测 293 s**。
同理 8k：attention 只值 0.14 s，4 s 的缺口全在别处。

⇒ **缺口的主要来源已由 §5.3 的 profile 定位：prefill 的 attention 只跑 1.56 TF/s（2%）。**
8k 里 attention 占 2.82 s / 9.08 s = 31%，而它的真实 FLOPs 只占 4.4/442 = 1.0%。
**GEMM 已经达峰（20.8 TF/s，§5.3.1），不是缺口来源。**
和 decode 完全不同：**prefill 的钱在 GEMM 达峰率，decode 的钱在权重流 + KV 读。**

## 5. 到极限：按“能不能拿到”排的路径

### 5.1 decode（目标：35.93 → 24 ms / 8k 单流，即 100 t/s）

| # | 项 | 现状 → 目标 | 值 | 依赖 | 把握 |
|---|---|---|---:|---|---|
| **D1** | GEMV 让 M=3 也走 warp-per-row + K 切片 | 297 → 425 GB/s | **−6.8 ms** | 已验证 M=8 到 425；M=3 待验 | 中 |
| **D2** | 数清并再融合一次 AR | 8–10 → 5 ms | **−4 ms** | 先 profile 数 op | 中 |
| **D3** | 修 3 号卡 14.3 GB/s | — | 间接 | 先查 slot/ACS | 未知 |
| **D4** | 长上下文 KV 读（§3.1） | 64.5 → 300+ GB/s | −12（仅 128k） | 先钉 dtype/重扫 | 中 |

D1+D2 可实现 day-one 收益 **约 11 ms（−30%）**，两者都不依赖新硬件。

### 5.2 合批（目标：B=4 从 70 → 200+ t/s）

这是**当前最大的结构性机会**，也是 11-07 完全没看到的一项。实测
`step(B) = 5.1 + 30.5B`，理想是 `22.7 + 15.7 + 0.12B`。**差 3.5×。**
根因已由 profiler 查明（见 **[合批专项](20261108-batch-gemm-switch.md)**）：

| 事实 | 实测 |
|---|---|
| B=1/2 走 GEMV（`fp8_emu_gemv_stream_block_kernel`） | 单价 78.6 µs @M=3 → **139.1 µs @M=6**（+77%） |
| B=4 走 GEMM（`fp8_emu_gemm_block_w8a16_kernel<32,32,64>`） | 单价 **364.0 µs**，占 kernel 时间 **49.9%** |
| 切换点 | `M = B×(1+k) > VLLM_DCU_FP8_GEMV_MAX_M=8` ⇒ B=4 的 M=12 越界 |
| 合批的净收益 | **每 token 只改善 4.6%**（48.2 → 46.0 ms/token） |
| 小算子 `other` | 占 46–49%，且单价随 B 涨 3.0× |

**两条修法**（详见专项文档）：

- **W2**：让 GEMV 在 M=3..12 跨请求复用一份权重读（≠ 现在的“按 M 线性读 M 遍”）。
- **W3**：拆 `other` 那 46–49%（elementwise/triton/rmsnorm/silu/quant），
  它们的 K 都是 5120，天然可合批。

> ⚠️ **光调 env 无效**：`_GEMV_MAX_M = min(env, _GEMV_MS_MAX=8)`，
> 已在真实模块上验证 `VLLM_DCU_FP8_GEMV_MAX_M=16` 的 effective 值仍是 8。
> 要测 M=9..12 的 GEMV，必须重编译 `fp8_emu_gemm.cu` 把 `kMsMax` 提到 16。

### 5.3 prefill（目标：838 → 1400+ t/s @8k）

**8k 的 2.9 s「未归因」已经查清：是 attention，不是 GEMM。**

#### 5.3.1 先排除掉 GEMM 的嫌疑（P1 已做）

直接量 rocBLAS fp16 在真实 prefill 形状上的达峰率（卡 0，`torch.mm`）：

| 形状 | M=512 | M=2048 | M=4352 | **M=8192** |
|---|---:|---:|---:|---:|
| gate_up (8704×5120) | 16.9 | 19.9 | 20.8 | **20.8** |
| down (5120×4352) | 16.1 | 19.9 | 20.6 | **20.8** |
| qkv (4096×5120) | 15.1 | 19.3 | 19.9 | **20.5** |
| o (5120×5120) | 16.1 | 20.0 | 20.6 | **20.7** |
| gdn (3584×5120) | 17.5 | 18.5 | 20.2 | **20.9** |

**大 M 下 GEMM 到 20.8 TF/s，比 4096³ 的 19.65 还高。**
⇒ **上一版把 2.9 s 归给「GEMM 达峰率」是错的，P1 已证伪。**

#### 5.3.2 真正的原因：prefill 的 attention 只有 1.56 TF/s

对一次真实的 8192-token prefill 做 profile（`/start_profile`，rank0）：

| kernel | 调用 | 总时间 | 占比 | µs/次 |
|---|---:|---:|---:|---:|
| `Cijk_Alik_Bljk_HBH_MT128x128x16...`（rocBLAS 大 GEMM） | 522 | **5082.0 ms** | 52.5% | 9735.6 |
| **`kernel_unified_attention_2d`** | **34** | **2819.3 ms** | **29.1%** | **82919.4** |
| `ncclDevKernel_AllReduce_Ring_Simple` | 264 | 670.1 ms | 6.9% | 2538.3 |
| `CatArrayBatchedCopy` | 96 | 187.5 ms | 1.9% | 1952.8 |
| `chunk_gated_delta_rule_fwd` | 96 | 147.2 ms | 1.5% | 1532.9 |
| 其余（elementwise/conv/dequant…） | — | ~180 ms | 1.9% | — |

**attention 的算力**：16 层全注意力 × `4·T²·kv_heads·head_dim`
= 4.4 TFLOP，实测 2.819 s ⇒ **1.56 TF/s 聚合 = 屋顶的 2.0%**。

> 注：SOL 公式里用的 `2T²·H·16` 是 11.0 TFLOP，与真实 GQA 的 4.4 TFLOP 差 2.5×
> （公式按 full-head 而非 kv-head 算）。**按真实 FLOPs，attention 的效率只有 2%。**

#### 5.3.3 所以 prefill 的账是这样的

| 组成 | 8k 实测 | 说明 |
|---|---:|---|
| 线性层 GEMM | **5.08 s** | 522 次调用，20.8 TF/s（**已达峰**） |
| **attention** | **2.82 s** | 34 次调用，**1.56 TF/s（2%）**，占 kernel 时间 **31%** |
| AR（RCCL ring） | 0.67 s | 264 次 × 2.54 ms |
| GDN + conv | 0.20 s | |
| 其他 | 0.18 s | |
| **kernel 合计** | **9.08 s** | 占 wall 9.84 s 的 **92%**，剩下 0.76 s 是 launch/采样/HTTP |

**⇒ prefill 的第一优化对象是 attention，不是 GEMM。**
attention 若能从 2% 提到 8%（仍远低于 GEMM 的 20.8），
2.82 s → 0.70 s，总时间 9.08 → 6.97 s，**8k 从 838 → 1176 t/s（1.40×）**。

**优先级（按性价比）**：

| # | 项 | 依据 | 值（8k） | 把握 |
|---|---|---|---:|---|
| **A1** | 把 `kernel_unified_attention_2d` 拆成 QK / PV / softmax / KV-load | 现在只知道 82.9 ms/call 的总量 | 先量，不改 | **必做第一步** |
| **A2** | 按 A1 提高 QK/PV 的 ILP 与占用 | S58：单链上限 6.05 TF/s，满占用 8 链 22.7 | −1.5～2.1 s | 中 |
| **A3** | prefill 的 AR 回落到 RCCL ring（已定位原因，见下） | 264 次 × 2.54 ms | **−0.5 s** | **已定位** |
| **A4** | 消 chunk 边界税（337 ms/边界） | 纯软件 | −0.34 s | 低风险 |

#### 5.3.5 A3 已定位：prefill 的 AR 被尺寸上限挡回 RCCL

同一份 trace 里，decode 与 prefill 走**两条不同的 AR 路径**：

| trace | `cross_device_reduce_push`（custom） | `ncclDevKernel_AllReduce_Ring` |
|---|---:|---:|
| decode B=1 | **4863** | 132 |
| decode B=4 | **4593** | 132 |
| **prefill 8192** | **6** | **264** |

原因在 env 与载荷大小的对比：

```
VLLM_DCU_CUSTOM_AR_MAX_KIB = 128          -> 上限 131 072 字节
prefill 8k 的 AR 载荷       = 8192 × 5120 × 2 = 80.0 MiB
                                        = 640 × 上限
```

⇒ **prefill 的单次 AR 是 80 MB，是 custom AR 上限的 640 倍，只能回落到 RCCL ring**
（实测 2.54 ms/次，有效带宽 **33 GB/s**，已达到 P2P 28.4 GB/s 的 116%）。**decode 的载荷只有 30–160 KB，正好在
custom AR 的适用区间内**，所以走 push（~20–35 µs/次）。

**这是一条“设计如此”而非 bug 的行为**，但它意味着
**prefill 的 670 ms AR 完全没享受到 decode 侧已经做好的 push AR 优化**。
A3 的现实做法不是“把 80 MB 塞进 custom AR”（那样每 128 KiB 一次的固定开销会爆），
而是**降低 prefill 的 AR 次数或载荷**：prefill 每层两次 AR（attention + MLP），
64 层 × 2 = 128 次，实测 264 次（含 MTP draft 的额外次数）。

> ⚠️ **但 33 GB/s 已经接近/超过 P2P 的 28.4 GB/s**（RCCL 在 ring 上会做
> 分块流水，实测值高于单对 `copy_` 的 28.4 并不矛盾）—— 说明这条 RCCL 路径
> **带宽上已经没有什么可榨的了**。A3 的 −0.5 s 只能靠**减少 AR 次数**
> （融合 / 用 TP 更小的切分），不能靠“换更快的 AR”。

#### 5.3.4 为什么 attention 只有 2%

四条已知因素（按影响排序，待逐条验证）：

1. **没有矩阵核**：gfx906 无 MFMA，`QK^T` 只能 `v_dot2_f32_f16`（2 MAC/指令）。
   满速率是 24.58 TF/s，但见 2–4 条，实际拿不到。
2. **单链 ILP 不足**：`z100-s58-result.md` 实测生产内核 QK^T 是**单条 fp32 累加链**、
   2 CTA/CU ⇒ dot2 上限只有 **6.05 TF/s**（满占用 8 链可达 22.7）。
3. **2 CTA/CU 的占用**：`peak.hip` 实测 2 CTA/CU 只有 82% 达峰率。
4. **每个 tile 重读 Q**：S58 已确认“钱花在每 tile 重读 Q 上”，去掉重复行
   能把 3.93 → 5.20 TF/s（1.32×，已落地）。

**2.0% 与 5.2 TF/s（S58 的内核级数）之间还有 3× 的口径差** ——
S58 量的是 attention 内核内部的有效 FLOPs，本篇量的是端到端含 KV 读写与
softmax 的墙钟。**两者不矛盾，但说明 attention 的成本里有一大块不是 FMA**，
下一轮该把 `kernel_unified_attention_2d` 内部按 QK/PV/softmax/KV-load 拆开。

**环境坑**（都实测过）：

1. **编译用 `/opt/dtk-26.10/bin/hipcc`**（PATH 上的 dtk2604 hipcc 指向不存在的
   `hip/lib/llvm/bin/clang++`），并加 `--gcc-install-dir=/usr/lib/gcc/x86_64-linux-gnu/11`；
   **跑 torch/服务用生产栈 dtk2604 的 `LD_LIBRARY_PATH`**。两套 DTK 不能混。

   `sol_idle_window.sh` 用「4 卡 0% + 无 vllm 进程」双条件判断。
4. `torchrun … vllm bench forward` 在本栈上仍会因 triton shim 报
   `UnicodeDecodeError`（`triton/backends/amd/driver.py:874`，只在特定 import
   顺序下复现；`HIPDriver().utils.get_device_properties(0)['arch']` 单独调用是正常的）。
   **单步口径请用 `s24_longctx.py` 的 ITL，或 trace。**

## 8. 这一版相对 11-07 的修正记录

| 项 | 11-07 | 11-08 实测 | 原因 |
|---|---|---|---|
| decode 单步 | 公式 38.5 ms（差 1.21×） | **实测 35.93 ms** | AR 用了 RCCL 的 140×112 µs，生产是 custom AR + fusion |
| 128k KV 项 | 1.28 ms | **16.6 ms** | 斜率实测 121.3 µs/1k token |
| 合批 | “撞算力墙需 24 路” | **B=4 就 3.5× 损失** | 边际成本 30.5 ms/路 = 1.34 个权重流 |
| prefill 峰值 | 1110 t/s（公式） | **838.5 t/s（实测）** | 公式假设 GEMM 全程 19.65；实测小 M 低、大 M 高（20.8） |
| prefill 缺口 | “GEMM 达峰率不足” | **attention 只跑 1.56 TF/s（2%）** | profile：GEMM 已 20.8 TF/s，attention 占 31% 墙钟 |
| 接受长度 | 固定 2.40 | **2.76→2.22 随 ctx 衰减** | 未纳入旧模型 |

**教训**：**离线微基准（RCCL 的 op 延迟、rocBLAS 的 4096³ 屋顶）不能直接
代进在线步时公式。** 每一层（fusion 与否 / cudagraph 与否 / 合批与否）都会
改变量级。**先端到端拟合，再用微基准解释斜率** —— 反过来做会得到自相矛盾的数
（“实测比理论 SOL 还快”）。
