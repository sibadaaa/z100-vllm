## 执行方式：一步一个子 agent，结果归档到 `docs/result/`

为控制主 agent 上下文，**每一步（S0–S10）都交给一个独立子 agent 执行**，流程固定：

1. **派发**：主 agent 按 `docs/design/z100-<NN>-*.md` 写任务书，声明该步的**写作用域**与门禁。
2. **执行**：子 agent 只读设计文档 + 方案 + `hygon_z100.md`，完成代码/验证，并在本机允许的范围内取原始证据。
3. **归档（强制）**：子 agent **必须**写出 `docs/result/z100-<NN>-<slug>-result.md`，
   结构见 [`docs/result/README.md`](result/README.md) 的模板（目标/改动/原始证据/门禁判定/未完成项/对后续影响/复现方式）。
   未产出归档 = 该步未完成。
4. **复核**：主 agent 读归档（不读中间过程），跑或抽查该步门禁，然后更新本文件的状态列与「执行记录」。
5. **回传**：子 agent 最终回复 ≤15 行（状态、改动文件、门禁是否通过、遗留项），详细内容一律放归档文件。

归档约定细节与索引见 [`docs/result/README.md`](result/README.md)。

## 全局硬约束（每一步都必须遵守）

1. **禁止在这台机运行自编译 HIP 二进制**。2026-10-07 曾因执行 `/tmp/t` 触发 hydcu 驱动 `kfd_wait_on_events` 死锁，进程不可杀、loadavg 涨到 878，只能重启。允许：`hipcc -c/-S` 编译、`dccobjdump`/`llvm-objdump` 反汇编、torch 层探针。禁止：执行任何自己编译出的 `.out`/`.o` 可执行程序。
2. **不动生产容器 `qwen38-vllm`（:8000）**。所有实验在影子容器（:8001 或更高）进行。
3. **构建产物必须落在 `/mnt/game`**（根分区仅剩 ~46 GB）。
4. **不替换** DTK 的 RCCL / rocBLAS Tensile / hipBLASLt / MIOpen / triton 后端目录 / `/opt/hyhal`。
5. **不把 gfx906 加进本 fork 的 `_ON_GFX9`**（该 fork 有意排除 gfx906/gfx908）。
6. 所有新增分支必须可被 `is_hygon_dtk()` 或"amdsmi 失败才走"的 fallback 包裹，保证未装 DTK 的机器行为不变。
7. 每个步骤完成后，先跑**该步骤的门禁**，再更新本文件的"状态"列与「执行记录」小节。
8. **DTK 镜像里所有 python 侧探针/门禁都必须先 `import torch`（或 `import triton`）**：否则 `import vllm` 会 `std::bad_alloc` → SIGABRT(134)（生产容器实际也是这个顺序）；归属见 S6 前置检查。
9. `pip install -e .` **不能**用于本项目的续跑构建（setuptools editable 每次用随机临时构建目录、`.so` 进 site-packages）→ 统一用 `build_ext --inplace`，构建副本在 `/mnt/game/port/gfx906-vllm`、持久 CMake 目录 `/mnt/game/port/build-gfx906/temp`。
10. 复用 S4 留下的构建容器 `z100-build`（`--memory=8g`，未 `--rm`）时：环境 `source /mnt/game/port/setenv.sh`，重建前必须 `docker exec z100-build pkill -f build-keepgoing`（ninja 会锁构建目录）。
11. **构建树有 mtime 边界**（S4d 实测）：hipify 已 stamp 化（无改动 0.1 s、单 TU ~40 s、全量 ~16 min），但 ninja 按 mtime 判 clean——若把**内容变化而 mtime 倒退**的文件（`cp -p`、解旧 tar）放进构建树，生成物会陈旧。规避：`touch` 该文件 / 删 `CMakeFiles/hipify_all.stamp` / `ninja -t clean`。

26. **27B TP=4 的内存约束：不是 cgroup 上限，而是"图模式的宿主匿名内存 > 本机物理内存"〔2026-10-09 第二次更正，S14 实测〕**。此前的说法（"真因 = 影子容器 `z100-s9` 的 cgroup 32 GiB 上限，`MemLimit=0` 就能跑"）**与内核日志不符，已作废**。原始证据（Lead 独立复核 `dmesg`/`journalctl -k`，三次 OOM 原文一致）：
    - `oom-kill:constraint=CONSTRAINT_NONE,...,global_oom,task_memcg=.../docker-<id>.scope,task=VLLM::Worker_TP`；
    - `Out of memory: Killed process ... total-vm:60223044kB, anon-rss:7085936kB, **file-rss:0kB**, shmem-rss:177240kB`；
    - 第三次（S14，容器 `z100-s14`）`docker inspect --format '{{.HostConfig.Memory}}'` = **0**、容器内 `/sys/fs/cgroup/memory.max` = **max**、`memory.current` 峰值 **29.76 GB < 32 GiB 上限** ⇒ **与 cgroup 上限无关，是宿主级 global OOM**（3 次里 0 次是 `CONSTRAINT_MEMCG`）。
    - **`file-rss:0kB` 的正确解读（S14 §3.7 实测更正了 Lead 的中间推断）**：它**不代表权重是匿名内存**——权重（`Model loading took 7.27 GiB`×4）在**显存**里；`file-rss:0` 是因为**页缓存是 OOM 时首批被回收的**。实测构成：每 worker `RssAnon` **4.3–4.5 GiB（TP=4 eager）/ 6.6–6.9 GiB（TP=2 graph）**、`RssFile` 0.19 / 1.27 GiB，EngineCore 另约 1.67 GiB。

    **已排除的两个方向（S14 §3.8）**：① **不是图池**——图池 1.67→0.22 GiB、捕获 685→7 s 仍 OOM 且落点不变；② **不是我们的 sdot4 权重重排**——`VLLM_DCU_USE_INT8_SDOT4=0`（改选 `TritonInt8ScaledMMLinearKernel`）同样 OOM（`anon-rss` 7.28 GB 同档）⇒ 多出来的需求在**编译/切分执行路径**。
    **可行的绕法**：挂 **16 GiB `/mnt/game/swapfile`** 后 graph TP=4 可跑（350/351 s 就绪，decode **49.66 ms/token**）。swap 的作用是**桥接启动瞬时峰值**（启动期换出 7.78 GB，权重本体仍在显存；引擎一关 swap 立刻回落 0.53 GB），**不是容量替代**。**但启动余量极小（一度只剩 507 MB）⇒ 生产不宜照搬，须单独评估**（→ S14c）。用无 cgroup 上限容器仍是必要条件，但**不是充分条件**。**4B 的 TP 曲线不能外推到 27B**（27B decode 是权重带宽主导，切 4 卡后每卡流量减半）。
