## 0. 已确认的决策

| 项 | 决策 |
|---|---|
| 目标软件栈 | DTK 26.04 + `torch 2.11.0+das.opt1.dtk2604` + `triton 3.6.0+das185.dtk2604` |
| 架构范围 | **只支持 gfx906**（本机 4 张 DCU 实测同为 gfx906，仅板卡 SKU 不同） |
| 交付节奏 | 阶段 A（dense fp16 文本推理 + TP）→ 验收 → 阶段 B（GGUF/MoE/MTP/多模态） |
| 适配策略 | **不改写 gfx906 内核与门控语义**；只新增一层 DTK 运行时兼容层 |

## 1. 核心判断

Z100 在 ISA 层就是 **gfx906**（Vega20 / GCN5.1）。分支内 382 处 `gfx906` 门控与专用内核语义仍然成立。真正的差异在运行时栈。因此采用两条正交轴：

| 轴 | 判据 | 说明 |
|---|---|---|
| ISA 轴（既有） | `on_gfx906()` / `on_cdna()` / `on_gfx9()` | 算力特性门控，**语义不动** |
| 运行时轴（新增） | `hygon_dtk.is_hygon_dtk()` | DTK 栈差异，全部为附加分支 |

> ⚠️ **不要**把 gfx906 加进本 fork 的 `_ON_GFX9`。前序计划里的这条建议针对**上游** `rocm.py`；本 fork 的 `on_gfx9()` **有意排除 gfx906/gfx908**（见 `vllm/model_executor/layers/fused_moe/experts/gpt_oss_triton_kernels_moe.py:53` 注释），改回去会打开 MFMA 假设路径。

## 2. 事实基线（实测，详见 [hygon_z100.md](hygon_z100.md)）

### 2.1 硬件与栈

| 项 | 实测 |
|---|---|
| DCU | 4 张 gfx906，各 32 GiB，`gfx_target_version 90106`，PCI DID `0x55B7`×2 / `0x54B7`×2 |
| DTK（宿主） | 24.04.3（HIP 5.7 / clang 15）；目标 26.04 在容器内 |
| 社区 ROCm | `/opt/rocm` 不存在；`rocminfo`/`hipcc` 仅在 `/opt/dtk/bin` |
| rocBLAS | 仅 gfx906 Tensile（`Kernels.so-000-gfx906.hsaco`）→ **已够用，别换** |
| hipBLASLt | 只有 gfx928 → **gfx906 不可用**，必须避开 |
| amdsmi | 无 python 模块；DTK 存在的版本把 gfx906 报成 **`gfx916`**（海光 SMI 命名）或 `gfx18446744073709551615` |
| DRM 序号 | `card0` 是 NVIDIA 卡，4 张 DCU 是 `card1..card4` → 不能按序号读 sysfs |

### 2.2 两个必须一起记住的坑

1. **架构归一化**：amdsmi 报 `gfx916`，而驱动/torch/自编译内核都是 `gfx906`。`gfx916` 会让 `_capability_from_gcn_arch` 得到 `(9,1)`，`capability.minor == 0` 的 gate 全部失效。**必须归一化 `gfx916 → gfx906`，不能只加白名单。**
2. **`get_device_properties("cuda")` 在 DTK 上死锁**，必须用整数索引 `(0)`。

### 2.3 bf16 结论（本轮实测钉死）

- ISA 层：gfx906 **无 bf16 指令**。DTK 汇编器对 `v_cvt_f32_bf16` 报 `invalid instruction`，对 `v_dot2_f32_bf16` 报 `instruction not supported on this GPU`；而 `v_pk_fma_f16`、`v_dot2_f32_f16` 均 OK。⇒ bf16 只能软件模拟。
- `torch.cuda.is_bf16_supported()` 在 ROCm 上**恒为 True**，**不得**作为判据。
- `torch.set_default_dtype(torch.bfloat16)` **不是能力开关**，只影响新建张量默认 dtype；正确开关是 `--dtype bfloat16` + `supported_dtypes`。
- 已实现**探针 + 显式开关**：`VLLM_DCU_BF16=auto|1|0`，`auto` 时按存储往返 / GEMM / softmax 实测；fp16 仍排第一，`--dtype auto` 行为不变。
- 生产上：fp16 可用（生产容器现在就跑 bf16，其 profiler 显示 bf16 rocBLAS GEMM ~8.2 ms/次 —— **2026-10-07 真机复核：与 4096³ 实测不符，实测 fp16 7.84 ms / bf16 21.54 ms，口径待 S9 复核**）；**bf16 保留结论已裁决**：真机探针 PASS（GEMM rel 0.229%），保留为可选 dtype、默认仍 `auto`，详见 [S3 归档](result/z100-03-bf16-verification-result.md)。

### 2.4 生产现状与约束

- 生产容器 `qwen38-vllm`：vLLM 0.18.1+das，端口 8000；其中 `_rocm_C` **缺失**（das 轮子剥掉了 `LLMM1`/`wvSplitK`/`wvSplitKQ`/`paged_attention_rocm`）→ 这是"支持很差"的物理原因之一。
- 影子服务端口 8001；模型在 `/mnt/game/models`；**根分区只剩 ~46 GB，构建必须落在 `/mnt/game`**。
- Triton gfx906 补丁（VEGA ISAFamily，57 行）已归档：`artifacts/triton-gfx906.patch`（针对 triton `c817b9b6`/3.4.0 验证）。
- 参考实现：[nlzy/triton-gfx906](https://github.com/nlzy/triton-gfx906)（最高 3.5.0、面向社区 ROCm）——**只作对照与补丁来源，不作构建基座**；其 `ISAFamily` 用 `VEGA20` 并把 gfx906 折进 `isCDNA()`，我们不采用该结构（MFMA 风险）。对照细节见 [S6 设计文档](design/z100-06-triton-gfx906.md) §4。
- 禁止替换：DTK 的 RCCL、rocBLAS Tensile、hipBLASLt/MIOpen、DTK 的 triton 后端（`compiler_hcu.py`）、`/opt/hyhal`。

### 4.2 实施中发现并修掉的真实缺陷

| 缺陷 | 影响 | 处置 |
|---|---|---|
| KFD `node0`(CPU) 也报 `gfx_target_version 0` | 架构一致性判断被带偏，`VLLM_DCU_GCN_ARCH` 导出失败 | 已修 + 回归单测 |
| DRM `card0` 是 NVIDIA 卡 | 按序号读 sysfs 会错位 | 改为 vendor(`0x1d94`) + PCI BDF 排序 |
| amdsmi 缺失时 `rocm_platform_plugin()` 返回 None | **无平台可用** | DTK 早返回；`is_fully_connected` 不再崩溃 |
| DTK clang 找不到 C++ 头（找 gcc12，本机只有 gcc11） | `hipcc` 任何 C++ 源码都 `'cmath' file not found` | `env.sh` 补 `CPLUS_INCLUDE_PATH`，已实测编译通过 |

### 4.3 尚未解决的缺口

1. **`gfx916 → gfx906` 归一化未实现**（§2.2）——当前 DTK 路径优先用 torch 的 `gfx906` 绕开了该坑，但非 DTK 检出路径仍可能拿到 `gfx916`。见 S1。
2. **构建/内核/Triton/验收未做**（S4–S9）；本会话 `/dev/kfd` 被拒，所有 GPU 运行验收需换非沙箱会话。
3. 现阶段未改动：`setup.py`、`CMakeLists.txt`、`vllm/utils/mem_utils.py`、`vllm/v1/worker/gpu_worker.py`。

## 6. 风险与回退

| 风险 | 缓解 | 回退 |
|---|---|---|
| fork 依赖 torch 2.11，DTK 26.04 只到 2.11（轮子存在） | S4 先用 `dcu-build.txt` 固定 DTK 轮子，不做跨栈混装 | 退回阶段 A 的 0.18.1+das 生产容器（不删镜像） |
| DTK clang 吃不下 fork 的 csrc | S5 逐文件试编，单文件定位；用 `-DCMAKE_HIP_FLAGS` 降级 | 只保留已通过文件，其余走 Triton/torch 回退 |
| 自编译 HIP 探针程序触发 hydcu 驱动死锁（本机已发生过一次，需重启） | **禁止在这台机执行自编译 HIP 二进制**；只用 `hipcc -c` 编译、或跑 torch 层探针 | 重启 + 用 `fix/install_reaper.sh` 兜底 |
| Triton 3.6 的 gfx906 支持只能靠补丁 | S6：先用 DAS triton 3.6.0 探针；失败则把归档补丁移植到 3.6.0 | 复用生产容器里已编译好的 triton |
| 改动泄漏到 ROCm 路径 | A7 门禁 + 代码审查 | 单文件回滚 |

## 7. 明确不做

- 不改 `on_gfx906()` / `on_cdna()` / `on_gfx9()` 的语义与调用点。
- 不为 gfx926/gfx928 增加任何路径。
- 不替换 DTK 的 RCCL / rocBLAS / hipBLASLt / triton 后端 / `/opt/hyhal`。
- 不引入新 CLI 参数（复用 `--kv-cache-memory-bytes`、`--enforce-eager`）。
- 不启用 FP8 / aiter / skinny GEMM。
- 不在这台机运行自编译 HIP 二进制。
