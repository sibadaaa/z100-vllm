# 更正：估算用错了基线（v2 投影作废）

> 起因：用户指出"这个数据目前比不过我不使用 wmma 的版本"。
> **结论：用户是对的。** [`z100-mma-plan-projection.md`](z100-mma-plan-projection.md) 里的 decode 估算
> （保守 9.6 / 预期 11.5 / 乐观 15.2 tok/s）**全部作废**——它算的是另一套配置。

---

## 1. 错在哪

我用了 `/home/lyh/server/优化方案-性能路线图.md` 的基线：**Qwen3.8-27B-Channel-INT8-w8a8，无投机解码，8.2 tok/s**。
而实际在跑的、并且是用户对比对象的，是本仓库的 **Qwen3.8-27B-FP8 + DFlash2 k=7**：

| 臂 | 栈 | step p50 | 接受长度 | 有效 ms/token | **tok/s** |
|---|---|---:|---:|---:|---:|
| **B1**（冻结） | rocm101 **docker**，无 w8a16 | 192.2 ms | 5.29 | 36.3 | **27.5** |
| **E2**（生产候选） | rocm101 **host**，W8A16=1 | 240.4 ms | 5.36 | 44.9 | **22.3** |
| 路线图基线（我误用的） | DTK host，**INT8，无投机** | 121.6 ms/token | — | 121.6 | **8.2** |

**我拿 8.2 tok/s 的栈去做优化，然后宣称"上限 15.7 tok/s"——而用户现在的版本已经是 22.3–27.5 tok/s。**
这不需要讨论方案，是基线选错了。

## 2. 更根本的错误：忽略了投机解码的乘数

投机解码下，**每输出 token 的成本 = step_ms / 接受长度**：

```text
22.3 tok/s = 240.4 ms / 5.36
27.5 tok/s = 192.2 ms / 5.29
```

所以：
- 任何内核级 **1.3×** 的改进，都会被 **5.3× 的接受长度**放大/缩小到几乎看不见——**它作用在分子，而用户已经拿走了分母的 5.3 倍**。
- 我在 projection §2.2 写的"地板 48–59 ms ⇒ 上限 17–21 tok/s"，**只对无投机栈成立**；
  在有投机的栈上，B1 实测 36.3 ms/token 就已经低于那个"地板"了。
- 因此 **"32 tok/s 一定做不到"是错的，撤回。** 32 tok/s = 31.25 ms/token，需要 `step ≤ 31.25 × acc`：

| 接受长度 | 需要的 step |
|---:|---:|
| 5.29（B1 实测） | **≤ 165 ms** |
| 5.36（E2 实测） | ≤ 168 ms |
| 6.0 | ≤ 188 ms |
| 6.5 | ≤ 203 ms |

B1 已经 192 ms，**只需再降 14% 就到 32 tok/s**；CUDA Graph 一项在这台机器上就实测过 −7~9%。

## 3. 更正后的 decode 投影（FP8 + DFlash2 栈）

| 阶段 | step ms | acc | ms/token | tok/s | 依据 |
|---|---:|---:|---:|---:|---|
| 当前 E2 | 240.4 | 5.36 | 44.9 | **22.3** | 【实测】 |
| ① 恢复到 B1 栈水平 | 192.2 | 5.29 | 36.3 | **27.5** | 【实测，同一代码不同栈】 |
| ② + CUDA Graph（路线 A） | 175–179 | 5.3 | 33–34 | **29.5–30.3** | 【实测 −7~9% 外推】 |
| ③ + rocBLAS dtype/形状修正 + lm_head int8 + 长尾 | 150–160 | 5.3 | 28–30 | **33–36** | 【推算】 |
| ④ + 接受长度 6.0–6.5（长上下文不塌） | 160 | 6.0–6.5 | 24.6–26.7 | **37–41** | 【推算，乘数效应】 |

**关键变化：最大的一项不是任何内核，而是 240.4 → 192.2 这 48 ms（−20%，值 +5.2 tok/s）。**

## 4. 那 48 ms 到底是什么

`z100-rocm101-perf-verdict.md` 已经给了判读：
> "decode 主因：不是 W8A16（E1/E3 关掉没改善）、不是 S23 后调优缺失（merge 已带入）、
> 不是 O2/attention BLOCK_M（E4 只 −2.0%）。**剩余主因指向 host rocm101 栈本身**：
> B1 同代码跑在 docker 上是 192.2 ms，host 栈上（E1–E4 全部）236–270 ms。"

但**尚未定案**，因为 B1 与 E1–E4 还差三个变量：

| 变量 | B1 | E1–E4 |
|---|---|---|
| 运行时 | docker（镜像 `z100-rocm101-vllm:20261023`） | host venv |
| `MAX_NUM_SEQS` | 128 | 4 |
| `--enable-prefix-caching` | 开 | 关（A/B 要求） |

> **所以"恢复 48 ms"仍是假设，不是结论。** 隔离这三项是本方案**唯一应该立刻做的实验**：
> 在 host 栈上用 `MAX_NUM_SEQS=128` + 开前缀缓存重跑一次；再在 docker 里用 `MAX_NUM_SEQS=4` 重跑一次。
> 两次跑完就能把"48 ms 归因于栈"还是"归因于并发/缓存配置"钉死。
> 若是后者，那 48 ms 是免费的；若是前者，就要抓 kernel trace 比 docker 与 host 的同一 kernel。

## 5. 这对 MMA / WMMA 方案意味着什么：**进一步降级**

在 FP8 栈上，设备时间构成是（kernel report 512c1）：

```text
rocBLAS aten::mm    47.2%   ← 6.0 ms/次，"只与小 M GEMM 相容"
GDN                25.8%
fp8 GEMV            4.3%   ← dot2/dot8 能改的就是这一块
comm                4.0%
attention           1.4%
```

- **dot2/dot4/dot8 直接能加速的只有那 4.3%**（fp8 GEMV）。即使 2× 也只值 ~2% 的 step。
- 占 47.2% 的 rocBLAS 是 **dtype 和形状派发问题**：gfx906 无 bf16 指令（bf16 GEMM 实测 3.42 TF/s，是 fp16 的 1/5.7），
  而 `--dtype float16` 下仍有大量 `aten::mm` 走 Tensile 瘦 tile。
  **修这个是改派发/配方，不是写新 GEMM。**
- 大 M 的 rocBLAS 已经跑到 16.5–17.7 TF/s（fp16 峰值的 67–72%），**自研 dot2 GEMM 去追 85% 是投入产出最差的方向**。

**修正后的优先级（FP8 + DFlash2 栈）：**

| 序 | 项 | 值（tok/s） | 人日 | 性质 |
|---|---|---:|---:|---|
| 1 | **隔离并修复 240→192 的 48 ms** | **+5.2** | 2–3 | 诊断/配置，**零新内核** |
| 2 | **CUDA Graph 路线 A 上生产** | +2~3 | 2 | 已有实测，只差门禁 |
| 3 | **rocBLAS 47% 的 dtype/形状审计** | +3~5 | 3 | 派发修正 |
| 4 | **长上下文接受率**（8k 现塌到 2.0/14.3%） | 乘数 | 3–5 | 投机解码策略 |
| 5 | 长尾融合（elementwise/quant/norm） | +1~2 | 4–6 | 新内核 |
| 6 | int4 权重（dot8） | +1 | 3–5 | 新内核，精度风险 |
| 7 | WMMA 兼容层 | **0** | 4+ | 保险，不做 |

> 注：这里的 "+x tok/s" 是**按 22.3 的基线**算的绝对值，不是相对百分比。

## 6. 仍然成立的部分

- dot8 的实测结论（2× dot4、9.1× fma、i4/u4 语义）不受影响，仍然成立；只是它的**优先级从 P1 降到 P2**。
- prefill 的估算（2.768 → 1.7–2.0 ms/token）针对的是 INT8 栈，**对 FP8 栈不适用**；
  FP8 栈的 prefill 是 5.32 ms/token（2722 ms / 512），瓶颈是 fp8-emu GEMM 与 rocBLAS 形状，另有其账。
- "融合长尾 20–30 ms 偏低"的修正仍然成立。
