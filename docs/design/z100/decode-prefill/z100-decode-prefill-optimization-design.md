## 0. 三十秒看懂

1. **目标不是"重构"，是把 7 个已经定位的漏点按证据强度排序吃掉。** 其中 2 个零代码、
   1 个已在树上只差部署、3 个需要改代码、1 个需要先做阻塞修复。
2. **顺序不可倒**：129 ms 的 decode step **从未被 profile 过**（PROJ §10.3①），
   所有"每项能回收多少"都来自一个 240.9 ms 的旧 step。所以第一阶段不是优化，是**建测量基座**。
3. **一条铁律**：任何一个数字进报告，必须带 `{树 SHA, env 全集, prompt 长度, 上下文, 采集命令}`。
   本会话已经因为缺这条在"167 vs 129 ms"上翻车两次（PROJ §2、§10.2）。

**目标数字（全部为 7469-token prompt、c=1、greedy）**

| 指标 | 现状（B0） | Must | Target | Stretch |
|---|---:|---:|---:|---:|
| decode tok/s @7469 | **22.0** | ≥23.7 | **28.2** | 29–38 |
| decode tok/s @512 | 34.7 | ≥37.4 | **44.5** | — |
| step ms @7469 | 129 | ≤120 | **~100** | ~80 |
| TTFT @7469 | 8.89 s | ≤8.65 s | **7.23–7.94 s** | — |
| TTFT @512 | 1.13 s | ≤1.10 s | **1.02–1.07 s** | — |
| prefill t/s @7469 | 839.8 | ≥866 | **940–1030** | 1452（SOL） |

> `@512` 的现状是 PROJ §6.4 的双锚点拟合值（559 ms + 1.1160 ms/token），
> **不是直接实测**；BUILD 的 P0-a 会先把它钉成实测值。若 P0-a 结果与本表差 >5%，以实测为准。

## 1. 七条杠杆与证据等级

证据等级只有三档，**任何 agent 不得把【推断】当【实测】写进结论**：

- **【实测】** 有本机日志/探针产物可复算；
- **【先测】** 有本仓历史 A/B，但不是当前配方；
- **【推断】** 由实测推导，必须写明依赖的假设。

| # | 杠杆 | 证据 | 预期收益 | 依赖 |
|---|---|---|---|---|
| **L1** | 图模式路线 A（去 `--enforce-eager` + `cudagraph_mode=piecewise`） | 【实测】step 127.5→**118.4 ms**（−7.1%）、c=4 聚合 48.4→51.6、TTFT 1.38→1.35 s、8/8 逐 token 一致 | step ×0.929 | 代码已在树 `f5083195e`，只差部署 |
| **L2** | `VLLM_DCU_FP8_GEMV_MAX_M=1`（verify 形状 M=8 改走平坦 GEMM） | 【先测】GEMM 在 M=1..8 平坦（0.5884→0.5900 ms，0.3%）；GEMV 在 M=8 = **7.38×**；端到端**从未跑过** | 未知，可能全表最大单项 | 零代码 |
| **L3** | TP allreduce（占 step 15–18%） | 【推断】260 µs × 128–143 次/步 | 19–24 ms | 需五相位 profile 定位 |
| **L4** | rocBLAS 非量化 GEMM（草稿塔 + lm_head，占 15.3%） | 【推断】旧 step 里 36.9 ms | ~35 ms | 同上 |
| **L5** | 长上下文接受长度（2.84 vs 短上下文 5.82） | 【实测】两档相差 2.05× | 最多 2.05× | 需先判"长度"还是"内容"；LABD 是唯一机制，但有三个阻塞 |
| **L6** | 337 ms / chunk 边界（MBT 8192 vs 2048 差 1012 ms） | 【实测】 | TTFT + 并发 | 根因待定 |
| **L7** | rocBLAS fp16 形状（prefill 57.8% SOL） | 【实测+推断】 | prefill +13~25% | 需 rocBLAS 形状/库路径审计 |
| **L8** | 策略指纹（20 个 `VLLM_DCU_*` 开关的可追溯化） | 不是性能项 | 0 | — |

**被否掉的方案**（PROJ §8、§10.2，不要重新提）：

- **重写 GEMV 内核** → L2 用一条已有的平坦路径就能拿到同样的量级，先测再谈重写。
- **`k` 从 7 加到 8** → 8 行就是一个 verify 组的上界，第 9 行要第二组，step 直接跳。
- **grouped verify / split-K** → Z100 是 GQA+TP4，每 step KV 只读 29–117 MB，上限占 step 的 0.2–0.9%。
- **MMA / WMMA** → gfx906 无 `v_mfma_*` / `v_wmma_*`（汇编探针实测）。

## 2. 为什么顺序不能倒

三个事实叠在一起，决定了流水线只能是"测量基座 → 单点实测 → 回收"：

1. **PROJ §10.1 的校准**：1Cat 在 4×V100 上 18.6 ms/round；我们 129 ms/step。
   把权重精度差（NVFP4 vs FP8）扣掉，归一化是 **5.51 vs 19.11 ms/GB ⇒ 栈差 3.47×**。
   ⇒ 说明 129 ms 不是硬件天花板，但**它指不出具体是哪一项**。
2. **PROJ §10.3①**：现有每项分解（GDN 97.9 / GEMV 46.1 / AR 37–43 / rocBLAS 36.9）
   全部来自一个 **240.9 ms** 的 step，而且那个 step 跑的是被削过的配方。
   把它们按比例缩到 129 ms 得不出结论——GDN 那 97.9 ms 大概率已经被吃掉了。
3. **PROJ §11.4**：`GEMV_MAX_M=1` 这一项有算子级 7.38× 的实测，
   **端到端从未跑过**。它一项就可能改变整个优先级排序。

⇒ 因此 **P0 全部是零代码 A/B**，P1 是部署一个已实测项 + 建 profile，
P2 之后才允许写内核。

## 3. 三条工作流

```
W1 测量基座（不改产品代码）
 ├─ P0-a 基线冻结（7469c1 / 512c1 / 709c1 / 8k1）
 ├─ P0-b GEMV 派发 A/B
 ├─ P0-c 纯 n-gram 接受长度上限
 └─ P1-b 五相位 round profile   ← 后面所有回收的量纲都出自这里
        │
        ├──────────────► W2 decode 回收                       ──► 28.2 tok/s
        │                 ├─ P1-a 图路线 A（已实测）
        │                 ├─ P2  按 P1-b 的实测分配做 L3/L4
        │                 └─ P2' LABD/q16（仅当 P0-b、P0-c 都为正）
        │
        └──────────────► W3 prefill + 排队行为                 ──► 940–1030 t/s
                           ├─ P3 337 ms/chunk 边界
                           └─ P4 rocBLAS fp16 形状审计
```

**W1 必须先行，且 W1 的任何产物不得修改 `vllm/` 下任何文件**（诊断扰动被测路径，PROJ §10.5④）。

## 4. 关键设计决策

### D1 —— 先做零代码 A/B，再做代码
理由：L2 的算子级收益（7.38×）大于 L1 的实测收益（−7.1%），而 L2 的代价是**一个环境变量**。
若先做代码，等于用一个可能被低估的基线去校准收益（PROJ §10.1 的教训）。
**否决**"先把图路线 A 落地上生产再测别的"——那会把 L1 和 L2 混在一起，之后再也拆不开。

### D2 —— L2 用"改派发"，不用"重写内核"
`vllm/model_executor/kernels/linear/scaled_mm/gfx906_fp8.py:82-83` 已有
`_GEMV_MS_MAX=8` 的编译期上限与 `_GEMV_MAX_M` 的 env 通道。
`docs/archive/result/z100-18c-gemm-dispatch-m-flat-result.md` 已测出"GEMV 线性、GEMM 平坦"。
⇒ 设计上把 L2 定为**派发策略问题**，不是 kernel 问题。
**约束**：`_GEMV_MS_MAX=8` 是编译期常量（`kMsMax`），所以**不能**用 `=16` 绕过去；
本设计的 q16 路线不依赖 GEMV 支持 M=16。

### D3 —— q16 的三个阻塞必须一起修，缺一即静默变慢
PROJ §11.3 的三个阻塞是**互相独立的三种失效**，任何一个不修，q16 都会"能跑但更慢"：

| 阻塞 | 位置 | 不修的症状 |
|---|---|---|
| B1 attention 把 16 行判成 prefill | `triton_unified_attention.py:67` `GFX906_VERIFY_MAX_QUERY_LEN = 8` | verify 掉出 split-KV，退回 2D 单 CTA |
| B2 M=16 踩中物化阈值 | `gfx906_fp16_prefill.py:132` `_FORCE_MIN_M = 16`、`:73` `_ROLE_MIN_M` 有 5 个角色是 16 | 每层权重当步 dequant + rocBLAS |
| B3 验证宽度 ≡ draft 宽度 | `dflash/speculator.py:71` `num_query_per_req = 1 + num_speculative_steps`；本树无 `draft_block` 符号 | 形状直接对不上，或 draft 批次吃掉 prefill 预算 |

⇒ 设计上把 q16 定为**一个原子工作包**，三个改动同一个 PR，共享一个验收门（G6）。
**否决**"先只改 B3 试试能不能跑"——B1/B2 的失效都是**性能**失效，不报错，测不出来就会被当成"q16 没用"。

### D4 —— 接受长度先量测，禁止先写代码
两个零成本量测已经足够判死或立项：

1. **纯 n-gram 上限**：本树 `method=ngram_gpu` 已可选（`vllm/config/speculative.py:67,1184,1962`），
   直接在真机上量这条 7469 prompt。LABD 的收益不可能超过这个上限。
2. **上下文扫描**：同一 prompt 截到 1K/2K/4K/8K，看接受长度是"随长度单调下降"还是"只看这一个点"。

⇒ 判读门槛：纯 n-gram 接受长度 **≥2 才立项 LABD**，≤1 直接砍。
**否决**"先移植 1Cat 的 `lookup.py` 再测"——那是 4–7 天的工作量去验证一个 30 分钟就能量的问题。

### D5 —— prefill 只动 rocBLAS，不动 attention / GDN
prefill 已经到 SOL 的 **57.8%**（839.8 / 1452 t/s），而且是**单 chunk**（7469 < MBT 8192），
GDN chunked 已经在生产脚本里（`serve_host_dflash2.sh:112`）。
⇒ 剩下的 42% 里，attention 只占 <1%（因果 attention 的 token-pair 数在单 chunk 下是 n²/2，
折算到 GEMM 的 100.8 TFLOP/rank 上是 0.9%）。
**否决**"顺手把 prefill attention 也优化一下"——那是把 0.9% 当成 40% 来做。

### D6 —— 测量单位改成 1Cat 的五相位 round + 策略指纹
1Cat 每份报告都给 `draft / draft→target / target / target→draft / complete round` 五个数。
我们只有一个 129 ms 的黑箱。同时有 ~20 个 `VLLM_DCU_*` 开关散在 env 与启动脚本里。
⇒ 五相位的定义 + 一个启动即打印的策略指纹，统一在 W1 里落地，之后所有 A/B 引用指纹。

## 5. 契约与不变量（所有 agent 必须遵守）

**C1 数值**：任何改动后，8 条固定 prompt 的 32-token greedy 输出必须**逐 token 一致**。
不一致即为 correctness bug，不论性能。

**C2 不退化**：任何 decode 改动必须在 **1K / 2K / 4K / 8K 四档上下文**都不退化（1Cat 门禁式）。
任何 prefill 改动必须在 **512 / 709 / 2048 / 7469** 四档都不退化。

**C3 单变量**：一次 A/B 只准改一个变量。env 全集必须逐字钉死并写进报告。

**C4 出处**：报告里的每个数带 `{SHA, env, prompt_len, ctx, 命令}`；每个论断带
`【实测】/【先测】/【推断】`，【推断】必须写出依赖的假设。

**C5 诊断隔离**：任何诊断核默认关、零分配、不得进被测量路径。

**C6 唯一属主**：一个文件同一时间只有一个 agent 改。任务板的 `属主` 列是硬约束。

## 6. 门禁设计

分两类：**阶段门**（做完才能进下一阶段）与**全局门**（每个 PR 都要过）。

| 门 | 类型 | 内容 | 不通过的动作 |
|---|---|---|---|
| **G0** | 全局 | 栈身份：`stack_identity --expect <树>` exit 0 | 停，先修栈 |
| **G1** | 全局 | C1 的 8 条 greedy 逐 token 一致 | 回滚该改动 |
| **G2** | 全局 | 静态：`pre-commit run` + 相关 pytest 全绿 | 不合入 |
| **G3** | 全局 | 策略指纹可打印且与报告一致 | 补，不算通过 |
| **G4** | 阶段 | P0 三臂（基线冻结 / GEMV 派发 / n-gram 上限）全部有完整 summary | 不进 P1 |
| **G5** | 阶段 | 五相位 profile 产出，且五项之和与 step p50 差 <5% | 不进 P2 |
| **G6** | 阶段 | q16 原子包：B1/B2/B3 三项各自有单变量证据 | 不进 P2' |
| **G7** | 阶段 | C2 的四档上下文全测，无退化 | 不进生产 |
| **G8** | 阶段 | 2 次重启 + 15 min c1/c4 soak，0 crash / OOM / NaN | 不进生产 |
| **G9** | 阶段 | 回滚演练通过 | 不进生产 |

**统计口径**（沿用 PROJ §1）：每组 repeat 2；两臂 p50 差 <5% 且区间重叠 → 判**不可判定**；
只有不可判定或与信任基线矛盾时，才**只重跑该臂一次**，不整套重跑。

## 7. 风险与回滚

| 风险 | 概率 | 影响 | 处置 |
|---|---|---|---|
| 图路线 A 冷启动 99 s → 7.4 min、宿主 RAM 21→34 GiB、KV −8% | **确定** | 运维 | 生产切图前必须先扩 swap 到 ≥16 GiB 并演练一次冷启动 |
| L2 在 W8A16 路径上不成立（S18 是 W8A8 测的） | 中 | 高 | P0-b 即判据；不成立则 L3/L4 权重上调 |
| q16 三个阻塞修完仍无收益 | 中 | 中 | G6 前不许写正式代码；G6 后一次性评估，停止线写死 |
| 337 ms/chunk 根因是 GDN 前缀重算，需要改 GDN | 中 | 中 | 先出根因报告再立项；不改则 MBT 8192 兜底 |
| 配方漂移（曾有被削过的配方冒充生产） | **高** | 高 | G3 策略指纹 + C3 |

**回滚**（每个工作包都必须能一键回）：
- L1：把 `--enforce-eager` 加回去 + 删 `--compilation-config`，即回到 B0。
- L2：`VLLM_DCU_FP8_GEMV_MAX_M` 回 8（本身是 env）。
- L3/L4：按工作包各自的 env / 开关回退。
- B1/B2/B3：三项各自独立可回（改常量 → 回常量）。
- 二进制（`.so`）：改前先备份，回滚脚本见 BUILD §9.3。

## 8. 不做清单

| 项 | 理由 |
|---|---|
| 重写 W8A16 GEMV 内核 | 先测 L2；若 L2 不成立，再按 P1-b 的实测分配决定 |
| `k=8`（神经 draft 加宽） | 8 行是 verify 组上界，第 9 行要第二组 |
| grouped verify / split-K | KV 占比 0.2–0.9%（PROJ §10.2②） |
| MMA / WMMA 移植 | gfx906 无对应指令 |
| 学 1Cat 的 mixed-batch decode | 有静默损坏先例，c=1 场景零收益 |
| 在 129 ms step 上用 240.9 ms 的分解做回收估算 | C4：那会变成【推断】冒充实测 |
| `VLLM_DCU_FP8_GEMV_MAX_M=16` | `_GEMV_MS_MAX=8` 是编译期上限，会被静默截到 8；靠它上 q16 是错的 |
