## 一页速览

**平台**：4 × 海光 Z100（`gfx906`，各 32 GB HBM）· **无 MFMA、无 fp8 指令、无 bf16 运算指令** · 宿主 31 GB RAM（关键约束）· DTK 26.04 · torch 2.11 + 自建 triton 3.6 · 容器 `z100-vllm`（bridge 网络、`RestartPolicy=no`）· 宿主内核 `iommu=pt` + `pci=disable_acs_redir=`（12 桥）

**关键成果**

|---|---|---|---|

**怎么读**：只看结论 → 本页；要复现/接手 → 第二、三、五章；要排查"能不能做" → 第四章问题清单（⛔ 结构性 / 🔶 有绕法 / ✅ 已修或已裁定）。

## 二、自研 HIP 算子：方法学与四族算子

### 1. 方法学：从 ISA 探针到归档的五步闭环

Z100（`gfx906`）上"能不能写算子"不靠文档与经验，靠**探针**：先把 ISA 能力钉死，再按钉死的能力设计内核，最后用**机器码**证明内核真的走了那条指令。三族算子（INT8 `sdot4`、FP8 仿真、BF16/FP16 dense GEMV）与 block-scaled 扩展全部走同一条闭环。

| 步 | 做法 | 为什么需要 | 产物 / 出处 |
|---|---|---|---|
| ① ISA 探针 | `tools/dcu/isa_probe.sh` 输出**三列表**（汇编器接受性 / `__has_builtin` / codegen 实际发射），外加 gfx906 **基线断言** | 文档会过时、内建存在性 ≠ 硬件支持、"我觉得 clang 会发这条"是假象的唯一来源；三列表把"能写"降级成"能落码"，再降级成"真落码" | `tools/dcu/isa_probe.sh`；S11d §3.1–§3.3/§3.7；S11f §3.1 |
| ② 内核设计 | 按①结论选**唯一可依赖**的 MAC 指令与数据通路，形态照抄已在本硬件验证过的骨架 | 指令没得选，能动的只有阻塞方式、LDS 布局、scale 放哪里；选错指令 = 白写（`v_mad_mix_f32`、`v_dot4c_i32_i8`、`v_dot2_f32_bf16` 在 gfx906 上都不存在） | `docs/design/z100-11f-fp8-bf16-emu-kernels.md` §3；`csrc/rocm/{w8a8_sdot4,fp8_emu_gemm,bf16_emu_gemv}.cu` |
| ③ 宿主集成 | `csrc/rocm/**` → CMake `VLLM_ROCM_EXT_SRC` → `torch.ops._rocm_C` → Python 内核类 → 选核表第 0 位 + env 开关 + 回退 | 内核再快，进不了选核表就等于没有；"默认打开一个新数值路径"不可接受（会无感改输出），每个算子必须能一键回到原行为 | `CMakeLists.txt:1548`；`csrc/rocm/{ops.h,torch_bindings.cpp}`；`vllm/model_executor/kernels/linear/scaled_mm/gfx906_*.py`；`vllm/envs.py` |

| ⑤ 归档 | 每个数字带**原始命令 + 原始输出**，记录产物 `md5`、回滚件、未做项 | 算子的结论依赖具体二进制，不留 md5 与回滚件则"复现失败"无法归因；不留未做项，未验证的边界会被后来者当成已验证 | `docs/result/z100-{11e,11e2,11f,11k,11l}-*.md`，每档登记 md5 与"未做" |

三列表的结论只有三条判读（逐列细节不再展开）：

- **汇编器接受 ≠ 硬件支持**：`v_qsad_pk_u16_u8`（gfx10+ 指令）在 gfx900/gfx906 上也被接受 ⇒ LLVM 谓词宽松；用 gfx900/gfx1010 交叉验证才有区分度（`v_dot4/v_dot8/fma_mix` 有，QSAD 没有）。
- **内建存在 ≠ 本目标可用**：`sdot8/udot8` 报 1；真正解释全部观测的是 feature 门槛——**gfx906 有 dot1 + dot2 + dot7，没有 dot8**。
- **codegen 只证明发射，不证明语义**：S11d 20 项 `EMITTED=20 MISSING=0`、两套工具链（宿主 DTK 24.04.3/clang 15 与容器 DTK 26.04/clang 18）三张表逐字节一致，但位运算语义正确性只能靠端到端数值兜住（见坑 1、坑 3）。

门禁五层各抓不同失败：编译纪律（`strings <so> \| grep -oE "amdgcn-amd-amdhsa--gfx[0-9a-f]+"` 只含 `gfx906`）、单测（契约矩阵：scale 形式 / bias / 奇数形状 / 错误路径 / 门控与 `can_implement`）、数值 sweep（对 fp32 反量化参考逐 shape 而非抽样）、机器码（目标指令计数 + 禁止项 `v_mfma`/`v_cvt_f32_fp8`/`v_cvt_f32_bf16`/`v_dot2_f32_bf16` 必须为 0，**按 kernel 归因**）、开关回归（默认 OFF，关闭后回到 `TritonInt8ScaledMMLinearKernel`/`TritonFp8BlockScaledMMKernel`/rocBLAS）。归档口径本身也要复核：统一口径为 **53 条基线 MATCH**，但那是脚本硬编码标签，探针表实际条目为 32 `asm` + 7 `blt` + 13 `cgo` = 52 条；基线还会随工具链漂移（clang 18 把 `u16x2 - {0xc000,0xc000}` 规范化成 `v_pk_add_u16`，`v_pk_sub_u16` 不再发射，该行已重钉）。机器码直方图口径：`llvm-objcopy --dump-section .hip_fatbin` → 按 `__CLANG_OFFLOAD_BUNDLE__` 拆包 → `clang-offload-bundler -unbundle -targets=hipv4-amdgcn-amd-amdhsa--gfx906` → `llvm-objdump -d`（S11d §3.12；S11f §3.5）。

#### 2.1 INT8 W8A8 `sdot4`

**背景**：ROCM 的 INT8 选核表 `_POSSIBLE_INT8_KERNELS[ROCM] = [Aiter, Triton]` 在 gfx906 上全不可用（Aiter 要求 `compute_capability >= 90`；Triton 退化成 FMA 展开，实测 2.2 TFLOPS），表里没有任何 `sdot4`（S11d §3.5），而 `v_dot4_i32_i8` 是 gfx906 上唯一有生产硬件先例（前序工程 13–14 ms/token）的 INT8 指令。

- **decode（M ≤ 8）一 block 一输出列**，64 线程切 `K/4` 个 int32，`sdot4` int32 精确累加 + LDS 树形归约——不能用 `tl.dot`：最小 tile M=16，M=1 时 15/16 是掩码行（16× 算力浪费，S11d §3.6(2)）。
- **prefill（M > 8）** 用 `BM×BN` 寄存器 tile、`BK=32`（8 int32）双缓冲 global→寄存器→LDS；`cfg` 0 自动（M≤32→32×64，否则 64×64）、1..4 显式；K 非 4 的倍数则上层回落 Triton。
- **不要** `v_dot4c_i32_i8`（gfx906 缺 dot8 特性，汇编器直接拒绝）、**不要** `v_dot4_u32_u8`（W8A8 需有符号，且树内 0 次使用无先例）；`can_implement` 只要求 `input_symmetric`。

**3.9× 由三条独立证据链支撑（别只记一个数字）**：逐 shape ABBA kernel-only 63/63 组最差 ×1.022、中位 ×2.16、最好 ×22.61（N=1024 K=5120 M=1，decode 的 k/v_proj），`full` 口径（含 `scaled_int8_quant`）最差 ×1.148；27B W8A8 TP=2 端到端 **84.07/82.74 vs 329.05/320.30 ms/token = 3.91×/3.87×**；kernel 级占比 GPU busy **82.5 vs 320.5 ms/step**、304 次/step 的 int8 GEMV **52.68 vs 290.85 ms = 3.88×/5.52×**；S11l 重验收 decode **84.00 ms/token**（3.82×）、TTFT 2.234 ms/prefill-tok（1.32×）、conc8 33.12 tok/s（1.94×）（S11e §3.5；S11k §3.5.2/§3.6；S11l §3.4）。

**`custom_op` + Dynamo 的教训（本族最贵的一课）**：内核/接入/数值/逐 shape 性能全过，但 `VLLM_DCU_USE_INT8_SDOT4=1` 时 27B 在 `torch.compile` 阶段抛 `ConstraintViolationError`（`L['positions'].size()[1]` 被标成 dynamic 却特化成 2048）、150 s 内退出，`=0` 正常。三次对照后定位：去掉 Python 的 M 分支**仍崩**，同 kernel 类换成 `_triton_fallback` 则 173 s 编译通过 ⇒ 触发者是**裸 `TORCH_LIBRARY` op 调用点**——Dynamo 在那里给符号 token 维加 `Eq(dim, hint)` 守卫并 `set_replacement(..., range_refined_to_singleton)` 成常量，而 vLLM 标记该维 dynamic；**不是 Meta 缺失、不是分支选错**。修法：`torch.library.custom_op` + `register_fake` 声明输出 `(x_q.size(0), w.size(0))`，并把 GEMV/GEMM 的 M 分支搬进 opaque body（`@torch.compiler.disable` 可用但引入 1 次 graph break；`splitting_ops` 结构性无效，崩在 Dynamo 出图后的 `build_guards`；给已注册 C++ op 补 `register_fake` 被 torch 拒绝）。验证：vs 裸内核 18/18、vs `triton_scaled_mm` 126/126 逐位相同，`dynamic=True` 下 M=2048→M=1 复用同一张图、无 graph break，副作用是 `torch.compile` 更快（88.24 s vs 159 s）、KV 显存相同（11.53 GiB）。

**遗留与默认值**：逐 token 文本一致未达成——把 opaque op 的 body 换成与基线**完全相同**的 `triton_scaled_mm` 后 **8/8 prompt 照样翻转**、5 个早期分叉点与 `opaque(sdot4)` 完全重合且方向一致 ⇒ **H_graph 成立、H_kernel 否定**，16 个分叉点全部落在 ≤0.53 nat 的贴边决策上；1 ULP 输入扰动 → int8 code 变 20–120 个（5120 里）→ 输出变 2.2–3.3e-3，比不量化的 fp16 路径大 2–5×。**默认保持 OFF**（S11k 有意推翻 S11e 的"默认开"），生产显式 `VLLM_DCU_USE_INT8_SDOT4=1`；S11e2 并入族总开关 `VLLM_DCU_USE_GFX906_EMU`，显式单项值优先。

#### 2.2 FP8 W8A8 仿真（`ds_read_u16` LUT 加宽 + `v_dot2_f32_f16`）

**背景**：gfx906 **没有任何 fp8 指令**（`v_cvt_f32_fp8`/`v_cvt_pk_fp8_f32`/`v_cvt_pk_f32_fp8`/`v_cvt_f32_bf8` 全部 `not supported on this GPU`）、没有 fp8 MFMA、`torch._scaled_mm` 的 FP8 路径不支持，vLLM 里**所有** FP8 选核在 gfx906 上拒绝；唯一能跑的是纯 Triton 标量 `v_fmac_f32` 模拟，实测 **≈36× 慢**（4096³：304.2 ms vs fp16 8.4 ms，机器码 `v_fmac_f32_e32` 8160 条、`v_mfma`/`v_dot2_f32_f16`/`v_dot4_i32`/`v_pk_fma_f16`/`v_cvt_f32_fp8` 全 0，S08b）。硬约束：27B FP8 ≈ 27 GiB，fp16 副本 54 GiB 装不下 ⇒ 必须**边读边转**。

- **路线选 LUT 而非位运算**：e4m3 的次正规（`\|x\| < 2^-6 ≈ 0.0156`，per-channel scaled 权重里很常见）与 fp16 次正规指数不同，无法"移位 + 加偏置"一步映射，位运算路线必须再补逐 lane 修正；而 **256 项 fp16 LUT 对 e4m3fn 与 e5m2 的全部有限码无损**，一次 `ds_read_u16` 即得精确值（注意 `ds_read_b16` 在 gfx906 上**不存在**）。默认 `VLLM_DCU_FP8_CVT=lut`，位运算只留 A/B；LUT 由宿主侧按 dtype 构建（`functools.lru_cache` + 每设备缓存，512 B），`test_lut_is_lossless_for_every_code` 对全部 256 码逐条断言。
- **GEMV（M ≤ 8）**：一 block 一输出列、`nt=64` 线程跨 `K/4` dword 连续读 + LDS 树归约；**M ≥ 2 时把 A 的加宽提到循环外**（多一个 widen kernel + `M×K×2` 字节 scratch），因为每个 block 都要重读同一份 A，不提出去的话 M=8 时 LUT 访存是 dot2 的 **9 倍**。
- **GEMM（M > 8）**：`BM×BN` 寄存器 tile + `BK=32` 双缓冲 LDS，结构照搬 `w8a8_sdot4.cu`，只是 LDS tile 单元从 int32 字换成 fp16 对（1 dword = 2 lane = 1 条 dot2），staging 时用 LUT 把 fp8 加宽成 fp16 对。

**收益与边界**：`fp8_emu_gemm.cu` 明确"只乘一次 scale"、权重常驻 fp8 不展开；Python 侧只启用实测获胜形状（单 token 全 N；`bf16 + M=4 + 128 ≤ N ≤ 1024`），M ≥ 8 与 fp16 小 N 一律回落 rocBLAS（M=512 N=5120 为 0.84×、M=64 N=48 为 0.07×，均未启用）⇒ **没有引入任何已知回退形状**。

#### 2.3 BF16/FP16 dense decode GEMV：f32 路线 vs f16 重定标路线

**背景**：gfx906 没有任何 bf16 运算指令（转换/点积都不存在），且 decode 形状的**未量化**线性层两条快路都不可用——`ops.LLMM1`（skinny GEMM）因 MFMA 被排除出 gfx906 构建，`n <= 16` 的 Triton matmul 带 `not on_gfx9()`，只能落到 rocBLAS：`[1,5120] @ [17408,5120]` bf16 GEMV 仅 **235 GB/s**（HBM 的 24%），N=512 更差（**24 GB/s**）。

- **f32 路线（bf16 默认）**：每 lane `v_lshlrev_b32 16` 精确展宽 + `v_fma_f32`/`v_fmac_f32`，对**全部** bf16 取值精确（含次正规/零/inf），就是"bf16 权重 + fp32 累加"的硬件 MMA 数值口径。
- **f16 重定标（仅 A/B，`range_safe=False` 默认不开）**：`(s - 112<<7) << 3` 得到 fp16 位型（前提 `e8 ∈ [113,143]`）再走 dot2；fp16 指数窗口比 bf16 **窄约 30 个 binade**——`\|x\| < 2^-14` 冲零、`≥ 65536` 饱和，**零值的 `e8=0` 会静默回绕（实测零 lane → 2.0）**，σ~1e-3 的权重分布被冲掉约 **6%** 的信号（阈值是绝对的）；契约要求**两个操作数的每个 lane** 都在窗口内。fp16 输入则直接走 dot2（route 0 默认，无转换、精确）。
- **S11f §8.1 修掉一个真 bug**：`on_gfx9()` 在 gfx906 上恒 `False`，`n <= 16 and not on_gfx9()` 的 Triton 分支把本内核**全部**可用形状截走（派发不可达）；修好后换用引擎真正在用的 `triton_matmul` 作基线。

**收益**：`bf16 M=8 N=17408` 为 0.51×（内核落后 rocBLAS，**未启用**），唯一启用的 M>1 形状是 `bf16 M=4 N=512`（2.14×）；`N=512` 上 bf16 达 **5.71×**、`N=48` 为 **2.46×**（rocBLAS 小 N 极差）。修 bug 后对 `triton_matmul` 收益为 **emu/triton = 2.28–8.54×**（bf16 N=17408：0.271 ms @657 GB/s vs triton 0.908 ms @196 GB/s），全部误差 ≤ **0.39 ulp**。

#### 2.4 block-scaled（128×128）FP8 扩展（2026-10-11）

**动机**：端到端选用的 ModelScope `Qwen/Qwen3.8-27B-FP8` 就是 **block-scaled** 的（`activation_scheme: dynamic`、`fmt: e4m3`、`weight_block_size: [128,128]`，**407 个 scale 全部是 `weight_scale_inv`**，没有任何 per-tensor `weight_scale`）。per-tensor 内核按设计拒绝它 ⇒ 回落到 `TritonFp8BlockScaledMMKernel`（标量 `v_fmac_f32` 模拟）：模型能起、输出连贯，但 **TTFT 4969 ms / decode 1984.8 ms/token（0.50 tok/s）**，服务不可用。

```
out[m, n] = Σ_kb ( Σ_{k ∈ kb} a[m,k] · w[n,k] ) · a_s[m, kb] · w_s[n // block_n, kb]
```

**关键洞见**：标量乘法可以分配到线程局部部分和上再归约——

```
Σ_t Σ_kb p[t,kb]·s[kb]  ==  Σ_kb s[kb]·Σ_t p[t,kb]
```

⇒ 只需在**当前 K 块的累加器**上乘 scale，就**保住了原有的"一次归约树 / 一个寄存器 tile"结构**，不必先归约再乘 scale，也不必为每个 K 块开一遍归约。

- **GEMV `fp8_emu_gemv_block_kernel`**：**每线程独占整个 K 块**（`kb = t, t+nt, …`）而不是跨线程切 dword——一个 block 只碰一个 cache line（block_k 字节、每元素 1 字节），**scale 每 128 元素只取一次**而非每 dword 一次；`acc[m] += loc[m] * (a_s[m·nkb+kb]·wsv)`。
- **GEMM `fp8_emu_gemm_block_kernel`**：两个 tile——`blk[TM][TN]`（当前 K 窗口）+ `acc[TM][TN]`（已完成块），**在 128-K 边界折叠**（`fp8_gemm_fold_block_scale` 做 `acc[i][j] += blk[i][j]*sa*w_s[(col/block_n)*nkb+kb]; blk[i][j]=0`，折叠点 `((c+1) % cpb) == 0`，`cpb = block_k / 32`），epilogue 只做 cast + bias。
- **W 行 stride（padding）**：block 路径走 `process_fp8_weight_block_strategy` → `_maybe_pad_fp8_weight`（`VLLM_ROCM_FP8_PADDING` 默认开，K=5120 满足 `stride*1 % 512 == 0`），权重变成 `stride(0) = K + 256` 的**非连续**视图；内核按 `w_stride = w.stride(0)` 索引行并要求 `stride(1) == 1` 且 `w_stride % 4 == 0`。权重方向自适应：`apply_block_scaled_mm` 按 `B.shape[1] == K` 判定 `[N,K]`/`[K,N]`，两种都**零拷贝**，`stride(1) != 1` 时**明确报错**而不是偷偷 copy。

**结果与上线**：质量 4 prompt × 32 greedy token 下 2/4 逐位一致，另 2 条只在**最后 1–3 个 token**、`Δlogprob ≤ 0.32 nat` 处分叉（与该机型噪声底 0.1–0.6 nat 同量级），4 条输出全部连贯；生产槽位起在 **:8000**（`api-gateway` upstream，服务名沿用 `qwen3.8-27b`，脚本 `/mnt/game/port/serve_fp8_8000.sh`），实测 307 tok / 39.07 s（~127 ms/token），经 gateway :8080 鉴权通过，KV 18.55 GiB / 1,192,990 tokens（S11f §9.3/§9.4/§10）。**未做（明确登记）**：graph 模式端到端（只跑 `--enforce-eager`）、UE8M0/MXFP8/非 128 的 block 形状（内核通用但只测 128×128）、MTP/视觉塔/长上下文/TP=2、block GEMM 的 tile 重调优（沿用 per-tensor 的四组 cfg）。

### 2. block-scaled（128×128）FP8 内核

**动机**：官方 `Qwen/Qwen3.8-27B-FP8` 是 block-scaled（`weight_block_size:[128,128]`、407 个 `weight_scale_inv`），原内核按设计拒绝 ⇒ 回落 Triton 标量模拟（decode 1984.8 ms/token）。

**契约**：`out[m,n] = Σ_kb ( Σ_{k∈kb} a[m,k]·w[n,k] ) · a_s[m,kb] · w_s[n//128, kb]`。

**关键洞见**：标量乘法可分配到线程局部部分和再归约（`Σ_t Σ_kb p·s = Σ_kb s·Σ_t p`）⇒ 只在**当前 K 块**的累加器上乘 scale，原有"一次归约树 / 一个寄存器 tile"结构不变。GEMV 每线程独占整个 K 块（一个 cache line/块，scale 每 128 元素取一次）；GEMM 在 128-K 边界把 `blk` 折叠进 `acc`；**W 行 stride 必须支持**（`_maybe_pad_fp8_weight` 会 pad K，权重成非连续视图）。

**门禁**（产物 md5 `fbfd45edb00713594793151a3e9ca76a`）：单测 **41 passed**（新增 11 项 block）｜ISA **53/53**｜选核 ON→新内核、OFF→Triton｜机器码 106 kernel、dot2 **37254**、LUT **2184**、`v_mfma`/`v_cvt_f32_fp8` 全 0；`v_fmac_f32` 1258 条**全是 block 内核的 scale 折叠 FMA**，per-tensor 内核仍 0。

### 3. 端到端上线（官方 Qwen3.8-27B-FP8，TP=4）

模型 82 文件 / **30.89 GB 与 API 清单逐项一致**。两臂同配方只差开关：

| 臂 | 内核 | TTFT | decode |
|---|---|---|---|
| 对照 | `TritonFp8BlockScaledMMKernel` | 4969 ms | **1984.8 ms/token** |
| 本步 | `Gfx906Fp8BlockScaledMMLinearKernel` | 600 ms | **123.0 ms/token（8.1 tok/s）** |

⇒ **16.1×**；与生产 **INT8** eager/TP=4 的 126.83 ms/token 同档 ⇒ 剩余成本在 eager 与 GDN/attention，不在 FP8 GEMM。**质量**：4 prompt × 32 greedy token 中 2/4 逐位一致，另 2 条只在第 29/31 个 token 分叉、`max\|Δlogprob\| ≤ 0.32 nat`（本机噪声底 0.1–0.6 nat），输出全部连贯。**上线形态**：生产槽位 drop-in 起在 `:8000`（网关 upstream），服务名 `qwen3.8-27b`，KV 18.55 GiB / 1,192,990 tokens。

### 4. 卡间通信 P2P：四层结论

| 层 | 状态 | 关键证据 |
|---|---|---|
| PCIe ACS | ✅ 关键位已清 | 12 桥 `ACS_Ctl` 由 `0x001d` → **`0x0011`**（ReqRedir/CmpltRedir 清零，靠内核参数 `pci=disable_acs_redir=`，开机即生效）；`dcu-p2p-acs.service` 已禁用 |
| HIP peer access | ✅ 12/12 | `torch.cuda.can_device_access_peer` 全 YES |
| 跨卡 `copy_` | ✅ **28.27–28.40 GB/s** | 本卡基线 396 GB/s；非 P2P 时约 6.95 GB/s |
| `hipExtMallocWithFlags(Uncached, 0x3)` | ⛔ 不可用 | **`out of memory`**（4 KB 也失败、同卡 `Default` 成功 ⇒ 缺 uncached 内存池；`Finegrained`/`UncachedXdp` 同；`hipIpcGetMemHandle`/`hipHostMalloc` 正常） |
| RCCL 集合通信 | ⛔ 不用 P2P | **10 组开关 + `iommu=pt` 全部 `via P2P=0`**；`NCCL_SHM_DISABLE=1` 掉到 `via NET/Socket`（1 MiB 2247→16371 µs，慢 7.3×）⇒ SHM 是最优 |

**根因**：RCCL 的 `transport/p2p.cc → ncclP2pAllocateShareableBuffer` 与 vLLM custom-AR 都依赖该 flag（`nm -D librccl.so` 实证动态链接 `hipExtMallocWithFlags@HIP`）；与 ACS/IOMMU 无关（`iommu=pt` 重启实验已证伪该假设，见 S11f §10）。**命令**：`sudo python3 tools/dcu/dcu_p2p_acs.py show`、`docker exec z100-vllm bash -lc 'PYTHONPATH=/src HIP_VISIBLE_DEVICES=0,1,2,3 python tools/dcu/p2p_verify.py'`、`bash /mnt/game/port/verify_p2p_after_reboot.sh`。

**补充（PCIe 物理口径，用于判定"到底是不是 P2P"）**：4 张卡链路均为 **Gen4 x16（16 GT/s ×16 ≈ 31.5 GB/s 可用）**。据此可判定：torch 跨卡 `copy_` 的 28.3 GB/s = 链路带宽的 **90%**，而**任何"绕主机中转"的拷贝上限只有 ~15.75 GB/s**（同一份数据要在链路上走两趟）⇒ 28.3 GB/s **必然是直接 P2P**；它随 ACS redirect 位开关（S12：6.95 → 28.3 GB/s，4.1×），而这两个位只影响对端事务，正是佐证。**反例警告**：`hipMemcpyPeer`（即便 `hipDeviceEnablePeerAccess` 返回 rc=0）在本平台只有 **6.2–6.9 GB/s**，即走中转载而非 P2P —— 所以判"P2P 是否生效"要用 torch 跨卡 `copy_`（或内核里直接访问对端指针），**不要用 `hipMemcpyPeer`**（实测见 `tools/dcu/p2p_capability_probe.py`）。
