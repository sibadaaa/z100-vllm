**目标（按顺序）**：
1. **P1–P2 之后 decode 进入 150–200 ms/token 量级**（≈2× 收益）；
2. 继续 P3/P4 争取 **≤130 ms/token（回到基线量级）**；

### 1.1 实测归因（S11b 已完成，2026-10-09）——假设 #3/#6 被否定，P2 是唯一大杠杆

TP=2 / fp16 / 不用 `--enforce-eager` / `max-model-len 4096`：sync **383.24 ms/step**、profiled 386.58、**GPU busy 380.50 ms（rank0）**、1448 kernels/step（与 S9b 的 378.8–380.6 一致）。占比闭合 100%：

| 类别 | ms/step | % of GPU busy | 说明 |
|---|---|---|---|
| **gemm/int8** | **370.37** | **97.3%** | 其中 `scaled_mm_kernel` 单独 **346.98 ms = 91.2%**（304 call/step） |
| 其它 | 7.80 | 2.1% | nccl 5.67 ms 为主 |
| gdn+mamba | 1.48 | **0.4%** | 假设 #3（GDN 占大头）**被否定** |
| attention | 0.42 | 0.1% | — |
| norm+activation | 0.38 | 0.1% | — |
| sampling | 0.05 | 0.0% | — |
| **CPU 侧** | 12.78 | **3.3%** | 假设 #6（CPU 瓶颈）**被否定**；step 内 371.19 ms 是 `hipEventSynchronize` 纯等 GPU ⇒ **GPU 绑定** |

**门禁判定：GEMM 97.3% ≫ 45% → 只做 P2；GDN 0.4% ≪ 35% → 不做 P3；CPU 3.3% ≪ 30% → 不做 P5。**

**⚠️ 对 P2 立项理由的修正（重要）**：S11b 做了机器码普查——本树 triton 的 `scaled_mm_kernel` **已经在发 2048–6144 条 `v_dot4_i32_i8`、0 条 fp16 dot / MFMA**，所以原方案"W8A8 没吃到 dot4 指令"**不成立**。真正的大杠杆是 **tile 形状**：`triton_scaled_mm` 的启发式对 **M=1 取 `BLOCK_SIZE_M=64`**（缓存内核 `tt.dot = 64×256 * 256×64 → 64×64`），**63/64 是 padding 冗余**。346.98 ms 对应的有效算力只有 **70 GFLOP/s**、权重流 **38.8 GB/s（≈3.8% HBM 带宽）**，而访存下界是 **13.13 ms/token ⇒ 相差 26.4×**。

⇒ S11e 选 **M≤8 的 GEMV 形态**恰好消除这个 padding，**方向正确**；P2 的验收要**新增"消除 64× M padding"这条指标**，ABBA 覆盖 **M=1、N∈{17408, 8192, 7168, 5120, 48}**。若 GEMM 真能 ~10×，**decode 落点约 35–70 ms/token**（除 GEMM 外全部只有 2.7% = 10.2 ms）——**比本方案最初估的"1.3–1.5×"大得多，甚至优于生产基线 122.47**（该数字仍是推算，需 S11e 冻结树后实测确认）。

**当前默认 `VLLM_DCU_USE_INT8_SDOT4=OFF`**（安全兜底）；**生产/评测用 `=1` 显式开**。

### 1.5 S11m 终版结论（2026-10-09）：**修正 §1.3 的口径** + 启动瓶颈定位

**修正（重要）**：token 变体主要由**编译产物/cache 的 vintage** 决定，**不由 `VLLM_DCU_USE_INT8_SDOT4` 开关决定**：

| 对照 | 位置差异 | 说明 |
|---|---|---|
| 同开关、**不同 vintage**（Z2 vs S11l arm2，都是 `=0`） | **422/512** | vintage 是主因 |
| **同一会话**内 `=0` vs `=1` | **仅 2/512** | 开关本身几乎不改输出 |
| `=1` **热启动 3/3**（S2=S3=S4） | **0/512**（Δlogprob 4.8e-5） | 加载 AOT 产物是**确定的** |
| 填缓存那次**冷编译 vs 它自己的加载** | 318/490 | 冷≠暖 ⇒ 生产必须"先预热再服务" |

⇒ S11l 说的"`=1` 改变输出 428/512"**主要是 vintage 差异**，不是内核或开关造成的；**同会话内 `=1` 与 `=0` 只差 2/512**。这让上线口径大大简化：预热之后，`=1` 的输出是**逐位可复现**的，并且与 `=0` 几乎一致。

**启动瓶颈定位（新的 P5 输入）**：三相位实测 `=1` uncached **1663 s** → cache-hit **1553–1573 s**（编译 95.05→19.6 s）；`=0` 1804 → **1633 s**。**瓶颈是两轮 graph capture（23–24 min，占 init 92–95%）**，AOT 修复只省 78–90 s（`=1`）/142 s（`=0`）⇒ **AOT 修复的价值是"确定性"，不是启动速度**。想把重启压到分钟级，必须动**图捕获**（减少 capture size 档位 / 复用编译子图），这是 P5 的新目标。

**其他实用结论**：
- `-cc.inductor_compile_config.benchmark_combo_kernel=False` 生效但**换 AOT key**，且只能把冷/热差异从 8/8 prompt 降到 2/8（318/490 → 58/506），**不能消除 ⇒ 不推荐**；
- **`VLLM_LOGGING_LEVEL=DEBUG` 会打开 inductor asserts 从而换 AOT key** ⇒ 带缓存的机器上**不要用 DEBUG 起引擎**；
- `=1` 的 S9 七文件回归 **146 passed / 0 failed**（含 `test_qwen3_5_gdn.py` 20）。

**生产配置定稿（S11m §6.1）**：① 仓库默认 **OFF**；② 生产显式 **`VLLM_DCU_USE_INT8_SDOT4=1`**；③ 固定 `VLLM_CACHE_ROOT`；④ **先空缓存预热一次（写产物、抽签）再对外服务**，此后每次重启逐 token 可复现；⑤ 不加 `-cc` 开关、不加 DEBUG、不加 `FORCE_AOT_LOAD`。

## 2. P0：kernel 级剖析（必做，1–2 h）

在 27B TP=2（`--dtype float16`、不用 `--enforce-eager`、`max-model-len 4096` 以缩短启动）上：

1. 复用已有 torch.compile 缓存（`VLLM_CACHE_ROOT=/mnt/game/...`，S9/S9b 已生成多份）避免 29 min 冷编译；
2. `LLM.start_profile()` / `torch.profiler.profile(activities=[CUDA, CPU])` 包住 **32 个 decode step**（`ignore_eos=True`、greedy），导出 `key_averages().table(sort_by="cuda_time_total", row_limit=25)`；
3. 同时记录：每 step 的 CPU wall time、`--cudagraph-metrics` 的 replay 命中、GPU 利用率（`hy-smi`）；
4. 按类别聚合：`gemm/int8` / `gdn+mamba` / `attention(kernel_unified_attention*)` / `rms_norm+activation` / `sampling` / `other`。

**产出**：`docs/result/z100-11b-perf-profiling-result.md` 顶部一张"380 ms 花在哪"的表（每类 ms + 占比 + top kernel 名）。**已产出**（2026-10-09，见 §1.1；零重跑——从上一任遗留的 29.4 MB×2 原始 trace 抢救，并用自写 stdlib 脚本独立重算，与上一任输出逐项一致）。
**判据**：GEMM > 45% → 先做 P2；GDN > 35% → 先做 P3；CPU > 30% → 先做 P5。

## 3. P1：并行度与 32 GB 宿主的绕法

**事实（2026-10-09 S14 二次更正）**：27B 的 TP=4 曾在影子容器 `z100-s9`（`--memory=32g`+`MemSwap=32g`）启动 4 min 即 `oom_kill 1`。**但"真因 = cgroup 上限"已被内核原文推翻**：三次 OOM 全部是 `oom-kill:constraint=CONSTRAINT_NONE` + **`global_oom`** + `anon-rss ≈6.9–7.25 GB/worker` + **`file-rss:0kB`**；S14 在**无内存上限**容器（`HostConfig.Memory=0`、cgroup `memory.max=max`、峰值 `memory.current` 29.76 GB < 32 GiB）里跑 **graph 模式** TP=4 **照样 global OOM**。真因是 **graph 模式 TP=4 的宿主匿名需求 ≈34–35 GB ≥ 本机 32.0 GB RAM + 4.1 GB swap**（OOM 点在 `Available KV cache memory` 后约 5 s 的 warmup）。
**关键结论（S14 定稿）**：① **本机"能跑 TP=4"分两句**——**eager 可行**（`serve_27b_tp4.sh` 默认 `ENFORCE_EAGER=1`，190 s 就绪、`oom_kill` 零增量、decode **126.83** ms/token），**graph 默认配置不可行**（3 次 `global_oom`），**挂 16 GiB swap 后可行**（350 s、decode **49.66** ms/token）。② **2×2 矩阵**：eager 下 TP=4 比 TP=2 **慢 1.12×**（126.83 vs 113.51），graph 下 TP=4 比 TP=2 **快 1.70×**（49.66 vs 84.22）⇒ **"TP=4 更慢"是编译模式的口径错配，不是并行度的锅**；对生产 121.43：TP=4 graph **快 2.44×**、TP=2 graph 快 1.44×。③ **多出来的宿主内存不在图池、也不在 sdot4 权重重排**（图池 1.67→0.22 GiB 仍 OOM；`=0` 改走 `TritonInt8ScaledMMLinearKernel` 同档 OOM）⇒ 在**编译/切分执行路径**，这是 S14c 的靶子。④ **swap 只能桥接启动瞬时峰值**（权重在显存；启动期换出 7.78 GB staging/冷页，引擎一关回落 0.53 GB），**启动余量一度只剩 507 MB ⇒ 生产不宜照搬**。⑤ **新未决问题（S14b 已定性）**：同 TP 下 graph↔eager **实质改变 token 流**，但**退化成英文重复循环的是 graph 的 P2 臂**（eager 侧才连贯；噪声底仅 0.1–0.6 nat ⇒ 系统性）。**S14b 判定：以 B（可解释数值）为主** —— 真值锚（4B TP=1 + CPU HF）显示 eager 差真值 **0.0025 nat**、graph **0.0023 nat**、graph↔eager 仅 **0.054 nat**（编译模式本身只值 0.05 nat），27B 的 1–4 nat 来自**动态 per-token INT8 激活量化 × 64 层 GDN 递推**的放大，**不是算子被编坏**；**但 graph 另有"运行间不可复现"的坏 draw**（同配置/同 cache 重跑得到不同结果，唯一相关因子是 AOT 现场编译 vs 磁盘重载）⇒ **S14d**。**质量/精度参照 = eager**（逐位可复现、贴近真值）；**graph 的 token 流不得用于质量评测，性能结论不受影响**。

**绕法（按优先级，逐条实测后再下一条）**：

| # | 做法 | 为什么可行 | 风险/代价 |
|---|---|---|---|
| 1 | **在能装下的模型上测 TP 缩放**：`Qwen3.5-4B`(8.8 GB) 与 `Qwen3-0.6B` 跑 TP=1/2/4，得 decode/prefill 的 TP 缩放曲线与通信开销 | 4B 在 32 GB 内可 4 卡；缩放系数可谨慎外推到 27B（归档里必须标注"外推"） | 外推不等于实测；仅用于决策 |

## 4. P2：gfx906 专用 W8A8 INT8 GEMM（自编 HIP 算子的主战场）

**背景**：gfx906 有 `v_dot4_i32_i8`（`V_DOT4_I32_I8`），而本树 W8A8 走的是 Triton `triton_scaled_mm`（反量化到 fp16 再做 fp16 GEMM），没吃到这条指令。生产自研的 `int8_sdot4` 正是走它。

**方案（A→C 递进）**：

- **A. 先清点、先复用**：`csrc/quantization/**`、`csrc/rocm/**`、前序工程 `/home/lyh/server/gfx906_port/{artifacts,fix}/`（只读）里是否已有 gfx906 INT8 算子或补丁；有就用现有开关打开（例如 `VLLM_ROCM_USE_GFX906_*`），**改一行胜过写一千行**。
- **A2. 先做 exact-shape 战术表（§4C.1 的结论，优先于写通用 kernel）**：把 27B 的真实 decode shape（M=1..8 × 各 N/K）列出来，逐个做 **ABBA 全权重 A/B**，门槛是"**没有任何 shape 变慢**"；参考实现用这一招在单个 shape 上拿到 +5.04%（占用率 6.24%→11.51%），成本远低于重写通用 GEMM。
- **B. 直接迁移前序已验证的 `int8_sdot4` 算子（主路线，S11e）**：`/home/lyh/server/int8_sdot4/w8a8_sdot4_kernel.hip`（484 行，GEMV + tiled GEMM）+ `int8_sdot4_patch.py`（337 行注入层）**完整可用**；S11d 已独立复验其 device 码在 **DTK 26.04 / clang 18** 下编译通过并落 **777 条 `v_dot4_i32_i8`（0 条标量 FMA）**：
  - 形态（照抄它）：`__builtin_amdgcn_sdot4(..., false)`（**不要** `v_dot4c_i32_i8`，gfx906 拒绝）；**M≤8** = 每输出列一个 block、64 线程切 K/4 个 int32、int32 精确累加 + LDS 归约 + epilogue `acc * x_s * w_s (+bias)`；**M>32** = 64×64 tile + BK=32 双缓冲 LDS；
  - 前序实测 **22 TFLOPS vs Triton 2.2**（约 10×）；
  - 4 个注入锚点在本树**全在**（`vllm/model_executor/kernels/linear/__init__.py:411/418/794`、`scaled_mm/ScaledMMLinearKernel.py:190`）；
  - 接入：编进 `_C`/`_rocm_C`（CMake），`is_supported = on_gfx906()` 并插到 ROCM 表**第 0 位**（优先于 Triton），Triton 作回退；
  - **编译纪律**：`strings <so> | grep -oE "amdgcn-amd-amdhsa--gfx[0-9a-f]+"` 必须仍只含 gfx906；装进 canonical 副本并记录新旧 md5；**不落地独立可执行程序**；
  - **验收**：同 shape vs fp32 反量化参考 `rel_err ≤ 1e-2`（对齐 S8 口径）；profiler 里该 kernel 与 Triton 版本的时间对比；**新增"消除 64× M padding"这条指标**（见 §1.1：Triton 对 M=1 取 `BLOCK_SIZE_M=64`，63/64 是冗余；访存下界 13.13 ms/token vs 实测 346.98 ms）；ABBA 覆盖 **M=1、N∈{17408, 8192, 7168, 5120, 48}**；27B decode 端到端**必须更快**且文本一致；**逐 shape ABBA，"no shape regresses"**。
- **C. 若 A/B 都不达标**：评估 `torch._scaled_mm`/hipBLASLt 之外的替代（例如把 W8A8 换成 W4A16 走已跑通的 `Gfx906GPTQWNA16LinearKernel`），但要注意量化方案变更需要模型侧支持。

**预期**：单 token GEMM 时间减半左右；对应 decode 若 GEMM 占 50%，端到端 ≈1.3–1.5×。

## 4B. P6：用 FP16 模拟 FP8，让 FP8 量化在 Z100 上真正可用

**动机**：S8b 已证明 gfx906 上 block-scaled FP8 走的是 **`v_fmac_f32` 标量模拟**（4096³ 里 8160 条，`v_mfma`/`v_dot*`/fp8-cvt 全 0）→ 数值干净但 **36× 慢**；per-tensor/per-channel FP8 则直接被 `init_fp8_linear_kernel` 全否决。用户的方向是对的：**用 FP16 硬件去模拟 FP8**。

**原理**：e4m3/e5m2 **可以无损放进 fp16**（fp16 的指数位更宽、尾数 10 位 ≥ fp8 的 3 位），所以"FP8 反量化 → FP16 → 用 packed FP16 乘加（FP32 累加）"在数值上是可行的，而且 `v_dot2_f32_f16` / `v_mad_mix_f32` 这类指令的吞吐远高于 `v_fmac_f32` 标量模拟。

**关键设计约束**：
- **不要在内存里把 FP8 权重整体展开成 FP16**（27B FP8 → fp16 要 54 GB，会撞 32 GB 宿主内存）。正确做法是 **GEMM 内核里边读边转**：权重常驻 FP8（显存占用不变），在寄存器/SMEM 里转成 FP16 再乘加；
- scale 的施加顺序决定精度：block-scaled 走"块内 FP8×FP8 → int/fp32 累加 → epilogue 乘 `scale_a*scale_b`"，与 S8b 的参考实现（`native_w8a8_block_matmul`）对齐口径；
- 累加必须 **FP32**（`v_dot2_f32_f16` 天然满足），否则 FP8 的动态范围会放大误差。

**实施路线（二选一，按 S11d 的 codegen 结论定）**：
- **Triton 路线（已由 S11d 实测确认为可行，选它）**：`tl.dot(fp16, fp16) → fp32` 在 gfx906 上**满密度发 `v_dot2_f32_f16`**（7/7 形状，无 `v_fma_f32`/`v_mfma`），落点在 `vllm/model_executor/kernels/linear/scaled_mm/triton.py:163`；`fp8 → fp16 → tl.dot` 已实测**数值完全正确（误差 0.0）**；
- **P6 的首要工作不是"换指令"，而是"摊薄/替换 fp8→fp16 的软转换"**：实测该转换约 **400 条 ALU/选通**，压过了 128 条 dot（硬件 fp8 转换指令在 gfx906 上**不存在**）。三条可选做法：权重转换 hoist 到主循环外 / 用 `v_pk_lshlrev_b16`+`v_pk_add_u16` 的 packed 位运算做 e4m3→f16 / 用 256 项 LDS LUT；
- **HIP 路线（备选）**：点积指令同为 `v_dot2_f32_f16`（`__builtin_amdgcn_fdot2` / `__ockl_fdot2`），epilogue 可用 `v_fma_mix_f32`（无 clang 内建，需 inline asm）。
- 另注意：**Triton 的最小 tile 是 `M=16`**，m=1 decode 时 15/16 算力被掩码浪费 ⇒ FP8 的 decode 场景优先考虑走 P2 的 exact-shape GEMV 思路或 HIP 路线。

**验收**：
1. 数值：与 `native_w8a8_block_matmul` 参考的 `mean_rel_err` 不劣于 S8b 的 Triton 结果（1.465e-07 量级），且全 finite；
2. 性能：4096³ 从 **304 ms** 往 fp16 的 8.4 ms 方向靠（目标先做到 **≤30 ms，即 ≥10×**），profiler 里能看到 packed FP16 / dot 指令（**不能再是清一色 `v_fmac_f32`**）；
3. 端到端：一个真实 FP8 量化模型（本地有就用，没有则用 llm-compressor 离线把 `Qwen3-0.6B` 量化成 FP8 per-tensor / block-scaled）能起服务、文本与 fp16 基线一致（允许 FP8 固有精度差）；
4. KV cache FP8（`--kv-cache-dtype fp8`）在同一套原语上做精度/吞吐评估（先精度后性能）。

**范围说明**：FP8 不在阶段 A 的必测矩阵里（阶段 A 是 fp16 dense + INT8/W4A16），P6 属于"把 Z100 的算力用满"的扩展项，优先级排在 **P2 之后**、与 P3 并行可行。

## 4C. 参考实现：[1CatAI/1Cat-vLLM](https://github.com/1CatAI/1Cat-vLLM)（V100/SM70）——"老硬件模拟新量化格式"的成熟工程

**为什么看它**：V100/SM70 与 gfx906/Z100 的处境高度同构——都没有 FP8/FP4 张量核心，却都要支持现代低精度量化。1Cat-vLLM 把这件事当成**算子设计问题**（不是 loader 问题）来做，并且给出"量化格式 → 可用高性能服务路径"的完整证据链，正好是我们 P2/P6 需要的方法论与配方来源（Apache-2.0；任何适配过来的实现必须**保留出处与许可声明**）。

**要从它身上取的 7 件事**（S11g 逐条给 `file:line` + 原始证据）：

| # | 它的做法 | 对我们的映射 | 预期价值 |
|---|---|---|---|
| 1 | **FP8 E4M3/E5M2 只用于 KV 存储**，QK/PV 用 FP32 计算（明确写了"E4M3 修复需要 precision revision 4"） | gfx906 上 `--kv-cache-dtype fp8`：**KV 流量减半**，attention 里反量化到 fp16/fp32 再算 | 长上下文 decode 直接受益（KV 带宽是 decode 大头） |
| 2 | **NVFP4 / MXFP4 在无 FP4 硬件上跑**：`nvfp4_qpn2_sm70.cu:143-163` 先做 E2M1×8 纯位扩展，紧接着 `:188-193` 的 `mma.sync…f32.f16.f16.f32`；主循环里 `half2 weights[8]` 是**唯一** FP16 形态（`:255-268`）；**`process_weights_after_loading` 把 checkpoint 权重释放成空张量**（`vllm/model_executor/kernels/linear/nvfp4/sm70.py:154-166`）；Marlin 路线只把 **scale** 升 fp16、权重保持 packed int32（`marlin_utils_fp4.py:230-266`） | **这条直接就是 P6 的硬约束**：权重常驻 FP8 + 寄存器内 `v_cvt`/`v_dot2_f32_f16` + **FP32 累加**，**绝不物化 FP16 权重副本**（同时满足 32 GB 宿主内存）；scale 口径照 `nvfp4_qpn2_sm70.cu:113-128`「在 FP32 里乘、只 round 一次」 | 让 P6 的"≥10×"与 S8b 的数值口径**同时**成立 |

**§4C.1 三条结论性建议**（S11g 分析后 Lead 定调）：

1. **P2 的第一步改成"exact-shape 战术表"**：先按 27B 的真实 decode shape（M=1..8 × 各 N/K）做 ABBA 全权重 A/B，找出**最差的那几个 shape**，再决定是"逐 shape 特化"还是"写 `sdot4` 通用 kernel"；不要一上来就写通用 GEMM。
2. **P6 的形态已被参考实现钉死**：FP8 权重常驻 + 寄存器内转换 + `v_dot2_f32_f16`/packed FP16 + FP32 累加 + scale 只在 epilogue 乘一次；**"物化 FP16 权重"这条路明确禁止**（既有内存约束，也有参考实现的相反证据）。
3. **P5/诊断照抄第 6 条的硬门禁模式**：`z100_profiles` 分 `configured / loaded / fallback_reason` 三层，并用环境变量在"加速未生效"时**直接拒绝启动**，而不是打一行 warning。

## 5. P3：GDN / 线性注意力与 MTP

1. **核对 gfx906 专用 op 是否真在 27B decode 路径上生效**：fork 有 13 个 gfx906 专用算子（`csrc/mamba/gfx906_decode_kernels.cu`：packed recurrent decode、causal_conv1d、fused sigmoid gating、GDN MTP 等）。逐个确认 Python 侧调用条件、是否需要环境变量、profiler 里是否出现；
2. **确认生产是否开 MTP/投机解码**（若开，复现它是单项最大收益）；fork 侧 MTP 的 gfx906 kernel 走 `VLLM_DISPATCH_HALF_TYPES`（仅 fp16）→ 与应用 `--dtype float16` 一致，可试；

## 7. P5：CPU 侧与冷启动

- 编译期开关：`-O3`、`VLLM_ROCM_USE_*` 系列逐个 A/B（每次只改一个变量）。
