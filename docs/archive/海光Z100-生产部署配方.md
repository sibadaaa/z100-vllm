## 2. 启动配方(已定型部分)

### 2.1 容器要求
* **不得设 cgroup 内存上限**(`docker run --memory 0`,或 `HostConfig.Memory=0`)。有 32 GiB 上限的影子里 27B 起不来。
* 挂载:工作区(容器内 `/src`)、`/mnt/game`、`/opt/hyhal`。
* 权重目录:`/mnt/game/models/Qwen3.8-27B-Channel-INT8-w8a8`。

### 2.2 必须显式导出的环境变量(少一个都会出事)
```bash
. /opt/dtk/env.sh
. /src/tools/dcu/env.sh
export PYTHONPATH=/src:/mnt/game/triton-gfx906/install   # ← 自建 triton,缺了就编不出 gfx906
export VLLM_CACHE_ROOT=<固定目录,见 §3>                    # ← 必须固定,否则每次都是新 vintage
export TRITON_CACHE_DIR=/mnt/game/triton-gfx906/cache
export VLLM_WORKER_MULTIPROC_METHOD=spawn
export TOKENIZERS_PARALLELISM=false
export PYTORCH_HIP_ALLOC_CONF=expandable_segments:True
export HIP_VISIBLE_DEVICES=0,1[,2,3]                     # ← 永远显式;绝不要 unset(等于占满 4 卡)
export VLLM_DCU_USE_INT8_SDOT4=1                         # ← 仓库默认 OFF,生产必须显式开
export VLLM_LOGGING_LEVEL=INFO                           # ← 不要 DEBUG(会打开 inductor asserts 并换 AOT key)
export PYTHONUNBUFFERED=1
```

### 2.3 命令行
```bash
python -c 'import torch; from vllm.entrypoints.cli.main import main; main()' serve \
  /mnt/game/models/Qwen3.8-27B-Channel-INT8-w8a8 \
  --dtype float16 \
  --tensor-parallel-size <2|4> \
  --gpu-memory-utilization 0.85 \
  --disable-custom-all-reduce \
  --skip-mm-profiling \
  --enable-prefix-caching --mamba-cache-mode align \
  --max-model-len 262144 \
  --max-num-batched-tokens 2048 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml --reasoning-parser qwen3 \
  --enable-prompt-tokens-details \
  --override-generation-config '{"temperature":0.7,"repetition_penalty":1.05}' \
  --default-chat-template-kwargs '{"reasoning_effort":"low"}' \
  --served-model-name qwen3.8-27b --host 0.0.0.0 --port <PORT>
```
* **`--dtype float16`**:永远不要 `auto`。
* **不加** `-cc`(默认图配置)/ `--enforce-eager` / `FORCE_AOT_LOAD` / `VLLM_LOGGING_LEVEL=DEBUG`,除非你明确在跑某个已登记的实验臂。
* **agent 三件套不能省**(2026-10-10 实测):任何带 `tool_choice:"auto"` 的请求(DSH/pi-ai 就是)**没有** `--enable-auto-tool-choice --tool-call-parser` 会被 vLLM 以 **400** 拒绝:`"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set`。同时 `--reasoning-parser qwen3` 才能把思考内容与正文分开。
* **`--enable-prompt-tokens-details`**:否则即使前缀缓存真命中,响应 `usage.prompt_tokens_details` 恒为 `null`,DSH/pi-ai 界面会显示"缓存命中 0%"。
* **模板/采样兜底**(该模型 chat_template 默认 `reasoning_effort=xhigh`,易"只出 thinking/重复循环"):`--default-chat-template-kwargs '{"reasoning_effort":"low"}'` + `--override-generation-config '{"temperature":0.7,"repetition_penalty":1.05}'`。
* **服务专用参考实现(推荐直接用)**:[`tools/dcu/serve_z100_tp4.sh`](../tools/dcu/serve_z100_tp4.sh)——= 本节的 agent 参数 + 配置 C 的图配置,已实测可用(ready 351 s、`tool_choice:auto` → 200 且正确解析 `get_weather({"city":"北京"})`)。
* 基准口径参考:[`tools/dcu/s14_arm_env.sh`](../tools/dcu/s14_arm_env.sh)(S14 全部实测都出自它,**不带 agent 参数**)。
* **配置 C(TP=4 graph)的额外参数**:`-cc.cudagraph_mode=PIECEWISE --cudagraph-capture-sizes "1 2 4 8"`。
  **该图配置是 S14 为压图池试出来的,不是默认值**;S14c 已证"图池不是主因"(1.67→0.22 GiB 仍 OOM),所以它对内存**只是小头**,真正决定性的是 §5。
* ⚠️ **改过引擎参数后的第一次启动很重**:配置哈希变了 ⇒ AOT key 不同 ⇒ **现场编译**(实测 `torch.compile` 145 s),随后 profile/warmup 阶段在 31 GB 宿主上换页抖动,`available` 一度只剩 3 GB、swap 用掉 7.6 GiB,>9 min 未就绪;而**编译产物一旦落盘,重启即走 AOT 重载**(实测 ready **351 s**)。⇒ 换参数后**别急着判死**,若确需干预,**杀掉重启**比继续等更划算。

## 3. 缓存与 vintage 纪律(必须遵守,否则输出不确定)
1. **固定 `VLLM_CACHE_ROOT`**;仓库存量:`/mnt/game/vllm-cache-27b`。
2. **"先空缓存预热一次 → 再重启服务"仍然值得做,但它只保证"启动快",不保证"输出一致"**(⚠️ **2026-10-10 更正**):S11m 当年测到 `=1` 热启动 3/3 逐位一致(0/512),据此写过"预热后走磁盘重载即可复现";**S14e 已否证该结论** —— 同一 artifact、三次真 AOT 重载、启动完全同构(ready 1542/1542/1553 s),结果**落在 2 个离散变体**(G1b ≡ S11m 的 S2/S3/S4,G1a/G1c 差 403/512;6 跑一致率 **7/15≈47%**)。⇒ **预热的价值是时间**(`init engine` 183→87 s、ready 351→230 s),**不是确定性**;要输出可复现只能用 **eager**(见 §4.1)。
3. **AOT 重载还顺带把启动时间减半**:S14c 实测 `init engine` **183 → 87 s**、ready **351 → 230 s**(decode 不变,49.96 ms)。
4. **不推荐** `benchmark_combo_kernel=false`:它会换 AOT key(要重新预热),且只把冷/热差异从 8/8 降到 2/8。

## 4. 质量口径(做评测前必读)
* **质量/精度参照 = eager**(`CompilationMode.NONE`):逐位可复现(1024 token、8/8 flip、同引擎重复 **Δ=0.000**),未量化 4B 上与 CPU HF 真值差 **0.0025 nat**(S14b)。
* **graph 的 token 流不得用于任何质量/精度评测**。graph 与 eager 同上下文的差只有 **0.054 nat**(舍入级),但经**动态 per-token INT8 量化 × 64 层 GDN 递推**放大成 27B 上的 1–4 nat(尾部 10–12 nat),表现为近 tie 翻转。

### 4.1 ❌ 第二轮门禁:graph "运行间不可复现"(S14d 定稿,2026-10-10)—— **graph 不能用于任何依赖 token 流的用途**
* **E4 硬失败**:生产候选配方(TP=4 / maxlen 262144 / `PIECEWISE` + `1 2 4 8` / AOT 重载 / 附加 4 GiB swap / `swappiness=200`)下,"预热那次"(空 cache 现场编译,ready 352 s、`aot_load=0`)与服务那次(同 cache 重载,ready 230 s、**`aot_load=4`**)对 12 prompt 的 token 流 **12/12 不逐位一致**;同上下文(字节相同 context)`prompt_logprobs` **mean|Δ| 1.04–1.76 nat、最坏 12.67 nat**、argmax flips 9–28、差异覆盖 **91.6%** 的位置、首个分歧中位 ≈9 个生成 token(最早第 0)。
* **根因不是 H-AOT**:同一 cache 的第 2/3 次重载与第 1 次**同样 12/12 不一致**(mean 1.24–1.43 nat)⇒ "现场编译 ≠ 磁盘重载"被否证,真因子是 **graph 路径运行间不可复现**。**7 臂 / 21 对 / 252 个 prompt-pair 仅 6 个(2.4%)逐位一致**,21 对的 `mean|Δ|` 全落在 **1.24–1.45 nat** 窄带且与配置正交;关掉 `combo_kernels`/`benchmark_combo_kernel` **无收益(1/36)**。
* **与 TP 正交**:S14b 的 P2(`'The'`/4.750)vs A1r(`'用户'`/1.047)就是 **TP=2 上的答案级翻转** ⇒ **TP=2 graph 在 token 流上同样危险**。
* **S14e G1(04:37Z):"默认图配置"也救不回来**。在 S11m 的口径(TP=2 / maxlen 4096 / **默认 `FULL_AND_PIECEWISE`,51 capture sizes**)下,两次**真 AOT 重载**(同一 artifact,md5 `91176924…` = S11m 归档值;`aot_load=2`、`ind_hit=1`)仍然 **403/512 位置不同**(同上下文 `mean|Δ|` 1.03–1.15、`max` 7.92 nat、9/12 prompt 流不同);而**启动路径完全同构**(ready **1542 / 1542 s**、两轮 capture 684+696 / 683+695 s)⇒ 不是"某跑多编了一次"。
  **关键的精确化**:仪器 A 上 5 次独立重载(S2/S3/S4/G1a/G1b)**落在 2 个变体上**,10 对里 **6 对一致(60%)**;`S2sw1hit vs G1b = 0/512` ⇒ **G1b 就是 S11m 那个变体**。所以 S11m 的"加载 AOT 产物这条路是确定的"**只在"同一容器 + 同一时间窗"内成立**;跨时间窗/跨配置会出现**离散变体**。
  ⇒ **生产没有"用默认图配置换回可复现"这条路**(而且它的代价还是启动 ≈26 min、余量 66 MB @16 GiB swap)。
* **S14e G2(只换图配置)**:`PIECEWISE`+`1 2 4 8` 三次重载落 **3 个变体**、一致率 **8/36(22%)** ⇒ **省内存配置不是"会不会分叉"的原因,只是抬高频率**(默认 50% → 省内存 22% → S14d 的 TP=4/262144 **2.4%**)。
* **⚠️ 由此否证 S11m 的部署配方**:"冷启动预热一次 → 重启即可复现"**不成立**(G1a/G1b 正是该场景,差 403/512);预热保留,但只当**启动加速**用(见 §3)。
* **S14g(05:xx,最后一枪):变体钉不住 ⇒ 不存在"可复现的 graph 配方"**。
  * **H1 ASLR 否证**:`z100-s14` 的默认 seccomp 拦 `personality(2)`,容器内 `setarch -R` **EPERM**(不是没装),故另建同镜像兄弟容器 `z100-s14g`(`--security-opt seccomp=unconfined`)才跑通。关掉 ASLR 后 **PIE 基址被钉死**(`555555554000`,两个 TP worker 逐字节相同),但 **heap/mmap 形态每跑仍不同**;两次 run **0/8 逐位一致**(`max|Δlp|` 0.401 nat),且落到**此前 14 跑从未出现的两个新变体**上;同容器 ASLR-on 对照则落回最常见的那个吸引子(与 S11m S2/S3/S4、S14e G1b/G2c 同签名)⇒ **布局确实参与决定变体,但关 ASLR 钉不住**。
  * **autotune 排除**:GDN prefill 的 7 个 `@triton.autotune` kernel 在两次 run 上 **config 逐字相同、全部命中磁盘缓存**(`bench_time=None`);`TRITON_CACHE_AUTOTUNING=1`(默认),当天 8 次健康 run **未写任何新 autotune JSON** ⇒ 不是 autotune 抽签。
  * **结论**:**没有任何配置/环境手段能把 graph 的变体钉住**。残余最可能是 **allocator 残余地址布局 → Triton specialization/cache key 变化**,该方向需要编译期取证(超出已完成范围)。
  * **工程注意**:`PYTHONPATH`/sitecustomize 注入**到不了** `VLLM::Worker_TP*`(只有 API server 生效),要用 site-packages `.pth`;worker 的 `/proc/*/environ` 被进程标题覆写、**不可信**;保持 `TRITON_CACHE_AUTOTUNING=1`,**不要**给引擎加 PYTHONPATH 钩子。
* **生产定论(两条路,已无第三条)**:**要 token 流可复现 ⇒ eager**;**要 2.44× ⇒ 省内存 graph 配方 + SLA 写明"重启后输出可变"**(12 题中 8 题 token 流会变;同上下文 `max|Δ| ≈0.3–0.4 nat`)。
* **E5(顺带纠正我此前的推断)**:我怀疑的"C2 142.59 vs P4e 126.83 = 没挂 swap"**不成立** —— 挂 16 GiB swapfile **133.83 ms** vs 不挂 **131.78 ms**(1.6%),而那 16 GiB **一页未用**、两边 available 都是 6.1 GiB ⇒ 是**抖动/vintage**,**"生产机需要内存余量"对 eager 不成立**(该条对 graph 仍成立)。
* **E3(新洞,已单独立项)**:conc=2 与串行在第 6 token 分叉(mean 1.82 / max 15.02 nat),而无并发的串行重发**逐位一致(|Δ| = 0.00000)** ⇒ 这是 **eager 的"批组合效应"**(该效应本身完全可复现:两个独立引擎五个数字相同)。**⇒ 本项目此前所有"conc=1 与 conc=8 混用"的数值对比都可能混入了批组合,评测必须固定并记录批组合。**

**可执行的部署口径(S14d §4.3 原文,可直接粘贴)**
```text
① 质量/精度/回归/审计口径 -> eager(TP=4, --enforce-eager), 且固定批组合:
   * eager 跨引擎逐位可复现; 同 prompt 串行重发 = 逐位一致(0.00000 nat);
   * 但 conc=2 与 conc=1 不同(第 6 token 分叉、mean 1.82 nat)
     => 评测必须记录并固定 --max-num-seqs / 批组合, 否则不可比。
② 性能口径 -> graph 可用(49.65 ms, TP=4, S14c 配方), 但只用于"延迟/吞吐/内存"测量,
   绝不用于 token 流。
③ 预热(AOT 重载) -> 保留: ready 352->230 s、compilation 117->25 s, 对数值无影响;
   生产启动用"空 cache 预热一次再重载"仍是最省时的做法。
④ 内存配方 -> 沿用 §5.1(graph + 附加 4 GiB swap + swappiness=200);
   eager 侧不需要内存条款(E5)。
⑤ 若要上 graph 做服务 -> 必须在 SLA 写明"同一请求跨重启/跨批组合的输出不保证一致",
   并在任何质量门禁之前用 eager 复核。
```

## 5. 内存 / swap 要求(S14c 实测,Lead 已用原始 trace 独立重算)
已知事实(全部实测):
* **27B TP=4 graph 是"稳态装不下",不是"启动尖峰装不下"**:peak−steady 只有 **1469 MiB**(C1),C2/C3 甚至为 **0** ⇒ 限捕获桶/清编译缓存/AOT 重载这类"降尖峰"手段**注定无效**。
* **TP 对齐后 graph 比 eager 每 worker 多 ≈1.4 GiB**(×4),被 EngineCore 反向的 ≈1.4 GiB 抵消 ⇒ 净缺口 **≈4 GiB(不是 S14 首版的 8.8 GB)**。
* **已排除的杠杆**:`MALLOC_ARENA_MAX=1`(C4 仍 OOM)、`MBT=512`(C6 反而最紧:minAvail 0.33 GiB)、`VLLM_DCU_USE_INT8_SDOT4=0`(同档 OOM)、图池压缩(1.67→0.22 GiB 仍 OOM)。

### 5.1 达标判定(Lead 独立重算 C10–C15 的 `*-memtrace.log`,归档 `z100-14c-*.md` 收口中)
| arm | swap 配置 | `swappiness` | decode 中位 | **min MemAvailable** | swap 峰值 | 判定 |
|---|---|---|---|---|---|---|
| C11 | 仅 `/swap.img` **4 GiB** + AOT 重载 | 默认 | 50.04 ms | **0.72 GiB** | 3.02 GiB | ❌ 余量不足 |
| C15 | 仅 `/swap.img` **4 GiB** + AOT 重载 | **200** | 50.30 ms | **1.78 GiB** | 4.00 GiB(打满) | ❌ 差 0.22 GiB 未达 2 GB |
| **C14** | **8 GiB** + AOT 重载 | **200** | **49.65 ms** | **2.35 GiB** | 5.40 GiB | ✅ **达标** |
| **C13** | **10 GiB** + AOT 重载 | **200** | 49.83 ms | **2.71 GiB** | 5.93 GiB | ✅ 余量最宽 |

**结论(与 S14c 归档 §3.13/§6.2 一致,S14c 判 G3 口径② 达成)**:
1. **decode 全部达标**:所有 arm **49.60–50.30 ms/token**,远优于 55 ms 的验收线,与 49.66 基准一致。
2. **"不挂 swap"做不到**:稳态即超出物理内存(S14c 已证"降尖峰"无效)。
3. **口径② 达成(注意计数口径)**:验收线里的"≤4 GiB swap"指的是**我们新增的 swapfile**。实测 **新增 4 GiB swapfile(宿主原有 `/swap.img` 4 GiB,合计 8 GiB)** + `swappiness=200` + AOT 重载 ⇒ **余量 2.35 GiB、decode 49.65 ms**(C14);若只看"总 swap ≤4 GiB"(C15,仅 `/swap.img`)则余量只有 **1.78 GiB**、且 swap 100% 打满。**生产按 C14 口径部署。**
4. **`swappiness` 是关键旋钮**:同样 10 GiB swap 下,默认 swappiness 的 C10 余量 **0.29 GiB**,调到 **200** 的 C13 是 **2.71 GiB**(把冷页主动换出,给匿名热页留 RAM)。这与"被换出的是加载期 staging/冷页"一致。
5. **生产建议口径**:专用 NVMe swapfile(**新增 4 GiB**,与已有 `/swap.img` 合计 8 GiB)+ `vm.swappiness=200` + **AOT 重载预热** + `-cc.cudagraph_mode=PIECEWISE --cudagraph-capture-sizes "1 2 4 8"`。**必须监控**:`/proc/swaps` 用量、`dmesg | grep global_oom`、`Available KV cache memory`。
6. **不要用默认图配置**(51+2 桶):S14c C7 实测 ready **1645 s**、余量仅 **66 MB**,只换 4.3% decode。

## 6. 运维与回滚
